## Root cause confirmation

`scripts/biddeed-daily-digest.cjs` `getLeads()` (pre-fix) selected every
`lead_profiles` row with `stage != 'unsubscribed' AND email IS NOT NULL` — no
consent predicate existed in the code at any point in this window. The ~50%
failure rate every run was Resend's sandbox-domain restriction rejecting most
addresses outright, not a compliance control; the 14–3 addresses/day that did
get through were 100% non-consented (skip-traced individuals and LLC-buyer
contacts), never anyone who opted in.

## Fix applied (this issue)

- Consent gate: `getLeads()` now queries `email_consent = true OR
  marketing_consent = true`, then subtracts anyone in the new
  `email_opt_outs` or `email_suppressions` tables, then re-verifies the count
  against an independent query and hard-fails if it's ever exceeded. See
  `scripts/biddeed-daily-digest.cjs`.
- Live consented count as of this audit (VERIFIED, queried moments before
  writing this doc): **2** `lead_profiles` rows have `email IS NOT NULL AND
  (email_consent OR marketing_consent) = true`, both `source='test'` /
  `source='reel'`, neither opted out. This number moves as real inbound leads
  consent (the GTM funnel is live) — every future run re-queries it live, this
  document does not hardcode a number into the pipeline.
- One caveat, INFERRED not fabricated: a third consented row (`source='reel'`)
  existed at 2026-09-05 14:20 UTC per this issue's own VERIFIED opening
  comment, and is no longer present in `lead_profiles` seconds ago when this
  audit was run — the row was deleted by some other process between the issue
  being filed and this fix landing. Not caused by this session (`email_opt_outs`/
  `email_suppressions` only ever INSERT, never touch `lead_profiles`, and no
  DELETE against `lead_profiles` was run). Flagged for Ariel's awareness, not
  investigated further — out of this issue's scope (M5).
- 21 addresses (the 15 above + the 6 pre-existing `source='unsubscribe_link'`
  rows) added to `public.email_suppressions` (local audit trail,
  `resend_synced=true` for all 21) and to the Resend `General` audience as
  `unsubscribed:true` contacts (best-effort compliance signal — Resend's
  contact-unsubscribed flag governs Broadcasts, not `emails.send()` calls, so
  the actual enforcement is the consent gate above, not this sync).
- The 6 `unsubscribe_link` rows were additionally backfilled into
  `email_opt_outs` (see migration `20260905c_gtm5_digest_consent_20034.sql`),
  treating them as opted out today per intent guardrail #2.
- One-click unsubscribe: `supabase/functions/email-unsubscribe` (deployed,
  HMAC-signature-gated, writes only to `email_opt_outs`), wired into every
  send via the footer link and `List-Unsubscribe` / `List-Unsubscribe-Post`
  headers.
- `lead is not defined` bug (the exact bug that failed the 2026-09-05 test
  send, `docs/spec/20029.md` §7) fixed — `featuredCard()` now receives `lead`
  as a parameter instead of reading it from an out-of-scope closure.
- Cron changed from `0 10 * * 1-5` (06:00 ET weekdays) to `0 22 * * *` (18:00
  ET daily), per `docs/gtm/GTM_SOP_v1.md` §3.
- Re-verification dry run (`TEST_EMAIL=everestcapital8@gmail.com`, the

  guardrail #1): log shows `Sending to 1 recipients across 50 counties` /
