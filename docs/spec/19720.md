## Negative test result
- **Future-dated winner guard**: `BEGIN; UPDATE ... WHERE auction_date > current_date; ROLLBACK;` →
  raised `23514 harvest_completeness guard: cannot write winning_bidder/sold_amount for
  auction_date 2026-09-03 (future, ET today=2026-09-02)`. Confirmed still rejects.
- **Forced-bad-credential login failure**: `REALFORECLOSE_PASSWORD=deliberately_wrong...`
  for one call against alachua/realtaxdeed → server responded `{"isOk":"NO"}`, script
  exited 1, zero result rows written, logged to `harvest_runs` with `login_ok=false`.
  Real credential confirmed intact immediately after (not persisted/overwritten in env).
- **Zero-scheduled county**: `glades`/foreclosure has zero rows anywhere in
  `v_harvest_completeness_30d` → `pct` reads NULL via `nullif`, never fabricated 100%.
- **Idempotency**: re-ran `realtdm_completeness_sweep.py seminole` twice back-to-back.
  Row count went 59→62 (3 new distinct case_numbers appeared between fetches — the
  portal's own live state, not a script artifact) but **zero duplicate case_numbers**
  (`uq_mca_county_case_sale (county, case_number, sale_type)` + `ON CONFLICT DO UPDATE`
  makes duplication structurally impossible). Gap noted: the script's own
  `rows_written` metric reports cards-processed, not new-vs-updated delta — doesn't
  literally print "0" on a no-op rerun even though the DB state is correctly idempotent.
- **Golden set self-correction** (not in the DoD's negative-test list, but the same
  spirit): `harvest_golden_check()` caught 2 real bugs (plaintiff-name misclassification,
  fixed in the trigger) and 3 of my own golden-set authoring errors (wrong case_number
  guessed for 3 counties, one wrong expected-result before I'd checked
  `auction_status='cancelled'` predated the harvest). All corrected; 14/14 now pass.

## Deviations from intent
- **`spi_task_registry.domain='harvest'`** does not exist — the live CHECK constraint
  only allows `BUSINESS`/`MICHAEL`/`FAMILY`/`PERSONAL` (this table is Ariel's personal
  SPI tracker, not an engineering-findings log). Filed under `domain='BUSINESS'` with a
  `[harvest]` tag in the description instead of blocking on this.
- **`harvest_quarantine` scope wider than the DoD's literal check**: the DoD's negative
  test only asks about `winning_bidder`, but the guard trigger (per the issue's own
  Phase 1 spec, item 5) also covers `sold_amount`. That caught 124 additional
  future-dated `sold_amount` rows (mostly Duval, 115 of them) beyond the 2 the intent
  found — a second, larger latent integrity bug, not scope creep.
- **Golden set is 14 rows, not 50**: built exclusively from genuinely re-verified live
  fetches this session (no synthetic/guessed rows) across 8 counties and all 3
  platforms. Reaching 50 needs more live harvest runs than fit this session's
  time/credential-risk budget (each realforeclose/realtaxdeed county costs one login
  against Ariel's account; intent flags Aug 10 lockout as the known failure mode, so
  logins were kept to the minimum needed to prove each platform's write path).
- **Phase 2 daily sweep is not scheduled** — see Open items, blocked by standing
  mandate M5, logged to `agent_ops_log`.
- **Phase 3 realtdm harvest is not authenticated** — turned out unnecessary; the
  portal is public (see Phase 0 comment on the issue), so no credential risk applies
  to the 8/12 counties that returned data.
