# Spec — issue #19829 — P1: composer persistence (Claude.ai UI parity, phase 1 of 4)

## Intent reference
No `docs/intent/19829.md` exists. No `docs/design/BIDDEED_CLAUDE_UI_PARITY_ARCHITECTURE.md` exists anywhere in the
repo (confirmed via repo-wide case-insensitive search before starting) despite the issue body citing it as the
canonical schema/architecture source. This session worked from the issue body alone, per the artifact-chain rule
(intent > body > comments, and body is what's available). See "Deviations" below for how this was handled.

## Scope actually attempted this session
The issue is P1–P4 across five brand-new subsystems (composer menu, Deal Rooms, Report panel, Skills registry,
Connectors, Alerts sidebar) layered onto a single 8,000-line vanilla-JS Cloudflare Worker with **zero** existing
chat-persistence, auth, or storage infrastructure. Per the issue's own phase gate ("do not start P2 until P1 is
merged and verified live"), this session built **P1 only**: composer "+" menu, upload + extraction, message
actions, persisted chats, and search. P2–P4 are explicitly not started (no Deal Rooms/Reports/Skills/Connectors/
Alerts code or schema exists yet) — that is intentional phase discipline, not an oversight.

## Deviations from intent (all material ones, with reasons)

1. **Schema location**: issue calls for a dedicated `chat` schema. Live-tested and confirmed this project's
   PostgREST exposed-schema list is `{public, graphql_public, pascal, geo_tracker, finance, winnerdata}` and does
   NOT include `chat` — confirmed with both the anon key and the service_role key (`PGRST106 Invalid schema:
   chat` in both cases; the restriction predates role permissions). A table in an unexposed schema is
   unreachable from the Worker (which only talks REST, not psql) forever, so I used `public` with a
   `biddeed_chat_*` prefix instead. Documented at the top of the migration file.
2. **Table naming**: the natural prefix `chat_*` (`chat_messages`, `chat_uploads`) collided with a **pre-existing,
   unrelated** table set already in `public` — an internal session-analytics system (`chat_messages`,
   `chat_uploads`, `chat_sessions`, `chat_reconciliation`, `chat_ground_truth`, columns like `task_id`, `domain`,
   `adhd_interventions_triggered` — nothing to do with biddeed.ai end-user chat). First migration attempt hit this
   via `CREATE TABLE IF NOT EXISTS` silently no-op'ing against the wrong table, then failed loudly on the first
   dependent `CREATE INDEX` (`column conversation_id does not exist`) — caught before any write occurred, nothing
   on the pre-existing tables was touched. Renamed to the collision-free `biddeed_chat_*` prefix.
3. **DB connection method**: `SUPABASE_DB_PASSWORD` fails on the pooler with `password authentication failed`
   (matches the known, already-documented constraint referenced in the standing mandate). Used the Supabase
   Management API (`SUPABASE_ACCESS_TOKEN`) for all DDL instead, per the sanctioned fallback ladder.
4. **No live Worker deploy this session**: this session has `SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_ACCESS_TOKEN`/
   `RESEND_API_KEY` but no `CLOUDFLARE_API_TOKEN`/`wrangler` auth, so it cannot run `wrangler deploy` and the
   repo's `deploy-worker.yml` only fires on push-to-main. All DB/storage/extraction/crypto logic was verified
   directly against the live Supabase project and via a local `wrangler dev` + real Chromium (Playwright)
   instance; the actual production `/chat/api/*` HTTP endpoints remain UNTESTED against the real deployed edge
   until this PR merges.
5. **New required secret is deliberately NOT required**: `SUPABASE_SERVICE_ROLE_KEY` is a new Cloudflare Worker
   secret this feature needs, and this session has no way to `wrangler secret put` it (same credential gap as
   #4). Following the exact documented lesson in `wrangler.toml` about the 2026-07-31 `ROUTER_PROXY_KEY`
   incident (shipping a required-secret switch before provisioning it broke prod), every new code path here is
   **fail-open**: `hasServiceRole(env)` gates all persistence/upload endpoints, and if the secret is unset they
   return a clean `503`/no-op rather than crashing — anonymous chat is provably unaffected either way. The chat
   identity HMAC key is derived from the *existing*, already-required `ROUTER_PROXY_KEY` secret specifically so
   this feature needs **zero** new Cloudflare secrets to ship the anonymous-safe half; only
   `SUPABASE_SERVICE_ROLE_KEY` needs provisioning before persistence actually activates (call out to Ariel before
   merge: `wrangler secret put SUPABASE_SERVICE_ROLE_KEY` on both `wrangler.toml` and `wrangler-staging.toml`).
6. **Identity is not Clerk, and is not inbox-verified**: confirmed via repo-wide grep that this app has **no**
   Clerk, Supabase Auth, or any login system anywhere — biddeed.ai is fully anonymous today. The issue assumes
   "RLS owner-only via Clerk `sub`," which does not exist. Building a full Clerk tenant integration into a public,
   anonymous marketing/chat site is a P0-scale prerequisite, not a P1 sub-task, and was not attempted. Instead:
   `POST /chat/api/identity` issues an HMAC-signed token binding a *claimed* email (reusing the exact
   Bearer-token auth shape this codebase already uses for MCP report-access keys). This gives real, verified,
   tamper-proof separation between two different token holders (see RLS evidence above) — it does **not** prove
   the token holder owns that email's inbox. That gap (magic-link/OTP verification) is explicitly deferred, not
   silently claimed as done. This decision will compound into P2 (share links) and P3 (alerts/connectors), which
   also assume real identity — worth a deliberate call before those phases start, not another silent workaround.
7. **Pre-existing dead header discovered, not fixed**: `/chat`'s own `<header class="hdr">` (logo, brand text, the
   old `$99/mo` link) is fully hidden (`display:none`) in production because `withPublicShell()`'s global CSS
   force-hides any `<header>`/`<nav>` that is a direct child of `.bd-shell-content` (the shell provides its own
   topbar). This predates this session — first found because a first draft of the new "Chats" button was placed
   inside that dead header and was invisible. Fixed by moving the new button into `.chat-col`'s own visible flow
   (`.chat-toolbar`, new). The underlying dead markup in `.hdr` is untouched (out of scope, mentioned per
   Karpathy K3 — not deleting pre-existing code that isn't part of this task).
8. **Message actions scope**: "Add to Room" and "Set alert on this sale" render **disabled** with a tooltip
   ("Coming in P2 — Deal Rooms" / "Coming in P3 — Alerts and Watches") rather than wired to nothing. This matches
   the issue's own phase gate (Deal Rooms and Alerts genuinely do not exist as subsystems yet) rather than
   building fake/dead buttons or skipping them silently.
9. **DOCX and image upload**: extraction returns `extraction_status='unsupported'` (file still stores; Deed is
   told honestly that extraction isn't available for that type). No npm PDF/DOCX/OCR library could be used
   because `deploy-worker.yml` runs `wrangler deploy --no-bundle` (confirmed: worker.js has zero `import`
   statements today) — adding a bundler step would mean editing the deploy workflow, which is out of bounds for
   this session (scope rule: no workflow-file edits). PDF got a hand-rolled, dependency-free extractor instead
   (brute-force object index + `DecompressionStream('deflate')` + `ToUnicode` CMap resolution for CID-keyed
   fonts) because it was the DoD's literal named case; DOCX/image OCR are deferred, flagged honestly rather than
   silently no-op'd.
10. **"Deep Research → SIGNAL$"**: wired to ask Deed (via the existing chat pipeline, which already knows to
    surface the $25 SIGNAL$ report) rather than to a new automated report-generation trigger — the existing
    `/report/json` SIGNAL$ flow is a separate, already-paid/gated product surface (`/buy-report` → Stripe
    checkout) that this session did not touch or attempt to auto-invoke from chat.
