## Normalizer reused (per issue instruction — do not write a new one)
Canonical source: `scripts/property_appraiser/common.py:_norm_text()` —
`re.sub(r"[^A-Z0-9]", "", str(s).upper())`. SQL equivalent used everywhere in
this work: `upper(regexp_replace(parcel_id, '[^A-Za-z0-9]', '', 'g'))`.

`zw_parcels` already had this exact normalization pre-computed and fully
populated in `pin_clean` (0 nulls across 10,514,611 rows, confirmed live) with
`idx_zw_parcels_pin_clean` — reused as-is, no new DDL there. `fl_parcels` had
a narrower existing expression index (`idx_fl_parcels_co_no_parcel_norm`,
strips only `-`, ` `, `*`) that under-matches dot/slash variants named in the
issue — this session added the full-normalizer equivalent alongside it
(does not replace/drop the narrower one).

## What was built
1. **`supabase/migrations/20260906i_mca_zip_backfill_parcel_norm_20055.sql`**
   (tracked + applied live via Management API):
   - `idx_fl_parcels_co_no_parcel_norm_alnum` — btree on
     `(co_no, upper(regexp_replace(parcel_id,'[^A-Za-z0-9]','','g')))`.
     **Deviation from the issue's suggested implementation, logged per K3:**
     the issue asked for a *stored generated column* + index, built via a
     post-reboot pg_cron scheduling trick (assuming DDL could only land in
     ~14-minute windows). A stored generated column on an 11 GB/10,516,355-row
     table requires a full table rewrite — high risk of being killed mid-
     rewrite by the next restart with zero partial credit. A plain expression
     index gives the same query acceleration without rewriting the table.
     Applied directly (no cron scheduling needed) with
     `SET maintenance_work_mem='1GB'`, non-concurrent, single statement.
     **Build time: 45 seconds** (14:47:24–14:48:09 UTC), size 395 MB.
   - `public.mca_parcel_zip_lookup(p_co_no int, p_parcel_id text)` — SQL
     SECURITY DEFINER RPC, same grant pattern as
     `public.ff_mls_parcel_audit`. Collision-safe: returns a row only when
     every fl_parcels match for the normalized parcel_id agrees on exactly
     one well-formed 5-digit zip. Used by the harvest ingest wiring (below).
2. **`scripts/realauction_winner_harvest.py`** — added `get_co_no()` (one
   `fl_counties` lookup per run, cached; a harvest run covers a single
   county) and `lookup_zip_by_parcel()` (calls the new RPC). Wired into the
   `insert_row` fallback: when the platform's own `city_state` string yields
   no trailing 5-digit zip via regex, fall back to the normalized-parcel-id
   join before leaving `zip` null.
3. Live data backfill (see Results) via ad-hoc, collision-safe, checkpointed

   data UPDATE, idempotent on `zip IS NULL`, matches the repo's established

## Collision safety (found live, designed around)
- `fl_parcels.phy_zipcd` and `zw_parcels.site_zip` both carry a real garbage
  sentinel value `'0'` for some rows (confirmed live) — excluded via
  `~ '^[0-9]{5}$'` on the source side, not just the destination.
- `idx_auctions_dedup_key` is a partial unique index on
  `(source_platform, auction_date, property_address, zip)` — a naive backfill
  crashed the very first batch attempt by writing a zip that collided with
  either (a) an existing other row, or (b) a sibling row being updated in the
  **same** batch (two duplicate-looking auction rows for the same real
  case/date/address). Fixed with a `NOT EXISTS` guard against existing rows
  plus an in-batch `ROW_NUMBER()` dedup so at most one row per
  `(source_platform, auction_date, property_address, zip)` group is written
  per pass. Rows that lose this dedup keep `zip IS NULL` (never crash, never
  silently overwrite).
- A normalized match is only trusted when every matching `fl_parcels` row for
  that `(co_no, parcel_id_norm)` agrees on a single zip
  (`array_length(zips,1) = 1`) — ambiguous matches are left null.
- **Never overwrote a non-null zip** — every UPDATE carries `AND zip IS NULL`.

## Coverage bug found and fixed mid-session (self-caught)
First backfill attempt batched via `... ORDER BY id LIMIT 500` re-selected on
`zip IS NULL`. Rows that are permanently unresolvable (no fl_parcels/zw_parcels
match) never leave that `zip IS NULL` pool, so the sliding window got stuck
re-examining the same unresolved head-of-table rows and falsely converged to
"0 new" after only ~9 batches (4,500 of 11,466 candidate rows) — a false
completion signal, not real exhaustion. Fixed by splitting into two phases:
(1) one exhaustive `SELECT` (index-driven, fast, not batch-limited) that
identifies every safely-resolvable `(id, zip)` pair across the full cohort,
then (2) applying that fixed, already-resolved list in explicit ≤500-row
`UPDATE ... WHERE id = ANY(...) AND zip IS NULL` chunks — checkpointed and
idempotent, immune to the same stuck-window bug because the resolvable set is
computed once up front rather than re-derived per batch.
