## Item 1-2 — root cause found and fixed

**The issue's corrected premise is right, but not quite in the way it was stated.** The pipeline's
tax_deed candidates were NOT being read from `clerk_ssot_sale_rows` (that was already fixed and
demoted to an additive, 0-row-contributing source by the prior #19794 session — confirmed still
true, see "Item 2b" below). The live query
(`scripts/biddeed_reels_pipeline.py::get_reel_candidates()`, pre-this-session) read tax_deed
candidates from `public.auction_buyer_sightings`, not `multi_county_auctions` directly.
`auction_buyer_sightings` is a **derived/classification table**, not the raw auction-results table,
and it only covers a *subset* of `multi_county_auctions`:

```sql
-- live, 2026-09-03, window = last 14 days from today
select count(*) from public.multi_county_auctions
where sale_type='tax_deed' and sold_amount is not null and sold_amount > 0
  and auction_date >= current_date - interval '14 days';
-- => 125

select count(*) from public.multi_county_auctions mca
where mca.sale_type='tax_deed' and mca.sold_amount is not null and mca.sold_amount > 0
  and mca.auction_date >= current_date - interval '14 days'
  and exists (select 1 from public.auction_buyer_sightings s where s.mca_id = mca.id);
-- => 88  (70.4% of the 125 -- the 37 gap rows are the "too narrow a slice" the issue names)
```

The 37 missing rows are concentrated entirely in **Putnam county on a single auction_date
(2026-09-02)** — real, low-value tax certificate sales (`sold_amount` $860–$1,650 range) that were
simply never promoted into `auction_buyer_sightings`, for reasons unrelated to whether the sale is
real (`multi_county_auctions` has no `buyer_type` column and, per the absolute-auction rule, tax_deed
needs none — `sold_amount > 0` is sufficient by itself).

**Fix applied** (`scripts/biddeed_reels_pipeline.py::get_reel_candidates()`): the single `mca_source`

`sale_type='tax_deed' and sold_amount > 0` over the requested date range — no
`auction_buyer_sightings` dependency at all for tax_deed. `clerk_priced` (the additive, dedup'd
`clerk_ssot_sale_rows` branch) is unchanged in behavior, now deduplicating against the union of both

## Item 2 (continued) — real tax_deed parcel-join rate (NOT assumed at parity with foreclosure)

The issue explicitly warns not to assume parity with foreclosure's join rate. **Correct methodology
check first:** the production code does **not** join on `multi_county_auctions.parcel_id` directly
— `scripts/biddeed_reels_lib.py::match_parcel()` matches by **normalized street address** against
`public.zw_parcels.site_addr` (with a county filter), because `multi_county_auctions.parcel_id` is
each county's own short/local ID format (e.g. Brevard `2919221`), not the FL statewide format
`zw_parcels.pin_clean` uses. A naive `parcel_id = pin_clean` string-equality check would
under-measure this (it happened to show 9/125 = 7.2% on a first pass) — the real number has to use
the same address-matching code path `process_row()` actually calls.

**Measured live, this session, using `match_parcel()` (the real production function), against the
124-row corrected `taxdeed_source` candidate pool (window 2026-08-20..2026-09-02):**

```
sampled 86 of 124 rows before the run was cut short (see below) -- 0/86 matched (0%)
by county: pasco 0/20, putnam 0/20, washington 0/15, brevard 0/10, volusia 0/9,
           highlands 0/5, lee 0/3, santa_rosa 0/2, bay 0/2
```

**This measurement was cut short, honestly reported rather than silently extrapolated:** each
`match_parcel()` call does an `ilike` scan of `public.zw_parcels.site_addr` (a table with no
trigram/functional index for this predicate on a ~10.5M-row table) — live-reproduced this session, a
single such query (`county=ilike.Putnam&site_addr=ilike.MAIN ST`) via `curl` did not return within
120 seconds. Running all 124 rows through this path (even at 12-way concurrency) stalled after ~87
completions with 0 matches; the process was killed rather than let it run indefinitely. **0/86-87 is
the real, verified sample** — not a projection. Given a 0% observed rate holding across all 9
sampled counties and 86 of 124 rows (69% coverage), the real join rate for this candidate pool is
**genuinely near 0%, categorically different from foreclosure's ~48% same-window rate**
(`120/248` measured the same way earlier this session) — this is a real data ceiling (tax-deed
source addresses/parcel formats not matching `zw_parcels.site_addr`'s format for the counties in
this window), not a coding bug, and not something this issue's scope can fix (would require either a
per-county address-normalization crosswalk or a parcel-ID crosswalk table, both out of scope here).

**Negative test (a) compliance unaffected:** the existing pipeline (`process_row()`) already refuses

Between session 1 (above) and this session, **the Architect performed a manual backfill via direct

tax_deed rows inserted into `winnerdata.biddeed_reels` at `status='generated'` (5 pre-existing rows

### Defect 1 — premium-sale rows would get a false "sold below assessed" narrative

**Real prevalence, measured live against the full 107-row backfill (not just the 5-row spot-check):
42/107 (39%)** sold ABOVE assessed value — mostly Pasco County raw-land tax certificates, delta up
to **+1266%** over assessed. This is a large fraction, not a rare edge case.

**Root cause (code read):**
- `agents/reel_studio/hook_writer.py::_payoff_phrase()` hardcoded `"...percent below assessed
  value."` unconditionally (en **and** es), regardless of `delta_pct`'s actual sign. For a premium
  sale this is a literal false claim in the spoken payoff line.
- `check_archetype_data_match()` had no direction precondition on the `hidden_value_reveal`
  archetype. Two of its five title templates (`"...Worth More Than It Sold"`,
  `"...Undersold Its Own Value"`) explicitly assert a discount story — false for a premium sale —
  and nothing blocked that archetype from being assigned to a premium-sale row (only
  `recommend_framing_archetype`'s "preferred slot" logic was direction-aware; the random pool used
  for the other 3 of 4 variant slots was not).

**Fix (`agents/reel_studio/hook_writer.py`):**
1. `_payoff_phrase()` now derives direction from `delta_pct`'s sign (`below`/`above`, `bajo`/`sobre`
   in es) instead of asserting `below` unconditionally.
2. `check_archetype_data_match()` gains a precondition: `hidden_value_reveal` fails when
   `sold_amount > assessed_value` (mirrors the existing `bank_vs_house`/`remote_bidder`
   precondition pattern already in that function — same named-check mechanism `director_qa.py`
   already enforces before a variant counts as reviewable).
3. `generate_variants_for_reel()` excludes `hidden_value_reveal` from the random archetype pool for
   premium-sale rows up front, so a doomed-to-fail variant isn't generated (and billed) via the LLM
   in the first place.

**Verified live, this session:**
```
check_archetype_data_match('hidden_value_reveal', {sold_amount:31013, assessed_value:2270}, ...)
  -> (False, ["archetype 'hidden_value_reveal' asserts the property sold for less than its "
             "real/assessed value, but this row sold ABOVE assessed_value ..."])
_payoff_phrase('postsale', {sold_amount:31013, assessed_value:2270, delta_pct:1266.2})
  -> "It sold for $31,013... 1266.2 percent above assessed value."   (was hardcoded "...below
      assessed value." before this fix)
```
**No live/shipped damage found:** a query for already-rendered `biddeed_reels` rows where
`sold_amount > assessed_value` AND `script_text`/`caption_text` contains a below-assessed/worth-
more/undersold phrase returned **0 rows** — this bug never reached a shipped script, because these
107 rows sat at `status='generated'` (pre-script) the entire time it existed.
`agents/reel_studio/eval_hook_writer.py` 42/42 and `eval_director_qa.py` 50/50 still pass post-fix.

### Defect 2 — placeholder address strings risked a false geocode, not a spoken leak

The Architect's report guessed the leak was in "the script generator." **Checked live and ruled
out:** `build_script_and_caption()` (the actual T4 script builder `process_row()` calls) and every
`hook_writer.py` script/title builder were grepped — none of them reference `property_address` at
all. The real, live risk is one step earlier.

**Real prevalence, measured live:** 9/107 (8.4%) of the backfill carry the exact literal
`"PROPERTY ADDRESS UNKNOWN"` (not 2 — the Architect's number was from a 5-row spot-check). Widening
the query to all of `multi_county_auctions` found this is systemic, not isolated: **~430 rows**
across at least 8 distinct sentinel patterns (`"00 UNASSIGNED LOCATION RE"` ×312, `"0 UNKNOWN"`
×58, `"00 Unassigned Location RE"` ×15, `"PROPERTY ADDRESS UNKNOWN"` ×11, bare `"UNKNOWN"`/`"N/A"`/
`"TBD"` ×4 each, plus `"NO ADDRESS ON TAX ROLL, <city>..."` and `"TBD, <county>..."` variants).

**Root cause (code read):** `scripts/biddeed_reels_lib.py::match_parcel()` already special-cased FL
GIO's `"NO ADDRESS ON TAX ROLL"` placeholder (pre-existing guard), but not this one — it would run a
full `zw_parcels` `ilike` scan on garbage input. Worse: `geocode_address()` (the fallback
`process_row()` calls when `match_parcel()` misses) had **no placeholder guard at all** and would
send the literal sentinel string straight to the Google Geocoding API — a real risk of a
false-positive `lat/lon` that silently pins the wrong real-world location/imagery/parcel outline to
the property (worse than "no data" — it would be *wrong* data presented with full confidence).

**Fix (`scripts/biddeed_reels_lib.py`):** added `is_placeholder_address()` — substring match on
`NO ADDRESS`/`ADDRESS UNKNOWN`/`UNASSIGNED`, plus a leading-token match on `UNKNOWN`/`N/A`/`TBD`
after stripping a leading house-number-like token (`"0 UNKNOWN"` → `"UNKNOWN"`) — wired into both
`match_parcel()` (extends its prior narrower guard) and `geocode_address()` (new; had zero prior
protection).

**Verified live, this session:**
- Unit-tested against 20 real production values (all 8 sentinel patterns + 2 real addresses as
  negative controls): **20/20 correct**, 0 false positives/negatives.
- Sampled 5,000 real `multi_county_auctions.property_address` values (tax_deed): 178 (3.56%)
  flagged; manually reviewed the flagged set — **0 false positives**, all genuine placeholders.
- `match_parcel('PROPERTY ADDRESS UNKNOWN', 'pasco')` → `None`, zero PostgREST calls fired.
- `geocode_address('PROPERTY ADDRESS UNKNOWN', <fake key>)` → `None`, zero HTTP calls fired
  (confirmed: a fake API key would surface as an HTTP error if a request had actually gone out; none
  did).
- `eval_hook_writer.py` 42/42 and `eval_director_qa.py` 50/50 still pass post-fix.
