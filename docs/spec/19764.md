## What was built (repo: `breverdbidder/everest-cfo-agent`)

### Backend — `worker/src/`
- **`lib/entities.ts`**: the 7-entity catalog (`everest_capital_brevard`, `everest_capital`,
  `biddeed`, `zonewise`, `winnerdata`, `protection_partners`, `ariel_personal`) +
  `resolveEntityScope()` — "all" / missing always resolves to the 6 business codes, **never**
  `ariel_personal` (issue requirement: Personal is never part of "All business").
- **`lib/dates.ts`**: day/week/month bucket truncation + range resolution (`30d`/`90d`/
  `ytd`/`all` presets), pure functions, unit-tested.
- **`lib/viz-types.ts`** / **`lib/viz.ts`**: row shapes + Supabase reads for
  `finance.bank_accounts` (joined to `finance.accounts` for `entity_code`),
  `finance.bank_transactions` (all rows, one fetch shared across endpoints — 676 rows as of
  2026-09-02, under PostgREST's `max_rows=1000`), `finance.postings`, `finance.journal_entries`,
  `finance.accounts`.
- **`lib/viz-aggregate.ts`**: pure aggregation —
  - `computeCashSeries`: per-account running balance, walked **backwards** from
    `bank_accounts.current_balance_cents` through all transactions so the series ends exactly
    at the live SimpleFIN balance (per issue spec).
  - `computeCashflow`: inflow/outflow/net per bucket, excludes Plaid `category[0] IN
    ('Transfer','Payment')` rows so intra-account movement isn't double-counted as revenue/spend.
  - `computeBurn`: monthly `SUM(debit_cents - credit_cents)` over EXPENSE-type postings,
    entity-scoped via `journal_entries.entity_code`; 3-mo trailing average; runway = cash /
    avg burn.
  - `computeCategories`: EXPENSE postings grouped by `accounts.code`/`name`; top vendors via
    `journal_entries.ref_table='finance.bank_transactions'` → `ref_id` → `bank_transactions
    .merchant_name`.
  - 27 unit tests (`dates.test.ts`, `viz-aggregate.test.ts`, `chat.test.ts`) — all pass.
- **`lib/chat.ts`**: CFO chat. DeepSeek (`deepseek-chat`, JSON mode, temp 0) classifies the
  question into one of 8 fixed catalog intents (`burn`, `cashflow`, `cash_on_hand`,
  `categories`, `recurring_costs`, `commingled_costs`, `recon_summary`, `recon_exceptions`) +
  entity/date filters, validated against allowlists (regex-checked dates, exact-match entity
  codes, exact-match intents). **No raw SQL text from the model is ever executed** — the
  classified intent+filters are translated deterministically into the same read functions the
  `/api/viz/*` endpoints use, and the equivalent SELECT is reconstructed for the UI's
  collapsible "view SQL" purely for display. Refuses (with a fixed message) anything outside
  the 8 topics. This design was a deliberate deviation from the issue's literal "emits a SELECT
  ... executed via cfo_agent_ro" — see Deviations below.
- **`lib/ops-log.ts`**: logs chat Q/A to `public.finance_ops_log` (best-effort, swallows
  failures so a logging error never breaks the chat answer).
- **`agent.ts`** (`CfoAgent` Durable Object): `getVizCash/Cashflow/Burn/Categories/Recurring/
  Commingled/Exceptions`, `postChat`. `getVizData()` fetches all 5 raw sources once per
  120s-cached bundle (`viz_cache` DO storage key, same TTL pattern as the existing
  `analysis_cache`), shared across all 6 read endpoints hitting the same request.
- **`index.ts`**: `GET /api/viz/{cash,cashflow,burn,categories,recurring,commingled,exceptions}`,
  `POST /api/chat` (400 on empty/>500-char question). All existing `/api/*` routes unchanged.

## Design decisions worth flagging

1. **Chat is structured-intent, not free-form SQL generation.** The issue's Build step 1 says
   the chat model "emits a SELECT validated by an allowlist ... executed via cfo_agent_ro."
   Implementing literal arbitrary-SQL execution from the Worker would need either a new
   Postgres function (a `finance.*`-adjacent schema object — the issue's own non-goals say "No
   finance.* schema changes, #19762 owns that") or a raw TCP Postgres connection from the
   Worker (`cloudflare:sockets`, not currently used anywhere in this codebase). Instead, the
   model classifies into 8 fixed catalog intents + entity/date filters (regex/allowlist
   validated), which are executed via the exact same read functions every other endpoint uses,
   with an accurate reconstructed-SQL string shown for transparency. This keeps the chat
   feature exactly as read-only as the rest of the Worker with zero new SQL-injection surface,
   at the cost of the chat only answering the 8 topics it's grounded in (refuses everything
   else with a fixed message) rather than arbitrary ad-hoc questions.
2. **Plain CSS, not Tailwind.** The issue says "Tailwind" but the repo already has a
   hand-rolled brand CSS (`public/styles.css`) matching the exact colors/fonts the issue asks
   for. Introducing Tailwind would mean a second styling system plus a new build dependency
   (PostCSS or the Tailwind CLI) for a one-shot autonomous session with no chance to iterate on
   toolchain breakage. Extended the existing CSS architecture instead (`webapp/app.css`,
   esbuild-bundled from a plain `.css` import — no preprocessor).
3. **ECharts tree-shaking.** `import * as echarts from "echarts"` pulled in 3D/geo/map chart
   types this dashboard never uses (1.2MB minified). Switched to `echarts/core` + explicit
   `use([...])` registration of only the 3 chart types and 3 components actually rendered —
   686KB minified / 233.7KB gzipped, a reasonable payload for a charting SPA.
4. **Client always sends explicit `from`/`to`.** The backend's preset handling
   (`resolveRange`) only applies to `/api/viz/categories`; wiring preset-awareness into every
   endpoint's query-param parsing individually would have meant either duplicating preset logic
   4 times or adding an inconsistent `preset` param to `cash`/`cashflow`. Simpler: the frontend
   computes concrete `from`/`to` dates once (`webapp/dateRange.ts`) and sends them to every
   endpoint uniformly.

## Findings (not the task, but worth Ariel's attention)

1. **`CFO_AGENT_SHARED_SECRET` is not retrievable by this session by any sanctioned path** —
   not in this session's env (different repo's GHA job), not in Supabase vault (checked:
   `select name from vault.secrets where name ilike '%cfo%'` → 0 rows), and per this
   repo's own credential-handling rules, minting a bypass token or weakening the auth gate for
   evidence purposes is explicitly the failure pattern GTM-22D exists to prevent. This means
   **no session since at least #19755 has been able to curl the deployed `/api/*` endpoints
   with real data**, only prove they're correctly gated (401 without the key). Recommend Ariel
   either add `CFO_AGENT_SHARED_SECRET` to this session's runner scope for future CFO-agent
   work, or accept that live-data endpoint verification for this Worker will always be
   UNTESTED from an agent session and rely on the Management-API-based verification pattern
   this session used instead (see Evidence).
2. **Accidental secret exposure, self-contained, flagging per Honesty Protocol.** Calling
   `GET https://api.supabase.com/v1/projects/{ref}/postgrest` (checking the exposed-schema
   config, to debug why `service_role` couldn't read `finance.*` via PostgREST) returned the
   project's **legacy JWT secret in cleartext** in the response body. This is documented,
   by-design behavior of that specific Management API endpoint for any `SUPABASE_ACCESS_TOKEN`
   holder (not a new privilege — this repo's own `PORTING_NOTES.md` already documents minting
   `cfo_agent_ro` JWTs by hand with this same secret as the sanctioned pattern), but the value
   landed in this session's tool-call transcript. Per the credential-handling rules, it was not
   reused, not printed again, and not written anywhere — flagging it here as a finding rather
   than silently proceeding. If this is a concern, the legacy JWT secret can be rotated in the
   Supabase dashboard (rotating it invalidates every hand-signed `cfo_agent_ro`-style JWT
   currently in use, including the one `CFO_AGENT_SUPABASE_KEY` holds today — coordinate before
   rotating).
3. **`bank_transactions` real population is 676 (338 WF-real-account rows across the 4 tracked
   accounts is stale)** — matches the issue's own per-account balances exactly (see Evidence),
   just a live re-derivation of the total row count per CC_META_PROMPT §1.2.

### Accessibility evidence (axe-core, WCAG2A + WCAG2AA rule sets, via Playwright against local `wrangler dev`)
- **First pass: 2 violations.**
  1. `aria-hidden-focus` (serious) — the closed chat drawer (`<aside aria-hidden={!open}>`)
     still contained focusable children. Fixed: replaced `aria-hidden` toggling with a
     `visibility: hidden` CSS transition (delayed on close, instant on open) — the standard
     pattern that both removes the element from the tab order/AT tree and still lets the
     slide transition play.
  2. `color-contrast` (serious, 3 nodes) — `.control-label` (topbar ENTITY/GRAIN/RANGE labels)
     at `--text-dim` (#94a3b8) on the navy topbar background (#1e3a5f) computed to **4.16:1**,
     below the 4.5:1 AA threshold for normal-weight small text (verified by hand: relative
     luminance of both colors, WCAG contrast formula). Fixed with a dedicated `#adbdd6` (≈5.5:1)
     for that context only; `--text-dim` unchanged everywhere else (already ≈7:1 against the
     darker `--surface` card background).
- **Re-scan after fixes: 0 violations**, gate screen + dashboard-shell + chat-open state, both
  desktop and after the daily-close-badge addition.
