# Spec — #20038 LAUNCH-D: winnerdata-ff Worker lockdown

Precedence: `docs/intent/20038.md` > this file > issue body > comments.

## What was built

Three changes, executed and verified live in this order (order was a hard
constraint in the intent file — deploy with secret first, verify, only then
revoke):

1. **`workers/winnerdata-ff/wrangler.toml`**: `workers_dev = true` → `false`.
   Only `ff.winnerdataai.com/*` (the `[[routes]]` binding) serves this Worker
   now. `winnerdata-ff.brevardbidderai.workers.dev` no longer resolves to it.
2. **`workers/winnerdata-ff/src/index.js`**:
   - Removed the hardcoded public anon JWT constant. `SUPABASE_KEY` is now a
     module-level `let`, assigned from `env.SUPABASE_SERVICE_ROLE_KEY` at the
     top of `fetch(request, env)` on every request.
   - Added `addSecurityHeaders()`, wrapping every response (success and
     error paths) with `X-Robots-Tag: noindex, nofollow` and
     `Cache-Control: private, no-store`.
   - No changes to `renderFF()`, the `values` object, or the imported
     template — producer-facing HTML is unchanged except `prepared_date`
     (confirmed by code-diff review; this session did not capture a byte-for-
     byte pre-image of a specific `/ff/<uuid>` page before the deploy, so the
     "byte-identical" claim is CONFIRMED by diff inspection, not a literal
     before/after `diff` of a saved HTML file).
3. **`.github/workflows/deploy-winnerdata-ff.yml`**:
   - New step "Set SUPABASE_SERVICE_ROLE_KEY worker secret" runs
     `wrangler secret put` (from `workers/winnerdata-ff`, using the repo's
     already-present `secrets.SUPABASE_SERVICE_ROLE_KEY` + `secrets.CF_API_TOKEN`/
     `secrets.CF_ACCOUNT_ID`) immediately before the `wrangler deploy` step, so
     the new secret-reading code is never live without the secret.
   - "Guard - required secrets present" now also fails closed if
     `SUPABASE_SERVICE_ROLE_KEY` is absent.
   - "Verify live" now asserts `ff.winnerdataai.com/healthz` **is** 200 and
     `winnerdata-ff.brevardbidderai.workers.dev/healthz` is **not** 200 (the
     inverse of the old workers.dev-as-fallback logic, which is obsolete now
     that `workers_dev = false`).
   - "Security gate" no longer checks the workers.dev URL (nothing to check —
     it should not resolve).
4. **`supabase/migrations/20260905d_ff_worker_revoke_anon_20038.sql`**:
   `REVOKE EXECUTE ... FROM anon, authenticated` on `ff_portal_leads(uuid)`,
   `ff_get_lead(uuid,uuid)`, `ff_record_bind(uuid,uuid,integer,text)`,
   `ff_upsert_response(uuid,uuid,text,text,text,text)`, `ff_healthz()`.
   Applied live via the Supabase Management API SQL endpoint
   (`SUPABASE_ACCESS_TOKEN`, same pattern as
   `.github/workflows/set-worker-secret-from-vault.yml`) — direct psql via
   `SUPABASE_DB_PASSWORD` is a known-broken path in this environment (decision
   log ids 169/205/287), so this is the standing working pattern, not a
   deviation.
5. **`BIDDEED_SSOT.md` §1**: added the `winnerdata-ff` Worker row (none
   existed before this issue) documenting the lockdown and the pre-existing,
   still-open `wd_*`-function gap on `/producer-report`/`/owner-dashboard`.

No template changes. No `wd_*` functions created. No LMS changes. Nothing
sent to Mariam or any producer (M1) — no batch, digest, or email touched.
