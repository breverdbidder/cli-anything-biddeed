## What was built

### Tier 1 — Lien search (Brevard) — LIVE, real data
- **`supabase/migrations/20260906e_title_tier1_results_20045.sql`** — new table `public.title_tier1_results` (mca_id, case_number, county, parcel_id, instrument_type, recording_date, book_page, instrument_number, transaction_item_id, direct_name, indirect_name, amount, status, source, raw_data jsonb, fetched_at). RLS enabled, no anon/authenticated policy (M2). **Applied live** — confirmed via SQL VERIFICATION below.
- **`scripts/pre_auction_lien_harvest.py`**:
  - Added `"brevard"` to `COUNTY_ACCLAIM` (base `http://vaclmweb1.brevardclerk.us`, prefix `/AcclaimWeb` — lifted from `scripts/acclaim_case_lookup.py`'s already-proven-working constant, same classic-ASP.NET AcclaimWeb family as santa_rosa/highlands). Brevard had never been in this dict before — `acclaim_case_lookup.py`/`acclaim_ct_sweep.py` only ever used `case_lookup()` for parcel-linkage and CT-sweep, never ran `classify_docs()` against Brevard.
  - **Real bug found and fixed**: Brevard's AcclaimWeb serializes `RecordDate` as an ASP.NET JSON date (`/Date(1725460460000)/`, epoch ms) and names the book/page field `Bookpage` (lowercase p) — not the `'YYYY/MM/DD'` string + `BookPage` shape Duval/Highlands return, which `classify_docs()`/`tier1_rows()` assumed. Unfixed, this would have (a) written garbage into the `date`-typed `recording_date` column (confirmed live: first insert attempt 400'd), and (b) silently miscomputed the Tier 2 senior/junior recording-priority comparison for any Brevard case with a real third-party lien. Added `normalize_brevard_docs()` — Brevard-only, does not touch the shared function or any other county's behavior.
  - **Second bug found and fixed**: the primary `classify_docs()` call in `main()` never passed `source=`, so every non-Duval county's `title_defects`/`lien_results` rows were mislabeled with the function's `"duval_acclaimweb_case_search"` default regardless of which county actually produced them. Fixed to pass `source=f"{county}_acclaimweb_case_search"` (byte-identical value for Duval, so Duval's behavior is unchanged).
  - Owner-name sweep (`name_lookup()`) explicitly **skipped for brevard** — that 3-step flow is reverse-engineered from Duval's Kendo-UI build; Highlands (the other classic-ASP.NET county) needed a separate Playwright driver because its real form differs, and Brevard was never verified either way. Disclosed gap, not attempted.
  - New: `tier1_rows()` / `tier1_statuses()` / `write_tier1_results()` — write the FULL per-case recorded-instrument list (every doc type, not just the lien-type subset `lien_results` keeps) to `title_tier1_results`, idempotent on `(mca_id, transaction_item_id)`. A real zero-document search writes a `NO_DOCUMENTS_FOUND` marker row (idempotent per mca_id) so the report can render "No instruments found ... verify" instead of a re-scrape-pending Pending.
- **`packages/biddeed-mcp/src/report/title-tier1.js`** — new. `buildLienSearch({mca_id, county}, {get})` reads the cached `title_tier1_results` rows; never re-scrapes.
- Wired into `composer.js`'s `buildReport()` as `report.title_tier1` (always computed, like `report.lien_survival`).

### Tier 2 — Lien survival (Brevard) — LIVE, real data
- No new code needed for the classifier itself — `packages/biddeed-mcp/src/report/lien-survival.js`'s `classify()` was already generic (reads `lien_results`/`title_defects` by case_number/parcel_id, county-agnostic). It had simply never had any Brevard rows to read (confirmed live at session start: 0 of 76 `lien_results` rows were Brevard-sourced). The Tier 1 harvest fix above populated real `title_defects` rows for 3 Brevard cases, which is enough for `classify()`'s `checkSearchedClean()` path to return a real "searched, zero third-party liens found" result — verified live (see evidence below).
- **Fix**: `baseItem()` in `lien-survival.js` was selecting `amount` from `lien_results` but never returning it on the item — the section-15 deduction logic (see below) had no way to read a lien's face amount. Added `amount` to the returned item.
- **§15 max-bid/verdict deduction** (`composer.js`): moved the `lien_survival.classify()` call earlier (into the same `Promise.all` as CMA/model/etc.) so its output is available before the ceiling/verdict decision. Added `survivingLienKnownDeduction` (sum of `survives===true` items with `amount > 0`, computed on a SEPARATE `effectiveCeiling` used only for the verdict/margin/outcome calculation — the raw `shapira_max_bid.value`/`bid_floor`/`bid_ceiling` triple is left untouched so `sellability.js`'s self-consistency gate, which validates the ceiling against its own formula bounds, cannot be broken by a lien deduction) and `survivingLienUndetermined` (any `survives===true` item without a usable face amount — downgrades `BID`→`REVIEW` and adds a `SURVIVING_LIEN_AMOUNT_UNDETERMINED` red flag; never silently ignored). A known deduction adds a `SURVIVING_LIEN_DEDUCTED` red flag stating the exact dollar figure and before/after ceiling. **Arithmetic verified** with a synthetic 3-item fixture (senior HOA lien $5,000 survives+known, mortgage survives+unknown, mechanic lien $9,999 extinguished) — assertions passed (deduction=$5,000, undetermined=true, effectiveCeiling=$95,000 off a $100,000 base). **Not exercised live end-to-end** — none of the 3 real Brevard test cases harvested this session had an actual third-party lien (all three were clean single-mortgage foreclosures with 0 lien-type documents), so this path is code-verified + unit-verified but UNTESTED against a real surviving-lien Brevard case. Flagged as an open item below.

### Tier 3 — Title search / chain of title (Brevard, partial, honestly gated)
- Read `docs/plans/title-chain-pull-P1-build-brief.md` in full. Its literal P1 scope is Duval-only; applied its generic two_owner algorithm/result-model "as far as it goes for Brevard" per the issue body (which takes precedence over the brief per M6 — the brief is a referenced design doc, not the intent file).
- **`scripts/brevard_title_chain_tier3.py`** — new. For a given case: resolves `parcel_id`/`mca_id` from `multi_county_auctions`, reads the ALREADY-HARVESTED `title_tier1_results` rows for that case (no re-scrape), looks for a DEED-type instrument naming the current owner. Writes one `title_chain_pull` header (`status='partial'`, `depth='two_owner'`, `source_platform='acclaim'`) per case, idempotent (checked by `parcel_id`+`county`). If no deed-type document is found among the case's own court filings (expected — see honest limitation below), writes a `title_chain_gap` row (`honesty_marker='UNKNOWN'`) rather than guessing an owner. If one is found, writes a `title_chain_owner` row with `reconciliation_confidence='name_only'`, `honesty_marker='INFERRED'` (never `VERIFIED` from a case-index search alone, per the brief's own reconciliation gate).
- **Honest limitation, disclosed not hidden**: a case-number search only returns documents FILED IN THIS LITIGATION (Lis Pendens, Judgment, Orders). The original recorded deed into the current owner is a separate, earlier instrument tied to no case number — finding it needs either a grantee-name index search against Brevard AcclaimWeb (same unverified-build risk as the Tier 1 owner-name sweep) or GIS legal-description reconciliation for deed-chain purposes (a different problem than `acclaim_case_lookup.py`'s existing parcel-from-legal-description resolver). Neither was built this session. All 3 test cases produced exactly this gap — checked for a deed-type document first (0 found in all 3), not assumed absent.
- **`packages/biddeed-mcp/src/report/title-chain.js`** — new. `buildTitleChain({parcel_id, county}, {get})` reads the pull/owner/gap tables; `parcel_id` is queried case-insensitively on `county` (see bug fix below).
- Wired into `composer.js` as `report.title_chain`.
- **Real bug found and fixed**: `composer.js`'s locatable-path call originally passed `parcel?.parcel_id || auction.parcel_id` (preferring the `matchStateParcel()` result). Live-confirmed for case 05-2024-CA-044972-XXCA-BC that these are two DIFFERENT parcel-ID schemes for the same property — `auction.parcel_id` = `"2703255"` (Brevard's native AcclaimWeb/GIS numeric ID, what the harvest scripts key on) vs `parcel.parcel_id` = `"27 3615-02-*-37"` (fl_parcels' DOR-format ID). Preferring the DOR-format ID silently missed every real `title_chain_pull` row. Fixed to always use `auction.parcel_id` for the chain lookup.

## Report composition — the actual bug vs. the fix that was safe to make

The issue's framing ("composition.lien_search/lien_survival/title_search render Pending for EVERY county, including Brevard where the data exists") is correct as a description of current behavior, but **the root cause is a global, human-controlled `ship_status` legal/accuracy gate on `public.biddeed_report_composition`** (confirmed live: `ship_status='blocked'` for all 6 canonical sections, including `auction_intel`, which the section's own `notes` field already calls launch-ready — this flag tracks a launch checklist, not "does this data exist"), not a bug in the per-case classification logic.

**I initially built `sectionComposition()` to gate `lien_search`/`lien_survival` on real per-case data presence instead of `ship_status`, then reverted that after tracing the actual consumer.** `src/worker.js`'s `renderS5ReportHtml()` — the SAME renderer used for both the internal-preview script and the live customer-facing `/report/json` → PDF path — reads `composition.lien_survival.status === 'delivered'` to decide whether a real, paying customer sees full lien-survival detail (`src/worker.js` lines ~1354-1360; `packages/biddeed-mcp/src/report/pdf.js`'s `judgment_encumbrance` does the identical check for the PDF path). Making `composition.status` flip to `'delivered'` from data presence alone — which is what my first draft did — would have shipped real, accuracy-unproven Brevard lien content to actual paying customers the moment this code merged, bypassing the `ship_status='blocked'` gate that `biddeed_report_composition.notes` explicitly states exists because "Accuracy not yet proven." That is a business/legal decision for Ariel/Steve Spira, not something this dispatch should make unilaterally by changing what "delivered" means.

**What actually shipped instead**: `sectionComposition()`'s ship_status gating is untouched (byte-for-byte identical decision logic to before this session) — `composition.*.status` only says `'delivered'` when a human has already flipped `ship_status='live'`, exactly as before. The real, per-case Tier 1/2/3 content (`report.title_tier1`, `report.lien_survival`, `report.title_chain`) is computed unconditionally (same pattern `lien_survival` already used) and rendered through `src/worker.js`'s pre-existing `internal=true` bypass — the same mechanism `packages/biddeed-mcp/scripts/generate_internal_signal_report.mjs` already used for the Tier 2 "internal preview" reports in the #19728 session. I extended that existing internal/production split to Tier 1 and Tier 3 (new render blocks in `renderS5ReportHtml`'s §16 composition, gated the identical way Tier 2 already was) rather than inventing a new mechanism. Production (`internal=false`) renders byte-identical Pending text to before this session for all 3 tiers, on every county, until a human flips `ship_status`. Verified live (see below) that the customer path shows zero real Brevard content and internal path shows real content with full citations.
