## Scope changes from the issue body (both from Ariel, 2026-09-03, both applied)
1. **AI-only support — no human handoff, ever.** Replaced "Handoff" with "Escalation":
   bot asks for an email, logs a lead via the existing `/chat/lead` upsert
   (`source='support_escalation'`), resolves the conversation. Never opens/assigns
   to an agent, never says "a team member will join."
2. **Deploy end-to-end, widget included** — Chatwoot website widget on both
   biddeed.ai (worker-rendered pages + biddeed-web) and winnerdataai.com,
   env-token-gated so it activates the moment Ariel provisions the tokens with
   no second code change.

    gate; everything else → 200 `{ignored:true}`.

  - `SECURITY_CSP` gained `https://app.chatwoot.com` in `script-src` /

## Chatwoot dashboard setup (for Ariel — do this to go live)
1. **Create the two bot secrets first** (in this repo's Cloudflare Worker,
   `worker-damp-snowflake-cead`): `wrangler secret put CHATWOOT_BOT_TOKEN`,
   `wrangler secret put CHATWOOT_WEBHOOK_SECRET` (any strong random string —
   you choose it, it's just the shared `?k=` value), `wrangler secret put
   CHATWOOT_INBOX_MAP` (value = the JSON map below, filled in with real inbox
   IDs from step 3). `CHATWOOT_BASE_URL` only needs setting if you're not on
   `app.chatwoot.com`.
2. In Chatwoot Cloud: **Settings → Integrations → Agent Bots → Add new bot**.
   Name it (e.g. "BidDeed Support Bot"). Webhook URL:
   `https://biddeed.ai/support/bot?k=<the CHATWOOT_WEBHOOK_SECRET value from step 1>`.
   Copy the bot's **Access Token** shown there — that's `CHATWOOT_BOT_TOKEN`.
3. **Settings → Inboxes → (each website inbox) → Configuration**:
   - Create/open the biddeed.ai website inbox and the winnerdataai.com
     website inbox (2 inboxes for Phase 0 — zonewise.ai deferred).
   - Note each inbox's numeric ID (visible in the inbox settings URL,
     `.../inbox/<id>`), and set `CHATWOOT_INBOX_MAP` to
     `{"<biddeed inbox id>":"biddeed","<winnerdata inbox id>":"winnerdata"}`.
   - Same Configuration tab has the **Website Token** — that's
     `CHATWOOT_WEBSITE_TOKEN_BIDDEED` / `CHATWOOT_WEBSITE_TOKEN_WINNERDATA`.
   - **Settings → Inboxes → (inbox) → Bot Configuration** (or similar, Chatwoot
     Cloud UI) — assign the Agent Bot created in step 2 to both inboxes.
4. **Set the website tokens as env vars** in the two other repos/hosts (NOT
   Cloudflare Worker secrets — these are client-exposed build-time vars):
   - `breverdbidder/biddeed-web` (Vercel project) → Vercel dashboard →
     Settings → Environment Variables → `NEXT_PUBLIC_CHATWOOT_WEBSITE_TOKEN_BIDDEED`.
   - `breverdbidder/winnerdataai-mvp` (Cloudflare Pages project, confirmed
     live host for winnerdataai.com) → Cloudflare Pages dashboard →
     Settings → Environment variables → `VITE_CHATWOOT_WEBSITE_TOKEN_WINNERDATA`.
5. Full secrets list in one block:

| Var | Where | Type | Found in Chatwoot dashboard |
|-----|-------|------|------------------------------|
| `CHATWOOT_BOT_TOKEN` | CF Worker secret (cli-anything-biddeed) | bot | Settings → Integrations → Agent Bots → (bot) → Access Token |
| `CHATWOOT_WEBHOOK_SECRET` | CF Worker secret | bot | you choose it — put the same value in the webhook URL `?k=` |
| `CHATWOOT_INBOX_MAP` | CF Worker secret | bot | Settings → Inboxes → (each inbox) → Configuration → inbox ID in the URL |
| `CHATWOOT_BASE_URL` | CF Worker secret (optional, default `https://app.chatwoot.com`) | bot | only if self-hosted / non-default cloud region |
| `NEXT_PUBLIC_CHATWOOT_WEBSITE_TOKEN_BIDDEED` | Vercel env (biddeed-web) | website widget | Settings → Inboxes → biddeed.ai inbox → Configuration → Website Token |
| `VITE_CHATWOOT_WEBSITE_TOKEN_WINNERDATA` | CF Pages env (winnerdataai-mvp) | website widget | Settings → Inboxes → winnerdataai.com inbox → Configuration → Website Token |

## Deviations from intent
1. **"home" is not worker-rendered.** `handleRequest()` proxies `path === '/'`
   to biddeed-web (`proxyToRadar`) *before* any other route check — the
   worker's own `buildHomepageHtml()` branch near the bottom of the function
   is dead code (unreachable, shadowed). So "inject into every worker.js-
   rendered HTML page (home, ...)" as literally written doesn't apply to
   home — home's widget coverage comes entirely from the biddeed-web
   `app/layout.tsx` change instead. INFERRED, evidence: `handleRequest`
   routing order read directly from `src/worker.js`, confirmed against the
   Worker's own in-file comment about the 2026-08-20 biddeed-web cutover.
2. **503 fires before the `?k=` 401 check when secrets are unset**, so the
   literal post-deploy check in the issue ("POST without `?k=` → 401") reads
   503 right now. This is correct/intended: you can't validate a webhook
   secret that was never provisioned, and the issue explicitly forbids
   inventing one. Once Ariel completes dashboard step 1 above, the same
   request will correctly return 401.
3. **No `notes`/`context`/`transcript` column exists on `lead_profiles`** —
   verified via `GET .../rest/v1/lead_profiles?select=*&limit=1`, full column
   list has no such field. The scope-change comment's claim ("transcript in
   the notes/context field it already has") does not match the live schema.
   Rather than add a column (forbidden by the issue's own "no schema changes"
   guardrail), the escalation transcript excerpt (first 500 chars) goes to
   the existing `log_worker_error` audit log instead, tagged
   `escalation (<trigger reason>)`. INFERRED as the correct call given the
   explicit no-schema-change guardrail; flagging here per Honesty Protocol
   rather than silently dropping the transcript requirement.
4. **Escalation resolve timing when no email is known**: the issue text is
   ambiguous about whether to resolve immediately or wait. Implemented: reply
   asking for an email, do **not** resolve yet (leave conversation open) so a
   follow-up message with the email re-triggers the same escalation path and
   completes the lead-log + resolve. INFERRED — documented here rather than
   guessed silently.
5. Widget scope-add's literal page list included "home" among "worker.js-
   rendered" pages — see deviation 1. All other named pages (`/counties`,
   `/county/:slug`, `/blog`, `/buy-report`, `/subscribe`, legal pages) got the
   widget exactly as scoped; pages *not* named (`/free-report/*`, `/report/:id`,
   `/chat`, `/pioneers`, `/proof/:id`, `/section18-teaser`) deliberately did
   NOT get it, to stay surgical rather than blanket-applying to every
   `withPublicShell()` call site.
