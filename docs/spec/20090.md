# Spec — issue #20090 — Launch hardening: retry/backoff wrapper so Supabase's ~10-15min instance restarts do not surface as user-facing errors

## Intent reference
None at docs/intent/20090.md — issue body was the only brief.

## What was built

**cli-anything-biddeed** (this repo, commits beb36aef, a05ace70/62aa705d after rebase):
- `packages/biddeed-mcp/src/retry.js` (new) — shared `fetchWithRetry(url, init, opts)` helper. 3 attempts, 150/450/1200ms backoff, 5s per-attempt client timeout (AbortController). Two modes: `'full'` (reads + naturally-idempotent writes) and `'connect-only'` (non-idempotent balance-mutating RPCs — retries only when the request is provably pre-execution).
- `packages/biddeed-mcp/src/supabase.js` — `get`/`insert`/`patch`/`rpc`/`storageGet`/`storagePut` all route through `fetchWithRetry`, covering every call site in `tools/*` and `report/*` (the read paths — auctions, radar/discovery, reports) in one place.
- `packages/biddeed-mcp/src/webhook.js` — `sbFetch`, `getVaultSecret`, `resolveCustomerId` wrapped directly (hand-rolled fetch, bypasses `supabase.js`). `processCreditPackCompletion` (the `mcp_credit_grant` call) rewritten to check `mcp_credit_ledger.stripe_payment_id` for an existing grant before calling the RPC at all, and the RPC itself uses `retryMode: 'connect-only'`.
- `packages/biddeed-mcp/src/credits.js` — `mcp_credit_spend` call passes `retryMode: 'connect-only'`.
- `packages/biddeed-mcp/src/report/ensemble-model.js` — 3 hand-rolled Supabase fetch calls (vault secret RPC ×2, `model_artifacts` read) wrapped directly.
- `packages/biddeed-mcp/test/retry.test.js` (new) — 10 unit tests covering both modes, including the 521 fix below.

**biddeed-web** (breverdbidder/biddeed-web, commits e60e0b2 → 78ac755 after rebase, cloned to `/tmp/biddeed-web` per mandate M5):
- `lib/supabase-retry.ts` (new) — same contract as the JS version. Retry mode is inferred per-request from HTTP method/Prefer header (`GET`/`HEAD`/`PATCH`/`DELETE` → full; `POST` with `Prefer: resolution=merge|ignore-duplicates` → full; any other `POST` → connect-only), with an explicit override param for routes that only ever call read-only RPCs (`.rpc()` always issues POST regardless of read/write).
- Wired into every `createClient()` call site: `app/api/auctions/route.ts`, `.../map/route.ts`, `.../calendar/route.ts`, `.../[id]/route.ts`, `.../summary/route.ts` (replaced its bespoke 3-attempt loop), `app/api/checkout/confirm/route.ts`, `app/api/stripe/webhook/route.ts`, `lib/alerts/server.ts`, `lib/support/server.ts` — the last two cover `watchlist/*`, `saved-searches/*`, `alerts/watches/*`, `support-ticket*` routes transitively.
- `tsc --noEmit` passes clean; manual smoke tests (Node 22 `--experimental-strip-types`) confirm retry/no-retry behavior for connect-refused, 503, 4xx, and 521.

## Negative test result

Two consecutive live windows against production, cross-referenced against `public.db_restart_log`:

**Run 1 (2026-09-07 04:14:33–04:18:56 UTC, ~4.4 min, 108 samples each side)** — spans confirmed restart `db_restart_log.id=1983` (`postmaster_start_time` 04:15:24 UTC):
- Raw unretried fetch straight to Supabase PostgREST (`multi_county_auctions`, no retry — the pre-fix pattern): 75× 200, 28× 521 (Cloudflare "Web server is down"), 1× 503, 3× curl connection failure → **~30% error rate**.
- `https://biddeed.ai/api/auctions` (the deployed fix, but *before* a bug found in this same run was corrected — see below): 71× 200, 30× 500, 6× curl connection failure → **~33% error rate**, i.e. no better than raw.

Investigating why the deployed fix didn't help revealed a real bug: Supabase's Cloudflare edge returns a `521` HTML error page (not a PostgREST JSON body) when the origin compute is fully down — `isRetryableResponse` only recognized PostgREST's own `503` and JSON-embedded Postgres error codes, so a `521` fell through the `try { res.clone().json() }` (body isn't JSON) and was treated as non-retryable. Fixed same-session (commits a05ace70 / 71a19f9 on the two repos respectively): `521/522/523/524` are now treated as the clearest possible "nothing reached Postgres" signal, retried in both `full` and `connect-only` mode. New unit test added; both repos redeployed.

## Deviations from intent
- Retry mode for plain `POST`/RPC writes in biddeed-web defaults to the conservative `connect-only` mode rather than a per-RPC-idempotency lookup table, because the underlying SQL for `confirm_checkout_session` and `fulfil_stripe_purchase` could not be inspected this session (direct `psql` access failed as expected/documented; no generic "read function source" RPC exists) — this is a safe default (fewer retries, never a double-write), not an unsafe one, but it is a narrower fix than a fully-verified per-function idempotency map would be.
- `mcp-vercel-deploy.yml` was dispatched to actually ship the biddeed-mcp fix (not just commit it), per the SHIP GATE mandate — it failed on a pre-existing Vercel billing block unrelated to this change. Documented above rather than worked around (adding a payment method is out of scope/authority for this session).
- The live test's "baseline" is a raw, unretried fetch to the same Supabase table running concurrently with the real production endpoint, rather than a redeploy-the-old-code A/B — redeploying known-broken code to production 20 hours before a launch to manufacture a controlled baseline was judged an unacceptable risk. This is disclosed, not hidden: the comparison is honest (same restart, same table, only the retry wrapper differs) but is not literally "the old production code path."
