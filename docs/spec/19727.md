# 19727: Daily Winner FF routing produced 0 routing_decisions (7 consecutive empty days)

## What was actually broken (CONFIRMED, live SQL evidence)

Two independent bugs in `scripts/winnerdata_pipeline.py`'s `main()`, both with the
same symptom (SPRINT3/`quote_drafts` and SPRINT4/`routing_decisions` never run
for that run's leads), plus one unrelated data-quality bug.

**Bug A — sprint2b (Tracerfy skip-trace) starved routing by burning the GHA
timeout.** `main()` ran `sprint2b_tracerfy_skiptrace()` and
`sprint3b_appraiser_verify()` *before* `SPRINT3`/`SPRINT4`, even though neither
enrichment step's output is read by the routing SQL. On 2026-09-02
(`winnerdata-daily.yml` run 33590274879, 04:17 UTC catch-up pass), the
Tracerfy account had 0 real credits — every `trace_lead()` call returned HTTP
402, and the loop retried this for every one of ~46 candidate leads with no
early exit, taking >25 minutes and getting the job killed by
`timeout-minutes: 30` before `SPRINT3`/`SPRINT4` ever executed. Confirmed via
`gh run view 33590274879 --log`: leads created at 04:19:54 UTC, then a wall of
`HTTP 402`/`521`/`503` errors, then `##[error]The operation was canceled.` at
04:48:08 UTC (exactly the 30-min timeout). This is what produced the P0's 0
routing_decisions for 2026-09-01's 16 routable leads.

**Bug B — sprint3b (appraiser cross-verify) crashed the whole script
uncaught.** On the 08-29, 08-30, 08-31 00:2x UTC runs (all `conclusion:
failure` in `gh run list`), `sprint3b_appraiser_verify()` →
`appraiser_dispatch.verify_leads()` hit a transient Cloudflare 521 writing to
`public.parity_audit` via PostgREST, raised an uncaught `RuntimeError`, and
crashed `main()` with exit code 1 — again before `SPRINT3`/`SPRINT4` ran.
Confirmed via `gh run view <id> --log` for all three runs: identical
traceback, `RuntimeError: parity_audit insert failed 521`.

**Why #19680 missed it:** that commit (`0b1e8be5`, 2026-09-01 15:51 UTC) only
changed `PLACEHOLDER_COUNTY_DATES_QUERY`'s `auction_status` filter inside
`sprint1b_brightdata_harvest()` — an earlier stage that resolves "3rd Party
Bidder" placeholder names during winner harvest. It never touched
`sprint2b`/`sprint3b`/the SPRINT3/SPRINT4 ordering, so it could not have fixed
either bug above; it fixed an unrelated stage.

**Bug C (data quality) — bidder ID leaking into `entity_name`.**
`scripts/realauction_winner_harvest.py`'s `get_bid_history()` parses the
winner's name from the RealAuction bid-history modal footer via regex. For
Lee County (confirmed live, cases 2026000036/086/141, auction_date
2026-09-01, `winning_bidder_source = 'realauction_bidhistory_modal:lee:
2026-09-01'`), that footer span contains the raw numeric `bidder_id` instead
of a resolved name, so `winning_bidder` (and downstream `leads.entity_name`)
became `"36660"` / `"56588"` / `"58878"`.

## Live SQL evidence at investigation start (all via Supabase Management API,
IPv4-forced — the sandbox's default route to `api.supabase.com` returns
Cloudflare error 1010; `curl -4` succeeds, matching the documented
psql-password-fails/PostgREST-schema-not-exposed constraint from the brief)

```
-- 2026-09-01 auction leads
select count(*) leads_total, count(*) filter (where is_lender_or_plaintiff=false) routable
from leads l join signal_events se on se.signal_id=l.signal_id
where se.occurred_at::date='2026-09-01';
→ {"leads_total":28,"routable":16}

-- quote_drafts / routing_decisions coverage for those 16, BEFORE fix
→ {"routable_leads":16,"has_quote_draft":0,"has_routing_decision":0}
```

## Fix applied

1. `scripts/winnerdata_pipeline.py` `main()`: reordered so `SPRINT3`
   (quote_drafts) and `SPRINT4` (routing_decisions) run immediately after
   `SPRINT2` (lead creation), *before* `sprint2b_tracerfy_skiptrace()` /
   `sprint3b_appraiser_verify()`. Both enrichment calls are now wrapped in
   `try/except` so a crash or timeout there can never again block routing or
   `sprint5_deliver()`.
2. `scripts/winnerdata_pipeline.py` `sprint2b_tracerfy_skiptrace()`: added an
   early exit — the first `HTTP 402` ("Insufficient credits") from
   `tracerfy_client.trace_lead()` stops the loop for the rest of that run
   instead of retrying it for every remaining candidate (this was the direct
   cause of the 30-minute timeout on 2026-09-02).
3. `scripts/winnerdata_daily_winner_ff_digest.py` `upsert_pending_batch()`:
   `on conflict (batch_date) do nothing` → `do update set lead_count =
   excluded.lead_count where status = 'pending_approval'`. Previously a
   rerun for an existing `pending_approval` batch_date could never refresh
   `lead_count` even after routing was fixed — required for the backfill in
   this same issue, and for any future same-day rebuild. Never touches an
   `approved`/`sent` row (status guard).
4. `scripts/realauction_winner_harvest.py` `get_bid_history()`: a
   purely-numeric `winner_name` (`.isdigit()`) is now treated as unresolved
   (`None`) instead of written as `winning_bidder` — stops a raw bidder_id
   from ever again masquerading as a buyer name.

## Live backfill performed (all via the real, unmodified query paths — SPRINT3/
SPRINT4 SQL executed via Management API; `winnerdata_daily_winner_ff_digest.py
--batch-date <date>` run for real, not dry-run)

- Ran `SPRINT3`+`SPRINT4` live → all 46 previously-undrafted leads (28 for
  2026-08-31's auction, 16 for 2026-09-01's, 2 older) got `quote_drafts` +
  `routing_decisions`.
- `routing_decisions.routed_at` defaults to `now()`, which would have filed
  these under *today's* batch_date instead of the auction day they actually
  belong to (`winnerdata_ff_digest_lib.get_batch_leads()` keys on
  `routed_at::date`) — backdated `routed_at` to noon UTC of the correct
  auction date for exactly these two sets (16 rows → 2026-09-01, 28 rows →
  2026-08-31) before building the digest.
- Ran `python3 scripts/winnerdata_daily_winner_ff_digest.py --batch-date
  2026-08-31` and `--batch-date 2026-09-01` for real (dry-run first, confirmed
  matching counts, then live).
- 2026-08-30 was **not** backfilled — confirmed via
  `public.multi_county_auctions` that zero auctions sold that day
  (`sold_ct=0`), so `lead_count=0` for that batch_date is correct, not a bug.
- Flagged the 3 numeric-`entity_name` leads via `public.lms_flag_lead()` (the
  existing sanctioned Tier-2 write RPC) so Ariel sees "needs manual
  buyer-name resolution" in the LMS before he'd ever approve the 2026-09-01
  batch that contains them.
