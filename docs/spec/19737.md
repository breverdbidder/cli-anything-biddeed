# Spec — issue #19737 — CFO v1 Issue C (CP4): everest-bank-engine Cloudflare Worker

## Intent reference
No `docs/intent/19737.md` exists — issue body was the only brief (per M6, artifact chain fallback).

## What was built
- **`workers/everest-bank-engine/`** — Hono + TypeScript Cloudflare Worker. Routes: `GET /link`,
  `POST /link/token`, `POST /link/exchange`, `POST /sync`, `POST /webhook`, `GET /healthz`.
  Cron trigger every 6h (`wrangler.toml` `[triggers]`) syncs all `status='active'` connections.
- **`supabase/migrations/20260902i_bank_engine_rpc.sql`** — 4 `SECURITY DEFINER` RPCs in
  `public` (`bank_engine_upsert_connection`, `bank_engine_upsert_accounts`,
  `bank_engine_apply_sync`, `bank_engine_list_active_connections`), `EXECUTE` granted to
  `service_role` only. Applied live via Management API (`mgmt_sql.py`) — see Deviations for why
  these exist at all.
- **`.github/workflows/deploy-bank-engine.yml`** — deploys on push to `workers/everest-bank-engine/**`,
  pushes 6 Worker secrets via `wrangler secret put`, verifies `/healthz`, and runs a security
  gate proving `/link/token`/`/sync` reject unauthenticated/wrong-secret requests.
- **`CFO_AGENT_SHARED_SECRET`** repo secret created on `cli-anything-biddeed` (did not exist
  before this issue) — see Deviations for why its value could not be copied from
  `everest-cfo-agent`.
- **`finance.cfo_checkpoints`** CP4 row (`id=c448cda0-1cb7-4a25-ae9e-c17a9fcab45d`,
  "Bank account connection (Plaid or manual statement import)") updated `pending` → `done` with
  evidence.
- **`public.agent_ops_log`** — one row, `dispatch_id='19737'`, `status='VERIFIED'`.
- **`public.finance_ops_log`** — rows written by the Worker itself on every link/exchange and
  sync call (`bank_engine_link_exchange`, `bank_engine_sync` tasks).

## SSOT bindings used
- `finance.bank_connections` / `finance.bank_accounts` / `finance.bank_transactions` (from
  #19716) — written via the new `bank_engine_*` RPCs, never directly.
- `finance.entities` — `entity_code` validated against this table's live rows
  (`biddeed`, `everest_capital`, `protection_partners`, `winnerdata`, `zonewise`).
- `vault.secrets` — read via `public.vault_secret(p_name)`, written via
  `public.ecu_set_vault_secret(p_name, p_value, p_description)` — both pre-existing sanctioned
  RPCs (CLAUDE.md CREDENTIAL HANDLING), not created by this issue.
- `public.agent_ops_log`, `public.finance_ops_log` — direct `service_role` INSERT (both already
  grant `service_role` INSERT natively; no wrapper needed, unlike `finance.*`).

## Deviations from intent
1. **Litigation-gate entity code corrected.** The issue's Inputs section says "Plaid team =
   Everest Capital of Brevard LLC → finance.entities code for that entity gets the litigation
   gate" and its Scope §3 says "Map the sandbox item to entity `everest_capital_brevard`". Live
   `finance.entities` has exactly 5 rows and **no** `everest_capital_brevard` code — the only
   Everest Capital row is `everest_capital` ("Everest Capital USA / Development"), which is also
   the literal code `finance._litigation_gated()` (from #19716's migration, itself written for
   the Abreu v. Everest Capital of Brevard litigation) checks. Used `everest_capital` for the
   sandbox proof instead of inventing a new `finance.entities` row for a code the brief assumed
   existed. Logged per CC_META_PROMPT §2.3 rather than silently creating a mismatched entity or
   blocking.
2. **`plaid` npm SDK dropped, replaced with direct `fetch`.** The SDK's `PlaidApi` (axios-based)
   failed live on the very first deploy: `POST /link/token` → HTTP 502
   `{"error":"Unsupported cache mode: default"}`, even with `compatibility_flags =
   ["nodejs_compat"]` set in `wrangler.toml`. This is axios setting a `cache` fetch option the
   Cloudflare Workers runtime rejects — a known class of Node-HTTP-client-on-Workers
   incompatibility, not a config mistake. `src/plaid.ts` was rewritten as a ~70-line direct-fetch
   client against Plaid's plain JSON REST endpoints, same method names/shapes the SDK exposes, so
   no other file needed to change. Full before/after evidence in the commit history
   (`fix(19737): replace plaid npm SDK with direct fetch`).
3. **Cloudflare secret names corrected.** Issue said "same `CLOUDFLARE_API_TOKEN`/
   `CLOUDFLARE_ACCOUNT_ID` pattern as everest-cfo-agent". Confirmed via `gh secret list` that
   `cli-anything-biddeed` has no secrets by those names — every Workers deploy workflow already
   live in this repo (`deploy-winnerdata-ff.yml`, `deploy-winnerdata-lms.yml`, etc.) uses
   `CF_API_TOKEN`/`CF_ACCOUNT_ID` instead (documented in-repo as a prior naming-mismatch fix).
   `deploy-bank-engine.yml` follows the repo's actual working convention.
4. **`CFO_AGENT_SHARED_SECRET` is a fresh value, not the `everest-cfo-agent` repo's existing
   one.** GitHub Actions secrets are write-only (no API/CLI can read a value back out once set),
   and no sanctioned vault accessor covers a name outside the `cli_anything_*`/`everest_*_pat`
   allow-list (CLAUDE.md CREDENTIAL HANDLING) — `cfo_agent_shared_secret` is not in `vault.secrets`
   at all (confirmed by name-only query). Generated a new 32-byte hex value with `openssl rand`,
   set it as `cli-anything-biddeed`'s `CFO_AGENT_SHARED_SECRET` via `gh secret set` (piped from a
   file, never printed), and used the same value for this session's own live-test curls (via a
   local `chmod 600` file, shredded at session end). The two Workers do not currently share one
   literal key; Ariel would need to manually align them if cross-Worker calls are ever added. This
   does not weaken either Worker's own gate — each independently rejects unauthenticated/wrong-key
   requests (proven in the deploy workflow's security-gate step and this session's live curls).
5. **New `public.bank_engine_*` RPC layer, not a direct-write path.** Confirmed live
   `has_schema_privilege('service_role','finance','USAGE') = false` — only `postgres` and the
   read-only `cfo_agent_ro` role can touch the `finance` schema at all (per #19716's
   `cfo_agent_ro_select`-only policies). Since this Worker authenticates to Supabase as
   `service_role` over PostgREST (`SUPABASE_DB_PASSWORD`/psql confirmed dead again this session,
   matching decision_log 169/205/287 — negative test: same 3 endpoints, same `password
   authentication failed for user "postgres"`), it cannot write `finance.bank_*` directly. Added
   4 `SECURITY DEFINER` functions in `public` (service_role already has `USAGE` there) that write
   into `finance.*` as their owner (`postgres`) — the same pattern already in production use for
   `ecu_set_vault_secret`/`vault_secret`. This is additive (new functions, zero grant changes to
   existing objects) and was applied live via the Management API, the working pattern for DDL
   when direct psql is unavailable.
6. **Webhook route not exercised with a real Plaid-signed delivery.** `POST /webhook` correctly
   rejects a request with no `Plaid-Verification` header (`401`, confirmed live). A full live
   test (Plaid's `/sandbox/item/fire_webhook`) would require pulling the just-stored
   `access_token` back out of vault into this session's shell — deliberately not done, since the
   whole point of storing it in vault is that this session (and everything after it) should never
   need to hold it again. Webhook JWT verification logic (`src/webhookVerify.ts`) is implemented
   per Plaid's documented algorithm (kid → `/webhook_verification_key/get` → ES256 Web Crypto
   verify → `iat` freshness → body-hash match) but its happy path is `UNTESTED`, not `VERIFIED` —
   flagged honestly rather than claimed.
