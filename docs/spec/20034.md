# Spec — #20034 GTM-5 daily-digest consent compliance

Precedence per M6: `docs/intent/20034.md` > this file > issue body > comments.

## What was built

1. **Consent gate** (`scripts/biddeed-daily-digest.cjs`, `getLeads()`):
   recipients = `lead_profiles` WHERE `email IS NOT NULL AND (email_consent =
   true OR marketing_consent = true)`, minus anyone present in the new
   `public.email_opt_outs` or `public.email_suppressions` tables. A second,
   independent count query re-checks the same consent predicate and the
   script throws (refuses to send) if the built recipient list ever exceeds
   that count — a regression guard, not just a filter.
2. **Unsubscribe honoring**: new Supabase Edge Function
   `supabase/functions/email-unsubscribe` (deployed, `--no-verify-jwt` since
   mail clients and browsers call it with no auth header). HMAC-SHA256
   signed (`email` + `sig` query params, keyed on the existing
   `cli_anything_shared_secret` vault secret via the sanctioned
   `cli_anything_get_secret()` accessor — no new secret, no raw secret ever
   held in script memory beyond the HMAC key derivation). Bad/missing
   signature → 403, no write. Valid signature → upserts
   `public.email_opt_outs` and returns a confirmation page (GET) or `200
   text/plain "unsubscribed"` (POST, for RFC 8058 one-click). Wired into
   every send via the footer "Unsubscribe" link and the `List-Unsubscribe` /
   `List-Unsubscribe-Post` headers on the Resend `emails.send()` call.
3. **Suppression**: 21 addresses (15 that received a digest without consent
   Aug 24 – Sep 4, sourced from the Resend `GET /emails` history for this
   sender since `digest@biddeed.ai` exists, deduplicated + the 6 pre-existing
   `lead_profiles` rows with `source='unsubscribe_link'`) written to the new
   `public.email_suppressions` table (`resend_synced=true` for all 21 —
   confirmed via a follow-up read after the sync loop) and pushed to Resend's
   `General` audience as `unsubscribed:true` contacts via the Contacts API.
   No `lead_profiles` row was touched or deleted at any point.
4. **Send audit**: `docs/spec/20034-audit.md` — per-run numbers for every
   `biddeed-daily-digest.yml` run since Aug 24, sourced from `gh run view
   --log` (each run's own `Leads:` / `Sending to N recipients` / `Done: X
   sent, Y failed` lines) cross-checked against the Resend API send history.
   Zero consented recipients across the entire window — confirmed, not
   estimated.
5. **Schedule + bug fix**:
   - Cron: `0 10 * * 1-5` → `0 22 * * *` (22:00 UTC = 18:00 ET daily, per
     `docs/gtm/GTM_SOP_v1.md` §3).
   - `lead is not defined` bug: `featuredCard(auctions, county)` referenced
     `lead.email` from a closure that never had `lead` in scope (the function
     is declared at module scope, `lead` only exists inside `main()`'s loop).
     Fixed by passing `lead` in as a third parameter, threaded through from
     `buildEmail()`.
   - Re-verified with `TEST_EMAIL=everestcapital8@gmail.com` (the internal
     recipient already established for this exact test in
     `docs/spec/20029.md` §7, and the only recipient intent guardrail #1
     permits during this issue) run locally against live Supabase + Resend +
     the deployed edge function: `Sending to 1 recipients across 50
     counties` / `SENT everestcapital8@gmail.com | QUICK_DEMO | <id>` /
     `Done: 1 sent, 0 failed`. Content-format deliverable (yesterday's
     results + top 3 + one reel link) deferred — see audit doc's Residual
     section; the reel-link input doesn't exist yet (0 published reels
     system-wide per the GTM SOP baseline).
   - Content-format deliverable (yesterday's results + tomorrow's top 3 + one
     reel link) is **deferred**, not shipped — see Residual section below.
6. **Re-enable**: workflow 321410535 re-enabled after 1–5 verified above.
   Verified recipient count the next real (non-test) run will target: **2**
   `lead_profiles` rows currently satisfy the consent predicate and are not
   opted out/suppressed (queried live immediately before re-enabling — see
   `docs/spec/20034-audit.md` for the exact query and caveat about a third
   row that existed at issue-open time and was independently deleted from
   `lead_profiles` by some other process before this fix landed).
