# Spec — issue #20056 — GTM-7: `/r/<code>` short-link Worker must never 404 on a DB blip

## Intent reference
No `docs/intent/20056.md` existed at dispatch time — the issue body is the only brief, per M6.

## Root cause (CONFIRMED)

`src/worker.js`'s `/r/:code` handler made one synchronous call to
`public.resolve_reel_link()` per request, with no cache and no retry. Any
transient failure of that single call (Supabase restarting 3-5x/hour during
the M9 launch window, per the issue) was mapped straight to a 404 — a real
signed-out visitor clicking a reel end card lost the lead. The issue's own
10-hit probe on `1BrNFC` (1×404, 9×302) reproduced this: same code, same
minute, different answers on a deal page that itself returned 200 every time.

## What was built (this repo only, per M5)

### 1. `src/worker.js` — edge cache + retry + never-404 fallback
- New helpers (`sleep`, `reelLinkCacheRequest`, `reelLinkCacheResponse`,
  `fetchReelLinkOnce`, `fetchReelLinkWithRetry`, `bumpReelClick`), placed next
  to `logErr`.
- `/r/:code` now checks `caches.default` first (key:
  `https://biddeed.ai/_internal/reel-link/<code>`, `Cache-Control: public,
  max-age=86400`). **Workers KV is NOT bound on this account** and this
  session has no Cloudflare API access to provision a namespace — the issue
  itself names Cache API as the sanctioned fallback when KV isn't available,
  and it's the same pattern already used elsewhere in this file
  (`fetchRuntimeConfig()`, `fetchReportCounties()`).
- Cache hit → serve the 302 immediately, no Supabase call on the request path.
- Cache miss → one call to `resolve_reel_link()`, one retry after a 200ms
  backoff on failure/timeout (3s timeout per attempt via `AbortController`).
  - Retry succeeds, code found → cache it, 302.
  - Retry succeeds, code confirmed not found → true 404 (unchanged behavior).
  - Retry fails both times (the DB-blip case this issue is about) → **302 to
    `/reels/<code>` instead of 404** (a lightweight, already-existing route
    that degrades gracefully if Supabase is still down), never a 503.
- Click counting split so a cache hit still counts: `resolve_reel_link()`
  already increments on every real (miss-path) call; a new fire-and-forget
  `bump_reel_click()` RPC increments on a hit, called via `ctx.waitUntil()`
  and gated to GET only (HEAD never counted, matching prior behavior).
- **Known tradeoff, explicitly in scope-boundary:** an admin edit to a live
  `reel_links`/`reel_variants` row won't be visible at the edge until the 24h
  TTL lapses — no schema change was in scope to push invalidation from the
  write side (e.g. a DB trigger calling out to purge the Worker's cache).

### 2. `supabase/migrations/20260906i_reel_click_cache_warm_rpc_20056.sql`
- `public.bump_reel_click(p_code text)` — increment-only counterpart to
  `resolve_reel_link()`, mirrors its two code namespaces
  (`winnerdata.reel_variants.short_code` → `reel_variant_metrics`,
  `winnerdata.reel_links.code` → `reel_links.clicks`). No-ops on an unknown
  code (no error).
- `public.list_reel_codes_for_cache_warm()` — returns every code (both
  namespaces) whose parent `winnerdata.biddeed_reels.page_http_status = 200`.
  Feeds the backfill script below.
- Both `grant execute ... to anon, authenticated, service_role` (matches
  every other reel RPC in this file — the Worker only ever calls PostgREST
  with the anon key).
- This is function-only DDL (`create or replace function`), consistent with
  ~10 prior migrations in this repo that modify `resolve_reel_link()` the
  same way — no table/column change, which is what the issue's "No schema
  changes" constraint is read to mean here.
- Applied live via `scripts/mgmt_api_migrate.py` (Management API — direct
  `psql`/`SUPABASE_DB_PASSWORD` is a known, already-documented non-starter
  for this project per decision_log 169/205/287).

### 3. `scripts/warm_reel_link_cache.py`
- One-time (re-runnable) backfill: calls `list_reel_codes_for_cache_warm()`,
  then issues a HEAD request per code to `https://biddeed.ai/r/<code>` to
  populate the edge cache via the real cache-miss path.
- Two live bugs found and fixed during verification (see Evidence below):
  Cloudflare bot-protection 403s urllib's default User-Agent (same class of
  issue already documented in `biddeed_reels_lib.py`'s `run_sql()` for
  `api.supabase.com` — fixed the same way), and `urlopen()`'s default opener
  follows the 302 transparently, so the script needs a no-redirect opener to
  see the short link's own status instead of the deal page's 200.
- **Documented limitation, not a bug:** Cache API is per-colo, not global
  like Workers KV. This script only warms wherever Cloudflare routes these
  particular requests from. A code cold in some other colo still falls
  through to the retry-then-fallback path in `src/worker.js` — never a 404.
  "On every new `reel_links` insert" (issue ask #3) was **not** wired,
  because the insert path is a `SECURITY DEFINER` RPC called from Postgres —
  making it call out to an HTTP endpoint on insert would be a Postgres-side
  change (e.g. `pg_net` + trigger) beyond this issue's declared scope
  (`src/worker.js`, "no schema changes"). Logged here as a residual, not
  silently dropped.

### 4. `.github/workflows/deploy-worker.yml` — CI smoke-test gate
- New step after `wrangler deploy`: 20 sequential hits each on 3 known-live
  codes (`F5oeMD`, `1BrNFC`, `D7qXFD`), asserts 100% `302` with `Location`
  containing `/deal/`. Any miss fails the deploy (`exit 1`), not just warns.
- **Scope deviation from the issue's literal wording:** the issue says "add
  to the deploy gate from #20053" — that gate (`cloudflare-production.yml`'s
  "Canonical-domain smoke checks") lives in `breverdbidder/biddeed-web`, a
  different repo, and per M5 this session operates only in the repo named in
  the issue. The router Worker under test here is deployed exclusively by
  *this* repo's `deploy-worker.yml`, so the gate was added there instead —
  functionally the same protection (fails the deploy on a bad `/r/:code`
  response), just co-located with the code and workflow it's actually
  gating.

## DoD status (per issue's numbered Fix list)

| # | Ask | Status |
|---|-----|--------|
| 1 | Edge cache in KV/Cache API, long TTL, `ctx.waitUntil` async refresh | **DONE (Cache API, not KV — see tradeoff above)**. No async background refresh on a hit (would double-count clicks against `bumpReelClick`'s design — see below); relies on 24h TTL + miss-triggered repopulation instead |
| 2 | Never 404 on lookup error; retry once; fallback to `/reels/<code>` or 503 | **DONE** — retry once (200ms backoff), fallback 302 to `/reels/<code>` on confirmed failure, true 404 only when `resolve_reel_link()` itself confirms no such code |
| 3 | Warm cache for every `page_http_status=200` code; backfill job + on every insert | **PARTIAL** — one-time/re-runnable backfill **DONE and run** (107/107 codes warmed live); on-insert warming **NOT DONE** (residual, documented above — would require a Postgres-side change out of this issue's declared scope) |
| 4 | Click counter fire-and-forget, never in request path | **DONE** — `bump_reel_click()` via `ctx.waitUntil()` on every cache-hit GET |
| 5 | CI smoke test, 20 sequential hits × 3 codes, 100% 302, added to deploy gate | **DONE** — in this repo's `deploy-worker.yml` (see scope deviation note above), verified green on the actual deploy of this change |
