## What was built

**cli-anything-biddeed (this repo):**
- `cloudflare/mcp-worker.mjs` — wraps `biddeed-mcp-production`'s existing
  `httpServerHandler` fetch: per-IP unauth rate limit (20/60s), per-API-key
  rate limit (120/60s, keyed on sha256 of the bearer token), 429 JSON-RPC
  error + `Retry-After: 60` on limit, and `Strict-Transport-Security` /
  `X-Content-Type-Options` / `Referrer-Policy` on every response.
- `cloudflare/wrangler.mcp.jsonc` — removed the (non-functional, see below)
  `ratelimits` binding config; comment explains the counter now lives in
  `mcp-worker.mjs` via `caches.default`.
- `src/worker.js` (`worker-damp-snowflake-cead`) — per-IP rate limits on
  `/chat/api` (30/60s), `/chat/lead` (5/60s), `/auctions` (60/60s),
  `/subscribe*`+`/buy-report*` (20/60s); edge-caches `GET /auctions` JSON and
  `GET /county/:slug` HTML for 60s via `caches.default`, bypassed when
  `Authorization`/`Cookie` is present. Existing CSP/security headers
  (already complete — HSTS, nosniff, X-Frame-Options, Referrer-Policy,
  Permissions-Policy, CSP) untouched.
- `wrangler.toml` — removed the (non-functional) `ratelimits` binding config
  for the same reason as above.
- `.github/workflows/cloudflare-mcp-production.yml` — the `ratelimit` unsafe
  binding drops the `workers.dev` preview URL Cloudflare normally prints on
  deploy (zone/custom-domain-only binding type); the workflow's `grep | tail`
  for that URL then failed under `bash -e -o pipefail`, killing an otherwise-
  successful deploy step. Made that non-fatal and the workers.dev-only gate
  table conditional on the URL existing. (Config was later removed again in
  the ratelimit-binding rollback, but the workflow fix is still correct/
  needed for any future `ratelimits`/`unsafe.bindings` use.)

**breverdbidder/biddeed-web** (cloned to `/tmp`, committed, pushed directly —
main has no PR requirement, confirmed via `gh api .../branches/main/protection`):
- `lib/rate-limit.ts` — `checkRateLimit()` rewritten from an in-memory `Map`
  (SEC-009, written for Vercel's long-lived process) to `caches.default`
  (Workers Cache API), now async. Preserves the existing progressive-backoff
  behavior (3 hits in 5min halves the limit).
- `middleware.ts` — all 4 call sites (`auth`, `checkout`, `csp-report`,

**breverdbidder/zonewise-web** (cloned, PR opened, **not merged** — intent
says main is protected, PR only):
- `wrangler.production.jsonc` — `assets.run_worker_first: ["/"]`. Root cause

  from the assets binding, which never invokes the Worker (and therefore
  never runs `middleware.ts`/`next.config.mjs`'s already-correct
  `headers()`). Scoping to `["/"]` (not blanket `true`) keeps every other
  static asset on the zero-Worker-invocation cost path.
- PR: https://github.com/breverdbidder/zonewise-web/pull/114 (branch
  `launch-a-20035-security-headers` → base `cf-exit`, the branch that's
  actually live — `cf-exit` and `main` have diverged by ~15k lines, so a
  PR against `main` would show an unrelated diff).

## Negative test result
Per-key rate limit (120/60s) on `mcp.biddeed.ai` does **not** trip under
normal agent-like use: 100 authenticated `tools/list` calls at ~5 req/s
(28s wall clock) all returned 200. Confirms the fix doesn't collaterally
throttle legitimate MCP clients.

## Deviations from intent

1. **Cloudflare's `ratelimits`/`unsafe.bindings type="ratelimit"` binding
   does not work on this account.** Both the legacy `unsafe.bindings` syntax
   and the current GA `ratelimits` top-level config (per
   developers.cloudflare.com, wrangler ≥4.36.0 — we run 4.86.0) deployed
   cleanly and `env.RATE_LIMITER.limit()` executed without error, but
   **always returned `success:true`** — verified with a temporary debug
   response header across 85+ live requests (up to 50 concurrent, both
   syntaxes). This matches an open, unresolved Cloudflare Community report
   of the identical symptom
   (community.cloudflare.com/t/workers-rate-limiting-binding-always-returns-success-true-for-the-same-key-and-colo/953250).
   A per-isolate in-memory `Map` was tried next and also failed live (25
   sequential requests, zero throttling — Cloudflare gives no single client
   session affinity to one isolate). **Landed on `caches.default`** (the
   Workers Cache API) as a best-effort, colo-shared counter store — this is
   the mechanism actually deployed in all three repos, not a Rate Limiting
   binding. It is documented inline everywhere it's used. A Workers Paid
   plan change (which would unlock Durable Objects, a more correct fix) is
   explicitly Ariel's call per the intent's non-goals — not attempted.
2. **zonewise-web fix does not use a custom Worker wrapper.** First attempt
   wrapped the OpenNext-generated Worker to inject a hardcoded fallback
   header list (mirroring the mcp-worker.mjs pattern) — this worked, but
   duplicated a header list already correctly maintained in
   `middleware.ts`/`next.config.mjs`. Root-caused instead to Cloudflare's
   static-assets-bypass-the-Worker default behavior and fixed with
   `assets.run_worker_first: ["/"]`, which routes just the homepage through
   the existing, already-correct header pipeline — zero duplicated logic.
3. **zonewise X-Frame-Options is `DENY`, not `SAMEORIGIN`.** The issue body
   says `X-Frame-Options SAMEORIGIN` for this deliverable, but that phrase
   is reused generically across all 4 workers in the issue's scope section.
   This site's `middleware.ts`/`next.config.mjs` already set `DENY`
   sitewide (nothing on zonewise.ai is iframe-embedded); matching the
   existing, deliberate, sitewide convention for this one route is more
   correct than introducing a one-off `SAMEORIGIN` value. Flagged here for
   Ariel to override if `SAMEORIGIN` was actually intentional.
4. **biddeed-web-production's `checkRateLimit()` was fixed for all 4
   callers** (auth, checkout, csp-report, generic `/api/*`), not just the
   `/api/*` line named in scope item 3 — the underlying in-memory-Map bug
   was identical and shared across all of them, so it was already silently
   non-functional for auth/checkout rate limiting too. No checkout/Stripe
   *logic* was touched, only the shared counter mechanism.
