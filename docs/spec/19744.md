## What was built

Files touched:
- `scripts/identity_cascade.py` — two fixes to the Exa leg of the Sunbiz cascade:
  1. `resolve_via_exa()`: the primary query (`"{entity} Sunbiz Florida Division
     of Corporations"`) pollutes Exa's neural ranking with wrong-company
     candidates, so the old `if not candidates:` guard almost never fell
     through to the far more accurate domain-restricted bare-name query. Now
     runs both queries unconditionally and merges/dedupes candidates by URL.
  2. `parse_sunbiz_text()`: bisprofiles.com has moved from the markdown-list
     page format the parser expected to a prose/header format. Added regex
     support for the current `Principal Address <addr>`, `#### <Name>\n\n
     Position <Position> Active From <City, ST>`, and `Registered Agent is
     <Name>\n\nFrom <City, ZIP>` patterns, confirmed against a live fetch of
     `https://bisprofiles.com/fl/jaykailash-l24000466406`.
- `scripts/seller_digest_enrichment.py` — `resolve_row()` now short-circuits
  a bare-digit `entity_name` (a Lee County RealAuction bidder-registration ID
  that leaked into `multi_county_auctions.winning_bidder` before #19727's
  `isdigit()` guard landed on the harvest side) straight to
  `identity_type=unresolved_bidder_id`, `NOT AVAILABLE`, zero vendor spend —
  instead of falling through `classify()` to `identity_type=person` and
  spending a real Tracerfy lookup on a registration number.
- `scripts/seller_digest_pdf_render.py` — the HTML/PDF filename slug (entity
  name + case number) had no length cap and blew past the 255-byte filesystem
  limit for long land-trust legal descriptions (`OSError: File name too
  long`), aborting the whole render job after 1 of N leads on both
  2026-08-31 and 2026-09-01 runs. Entity portion capped to 80 chars;
  case_number/lead_id suffix (the uniqueness key) stays intact.
- `docs/spec/19744.md` — this file.

No migrations, no RPCs/views created. No `.github/workflows/*` files were
committed — see **Deviations** below, this is the load-bearing finding of the
session.

## Root cause chain (in order of how deep the diagnosis went)

1. **Surface symptom**: `stage2_sunbiz_chain` outcome=`miss` for 18/18
   business LLCs, evidenced by `winnerdata.ff_enrichment_attempts.output_json`
   showing `"sources_tried": ["exa","mirror_direct","brightdata_browser",
   "playwright_direct"]` — all 4 cascade legs ran to exhaustion.
2. **Ground truth check** (ruled out "these aren't real Sunbiz entities"):
   independently verified via web search (not this pipeline's own code) that
   JAYKAILASH LLC (Doc# L24000466406), COY PROPERTIES LLC (Doc# L05000068516),
   and QUEEN EQUITIES LLC's near-namesakes are all real, Active Sunbiz
   entities with public officer/registered-agent data. The issue's own
   "18/18 miss against Florida's own public registry is not plausible" was
   correct.
3. **Two real code bugs found and fixed** in `identity_cascade.py` (see
   "What was built" above) — verified live, with `EXA_API_KEY` present
   locally, that these fixes let `resolve_via_exa('JAYKAILASH LLC')` return a
   populated hit (doc number, principal address, 1 officer) where it
   previously returned `None`.
4. **The actual, dispositive, production root cause**: re-running the real
   GHA workflow after landing those two fixes produced **zero change** —
   stage2 still missed on every business lead. Reading
   `.github/workflows/winnerdata-seller-digest-enrichment.yml`'s `enrich` job
   env block shows it **never passes `EXA_API_KEY` or
   `BRIGHTDATA_BROWSER_WSS`** to `scripts/seller_digest_enrichment.py`.
   `identity_cascade.py`'s `exa_search()` does `if not EXA_API_KEY: return []`
   — a **silent no-op, no exception, no log line** — so the only cascade leg
   with a working parser is dead on arrival in every real run of this
   workflow. The sibling workflow `winnerdata-nine-ff-enrichment.yml`, which
   uses the *same* `identity_cascade.py` module and is almost certainly the
   pipeline behind the 2026-08-27/28 successes the issue cites (SWP
   Investments LLC → Stanley Pszczolkowski, etc.), **does** wire both
   secrets. This maps most closely to the issue's own hypothesis (c)
   ("a credential/proxy failure being swallowed as miss") — refined to: the
   credential was never provided to this specific workflow in the first
   place, not swallowed after a request.
