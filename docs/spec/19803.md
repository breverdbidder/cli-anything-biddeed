## Root cause — CONFIRMED, and different from the issue's own hypothesis

The issue's CONTEXT block states: *"property.condition is null for these
rows (verified: most FL parcels lack a condition rating)."* This premise was
**INFERRED and wrong**. Live query confirmed:

```sql
select br.id, br.condition_json->>'general_condition_tier' as tier
from winnerdata.biddeed_reels br join winnerdata.reel_variants rv on rv.reel_id = br.id
group by br.id, br.condition_json;
-- 0/5 reels had null/empty condition_json. All 5 had a real tier: good (3) / fair (2).
```

The real root cause was **two independent bugs**, both introduced across
#19782/#19802:

1. **`agents/reel_studio/director_qa.py::fetch_reel_facts()`'s SELECT
   omitted `condition_json`.** This function builds the `reel_facts` dict
   that `_cp3c_regen_19802.py` fed into `hook_writer.build_bespoke_script()`.
   Because the column was never selected, every `reel_facts` dict had
   `condition_json=None` regardless of the parent row's real data —
   `hook_writer._condition_tier()` then always fell back to its internal
   `"unknown"` sentinel, for every single row, independent of what that
   row's own vision-scored condition actually was.
2. **`hook_writer.py`'s spoken-text templates had no graceful fallback for
   that sentinel.** `_tension_phrase()` and `build_bespoke_script()`'s setup
   line both did `f"{condition}-condition ..."` / `f"...condición
   {condition}..."`, so the internal token `"unknown"` was spoken verbatim
   as an adjective — exactly the defect quoted in the issue ("This
   unknown-condition Lee County home...").

Bug 1 explains why it was 20+/21 (nearly every row, not a data-dependent
subset) — it wasn't that most parcels lack a condition rating, it's that the
rating never reached the generator. Bug 2 is the actual instruction target
("fix the fallback so a missing condition value never reaches spoken
output") and is fixed defensively so it also protects any future row whose
`condition_json` genuinely has no tier.

## What was built

- `agents/reel_studio/director_qa.py`:
  - `fetch_reel_facts()` — added `condition_json` to the SELECT (root cause
    fix #1), with the same str→dict jsonb parsing every other reader in this
    codebase already uses.
  - `check_no_placeholder_tokens(variant)` — **new permanent QA check**
    (item 4 of the issue). Regex `\b(unknown|n/a|null|undefined)\b`
    (case-insensitive, word-boundary so it also catches hyphenated/
    punctuated forms like `"unknown-condition"` or `"(null)"` without
    false-positiving on unrelated words) over `title` and every
    `script.beats[].line`. Wired into `review_variant()`'s `qa_scores` —
    any hit now fails `qa_pass`, permanently, regardless of which generator
    produced the text.
- `agents/reel_studio/hook_writer.py`:
  - `_has_condition_data(reel_facts)` — new helper; `True` only when
    `general_condition_tier` is one of `excellent/good/fair/poor` (i.e. real
    data), `False` for the `"unknown"` sentinel.
  - `_tension_phrase()` and `build_bespoke_script()`'s setup-line
    construction (EN + ES) — every template that previously interpolated
    `{condition}-condition` / `condición {condition}` now branches: real
    tier → same phrasing as before; no tier → **the condition clause is
    dropped entirely and the sentence is rephrased to not need it** (the
    issue's own preferred option 1), never a substituted placeholder token.
- `agents/reel_studio/_cp3c_regen_19803.py` — new one-shot regeneration
  script. Re-derives `script` + `caption_groups` (title/archetype/loop-line
  logic untouched per the issue's non-goals) for every live variant via the
  now-fixed `fetch_reel_facts()` + `build_bespoke_script()`, validating
  payoff-confinement / loop-line-match / placeholder-token-absence before
  each write, and only issuing an `UPDATE` when the text actually changed.
- `agents/reel_studio/_fix_19803_translated_rows.py` — new one-shot repair
  script, see **Deviation / self-caught mistake** below.
- `agents/reel_studio/eval_hook_writer.py` — unchanged (all 42 existing
  assertions re-verified passing; no new assertions needed here, the
  behavior change is covered by `eval_director_qa.py`'s new fixtures).
- `agents/reel_studio/eval_director_qa.py` — 4 new assertions (47-50), and
  `.claude/skills/reel-director-qa/eval.json` updated to match
  (`check_no_placeholder_tokens` fail/pass fixtures built from the real
  shipped defect, plus an end-to-end `build_bespoke_script()` fixture
  proving the generator itself never emits `"unknown"` when
  `condition_json={}`).

## Deviation / self-caught mistake — MUST READ before trusting the `es`/`pt-BR` rows

`_cp3c_regen_19803.py`'s first pass called
`hook_writer.build_bespoke_script(archetype, reel_facts, title_stem,
lang=<row's own lang>)` for **every** variant, including the 3 `es`/`pt-BR`
rows. Those 3 rows are not native `hook_writer` output — they are
LLM-translated siblings of an English source row, produced by
`translator.py` (issue #19793 PART 3). `hook_writer.py` has **no `pt-BR`
branch at all** (falls through to the English branch) and its `es` branch
interpolates the raw English tier word untranslated (`"condición good"`).
The first pass silently overwrote those 3 rows with wrong-language /
mixed-language script text — a real regression, caught by manually
re-reading the regen output before considering the task done (not caught by
any automated check, since `check_no_placeholder_tokens` only checks for
placeholder tokens, not language correctness).

**Fix applied:** `_fix_19803_translated_rows.py` restores each row's
original professionally-translated wording (recovered from this session's
own before/after log captured immediately before the bad `UPDATE` ran) and
applies only the minimal fix the issue actually asked for — the condition
clause (`"de condição desconhecida"` / `"en condición desconocida"` —
Portuguese/Spanish for "unknown-condition") is dropped from the setup beat,
the same drop-the-clause treatment as the English fix. No new LLM call was
made; this was a targeted, verified text edit, checked against
`check_no_placeholder_tokens` before writing.

**Live-verified after the repair:** `select check_no_placeholder_tokens for
all 25 rows` → 0 hits, including the 3 corrected-twice rows. Their
`lang`/wording is back to native Portuguese/Spanish.

**Not fixed (root cause of the mistake, flagged for a future issue):**
`hook_writer.build_bespoke_script()` and `_cp3c_regen_19803.py` have no
guard against being pointed at a translated row. A future regen of this
class should either (a) skip any row with `lang not in (None, "en")` and
instead re-run `translator.py` against the fixed English source, or (b) add
an explicit `assert lang in (None, "en")` to `build_bespoke_script()` so
this mistake fails loudly instead of silently producing wrong-language text.
Not fixed here — would be scope creep on a P0 placeholder-token bug — but
is the single most important thing for whoever touches this pipeline next
to know.
