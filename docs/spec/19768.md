## Pre-flight findings (re-derived live, not trusted from the brief)

### 1. `finance.simplefin_backfill()` reintroduced the exact bug #19765 fixed — CRITICAL, fixed
The issue's text treats `simplefin_backfill(from,to)` as proven ("chat added it; pulled 347
rows"). Live inspection showed it never received the fixes #19765 applied to `simplefin_sync`:
no `simplefin:` id prefix, un-negated amount sign, stub raw payload, no credential/HTTP error
handling. Confirmed live before touching anything: **347 unprefixed duplicate rows**, every one
with a matching prefixed row of the exact opposite sign, **zero** with a `journal_entry` yet.
Not yet posted, but the next `process_bank_transactions()`/`daily_close()` tick would have
posted all 347 as duplicate, wrong-signed, miscategorized entries — a negative "expense"
duplicate lands as fake income. This would have directly corrupted the P&L and 1099 views this
issue asks for, including double-counting the SHAPIRA MARIAM Zelle payments named in scope item
6 (confirmed: those 5 real payments each had an unprefixed duplicate pending). Fixed the function
to match `simplefin_sync`'s convention and deleted the 347 rows (guarded on: unprefixed id +
simplefin connection + zero journal_entries + matching prefixed opposite-sign row exists).
Verified before/after: `unprefixed` count went 347 → 0; real per-account txn counts correctly
dropped (e.g. brevard 3519: 102 → 66, 9264: 208 → 129) once the duplicates were gone.

### 2. `finance.bank_accounts.mask` regression — root cause found, not assumed
`workers/everest-bank-engine/src/simplefin.ts::syncSimplefin()` hardcoded `mask: null` on every
account upsert (SimpleFIN's protocol carries no top-level mask field — it's embedded in the
account name, e.g. `"BUSINESS CHECKING ...3519 (3519)"`). `public.bank_engine_upsert_accounts`'s
`ON CONFLICT DO UPDATE SET mask = excluded.mask` then blanked whatever mask had been populated
on **every single 6h cron tick**. Two-part fix: (1) the SQL upsert now coalesces against the
existing value so an incoming null can never clobber a good mask, (2) the Worker now extracts
the real mask from the account name via `/\((\d{4})\)\s*$/` instead of hardcoding null.

### 3. Jan 1 – Mar 5 gap is real — probed live, not assumed
Wrote `finance.simplefin_probe_range(start_epoch, end_epoch)` (read-only, no inserts) and queried
the live SimpleFIN Bridge directly in ≤45-day windows for 2026-01-01→2026-02-15 and
2026-02-15→2026-03-06: **0 transactions, all 4 real WF accounts, both windows.** Sanity-checked
the same probe against 2026-03-01→2026-03-15 (a range known to have data) and got real
transactions back (2–14 per account), proving the probe itself works and the Jan–Mar zero is a
genuine Bridge-side gap, not a bug in the check. Confirmed via `finance.v_bank_coverage`: all 4
real accounts' earliest transaction is 2026-03-06 or 2026-03-09.
