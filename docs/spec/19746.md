# Spec — issue #19746 — Tracerfy 0/7 on resolved LLC principals: pipeline never runs fl_parcels self-match on the PERSON after Sunbiz

## Intent reference
None at docs/intent/19746.md — issue body was the only brief (per M6).

## Root cause (confirmed live, evidence_ledger before this session)
`scripts/seller_digest_enrichment.py::resolve_row()` already had a stage2->stage1
"try the principal too" hop (from #19729 T2), but it was gated on
`if stage1_addr is None` — i.e. it only ran when the LLC-level fl_parcels
self-match had already MISSED. When the LLC-level match HIT (its own
registered/mailing address), the person-level self-match never ran at all, so
Tracerfy got the LLC's own address paired with a human principal name
(Gayatri Parivar LLC -> Shilpa Shah: LLC hit "505 TOMAHAWK CT, PALM BEACH
GARDENS" — not Shilpa Shah's home). Three compounding, previously-unhandled
failure modes on top of that: (1) a PO Box LLC-level address (Florida
Investors Capital LLC -> "PO BOX 2086, LUTZ") is not a traceable anchor but
was still passed through; (2) a resolved "principal" can itself be another
LLC (Casscap, LLC / Tokinvest LLC) with no further hop attempted; (3) Sunbiz
officer names can come back "Last, First" (Panah, David) with a literal comma
that breaks the fl_parcels LIKE-substring self-match.

A 4th, deeper root cause found during implementation (not named in the issue
body, discovered live): `public.fl_parcels.own_name` is SURNAME-FIRST
("PATEL RAJENDRAKUMAR", "STERN BEN"), but a Sunbiz-resolved principal name
comes back in natural First-Last order ("Rajendrakumar Patel", "Ben Stern").
A single-order LIKE query never lines up even when a real match exists —
confirmed live: "Ben Stern" -> 0 rows, but "Stern Ben" -> real hit
(STERN BENJAMIN E &, 3700 S OCEAN BLVD APT 1405, HIGHLAND BEACH FL).

## What was built
- `scripts/identity_cascade.py`: `normalize_person_name()` (parser boundary,
  item 3) — reverses only an unambiguous two-part "Last, First" comma shape to
  "First Last"; guards on a legal-entity-suffix regex so `"Casscap, LLC"` is
  never mangled. Applied where `resolve_identity()` derives `principal_name`
  from parsed Sunbiz officers.
- `scripts/seller_digest_enrichment.py`:
  - `is_po_box()` — PO Box regex guard (item 4); applied at both the
    entity-level and principal-level `stage1_identity` hits.
  - `stage1_self_match_both_orders()` — tries the name as given, then (for a
    2-token name) the swapped order, against `fl_parcels` (free internal
    query, no vendor spend either way).
  - `resolve_row()` stage2 block rewritten: chains up to 2 `stage2_sunbiz_chain`
    calls when the resolved principal is itself a business (item 2, evidence
    key `stage2_sunbiz_chain_hop1`); once the chain lands on a PERSON, **always**
    runs the person-level self-match via `stage1_self_match_both_orders()` —
    no longer gated on the LLC-level match having missed (item 1, the P0 fix).
  - `resolve_row()` stage1_identity block extended: direct `person`/
    `person_joint` buyers (not just Sunbiz-derived principals) now also get
    the dual-order self-match — trivial reuse of the same helper, applied
    after the mandated "Also report" spot-check surfaced the identical
    word-order bug there too (see DoD "Also report" row).
- `scripts/winnerdata_ff_digest_lib.py`: `dedupe_leads_by_entity_name()`
  (item 5) — collapses `get_batch_leads()`'s result to one row per buyer NAME
  (case-insensitive), keeping the highest-`sold_amount` property, tie-broken
  by earliest `routed_at`. Applied inside `get_batch_leads()` itself so build,
  backfill, AND send paths all see the same deduped set going forward.

## Also report (diagnosis, per issue's own "unless trivial" carve-out)
- The 5 (actually 8, both batches combined) direct `person`/`person_joint`
  buyers that missed `stage1_identity` were spot-checked by hand:
  - **STEVE A MARSH**: a plausible real match exists in `fl_parcels`
    (`MARSH STEVEN A`, 24916 JOINER CT, LUTZ) but is missed by BOTH the
    original and swapped-order query — 3-token name, and "STEVE" vs
    "STEVEN" is a nickname variant, not a pure order problem. Out of scope
    for this issue's 2-token swap (determining which of 3 tokens is the
    surname is genuinely ambiguous); flagged as a candidate for a future,
    separate fuzzy-matching issue.
  - **John and Jacqueline Passeggiata**: confirmed via direct query — zero
    `fl_parcels` rows for "PASSEGGIATA" + "JOHN" in either order. Genuinely
    owns nothing else in FL under this name (or the joint "and" format never
    matches county-roll convention); not a matching-strictness bug.
  - **Jean rosalva** and **Dorin Birta**: real matches DO exist, found only
    via the swapped order (`ROSALVA JEAN YVELT`/`ROSALVA JEAN JONAS`;
    `BIRTA DORIN`, 11412 JOHNSTONE DR, PENSACOLA) — same word-order bug as
    the principal-name case. This was trivial to fix (same helper, already
    built) and IS applied in this session's code (see "What was built").
  - Net: of 8 direct-person misses, 2 were a genuine pipeline bug (now
    fixed), 1 (Passeggiata) is a genuine no-record case, and 1 (Marsh) is a
    known, separate, out-of-scope limitation (3-token/nickname matching).

## Deviations from the issue body
- Item 5's fix (dedupe) was implemented as a single change inside
  `get_batch_leads()` in `winnerdata_ff_digest_lib.py`, not as a change to
  `winnerdata_daily_winner_ff_digest.py` directly — `get_batch_leads()` is
  shared by the build, backfill, AND send scripts, so fixing it at the
  source guarantees the send path can never fire two FFs for one name
  either, not just the build/persist path the issue's own wording focused on.
- Extended the dual-order self-match (items 1/3's `stage1_self_match_both_orders`)
  to direct `person`/`person_joint` buyers' top-level `stage1_identity` call,
  not just Sunbiz-derived principal names — the issue's "Also report" section
  explicitly invites a trivial fix, this reuses the exact same
  already-verified helper with zero new complexity, and it found 2 additional
  real addresses (Jean rosalva, Dorin Birta) live.
- Did NOT re-run the full batch a second time to live-verify this last
  extension's Tracerfy outcome: `public.ff_daily_credit_ledger` was at
  289/300 combined units for 2026-09-02 by the time this last code change
  landed (11 remaining, a shared resource other pipelines also draw from
  today). The 2 affected rows remain `row_enrichment_status='complete'` with
  no contact, so they will be reprocessed automatically on the next routine
  run (RERUN_PAID_LOOKUPS=false only skips rows with a real resolved
  contact) — tagged UNTESTED, not verified live this session.

## Why 0 phones / 0 emails / 0 billable persists after the fix
The P0 as literally titled ("pipeline never runs the fl_parcels self-match on
the PERSON") is fixed and verified (DoD #1-2). The business OUTCOME (contact
counts) is still 0/0/0 across both batches — this is a **separate, genuine
vendor-data ceiling**, not a residual pipeline bug: Tracerfy's enhanced-trace
endpoint returned `NO_MATCH` for every (name, now-correct-address) pair this
session tried, including the brand-new correct addresses found for Shilpa
Shah and Stern Ben. `JAYKAILASH LLC -> Rajendrakumar Patel` already had a
correct address from the prior (#19729) session and Tracerfy missed it too,
both before and after this fix — direct evidence this is a vendor lookup
limitation on these specific individuals, not an anchor-address bug. Tagged
CONFIRMED (evidence_ledger comparison pre/post this session, same address,
same miss).
