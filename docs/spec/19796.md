## Root causes found (live-verified, not inferred from migration filenames)

**#1 — `/deal/:county/:case` 404 for every plain visit.** `get_reel_landing()`
required `?preview=<row id>` to match before it would render a
`pending_approval` row. All 23 live rows are `pending_approval` and there is
no approval mechanism in this codebase for this table (unlike
`winnerdata.ff_batches`'s LMS), so under M8 (never write `status`) the gate
was permanently closed — every reel's own baked-in QR/CTA promise a page
that can never load. Confirmed live: `curl -sI https://biddeed.ai/deal/lee/2026000141` → 404 before fix, matching the issue's own 5/5 sample.

**#2 — `/reels/:code` 404 for every `reel_variants`-minted code.**
`agents/reel_studio/analyst.py::mint_variant_short_link()` mints
`short_code`/`short_url=/r/{code}`/`qr_url` for every variant and bakes that
URL into the rendered video's QR/CTA plate, but never inserted the matching
`winnerdata.reel_links` row that `get_reel_by_code()`/`resolve_reel_link()`
both require. Verified live: `select count(*) from winnerdata.reel_links
where code in (select short_code from winnerdata.reel_variants)` = 0/21
before fix.

**#3 — `/r/:code` redirected straight to the raw Supabase Storage MP4**,
confirmed only by live-curling (`curl -sI https://biddeed.ai/r/wvs4hW` →
302 to `.../reel_bolt32.mp4`), not by reading migration files in filename
order. Migration filename order does **not** equal applied order in this
project's history: `20260903c_reel_variant_studio.sql`'s `resolve_reel_link()`
(which checks `reel_variants` first and redirects to `v_variant.video_url`)
turned out to be the version actually live, even though
`20260903f_cmo_factory_cp3g_distribution_lane.sql` and
`20260903g_reel_landing_sticky_wiring.sql` — both later filenames, both
redefining the same function to the simpler `reel_links.target`-only
behavior — exist in the repo. Whoever ran those two migrations' other
statements evidently didn't re-run this one, or ran them out of order. This
is logged per CC_META_PROMPT §2.3 ("the DoD query itself may be wrong / a
prior session's stated state may be wrong — verify live, don't substitute
silently").

**Also found and fixed while in the same RPC**: `get_reel_landing()` never
selected `winnerdata.biddeed_reels.property_address` (a real column,
populated 23/23, a public county-record street address — fine per M3) even
though the issue's Part 1 lists "address" as a minimum required field on
the page. Added to the field allow-list and rendered on both
`buildDealLandingHtml()` and `buildPresaleDealHtml()`.

## What was built (all additive/idempotent, M2/M5-compliant — no protected
table touched, no `status` column written anywhere, single repo)

`supabase/migrations/20260903h_deal_reel_404_fix.sql`, applied live via the
Management API SQL endpoint (`SUPABASE_DB_PASSWORD`/direct psql failing is
the known, already-documented constraint — CC_META_PROMPT §4 ladder step 3
used instead, per this session's dispatch instructions):

1. `get_reel_landing()` — drop the preview-id gate on `pending_approval`;
   add `property_address` to the return object. `p_preview_id` stays in the
   signature (unused) so `src/worker.js`'s existing call site needed no
   change.
2. `get_reel_by_code()` — same gate removal; **prefers a `reel_variants`
   match** so a per-variant code plays that variant's own bolt32 render
   (`video_v2_url` in the JSON is populated from `reel_variants.video_url`
   when the code matches a variant, else falls back to the reel-level
   `video_v2_url` exactly as before); `short_url` in the response is always
   `https://biddeed.ai/r/{the code that was actually requested}`.
3. Backfill: one `winnerdata.reel_links` row per `reel_variants.short_code`
   missing one (21 rows inserted), `target='https://biddeed.ai/reels/{code}'`.
4. Repoint every pre-existing reel-linked `reel_links.target` (rows with
   `reel_id is not null`) from `/deal/...` to `/reels/{code}` — rows with
   `reel_id is null` (the 4 non-reel `/auctions` short links) untouched.
5. `resolve_reel_link()` — redefined so a `reel_variants` match redirects to
   `https://biddeed.ai/reels/{code}` (the player) instead of
   `v_variant.video_url` (raw storage) directly. Click-metrics logging to
   `winnerdata.reel_variant_metrics` unchanged.

`agents/reel_studio/analyst.py::mint_variant_short_link()` — now inserts the
`winnerdata.reel_links` row (`on conflict (code) do nothing`, idempotent) at
mint time, so root cause #2 cannot recur for the next batch of variants.

`src/worker.js::buildDealLandingHtml()` / `buildPresaleDealHtml()` — render
`reel.property_address` under the price headline, both wired to the CSS
classes `.deal-addr` / `.psale-addr`. No routing/RPC-call-site changes — the
existing `/deal`, `/reels/:code`, `/r/:code` routes and `get_reel_by_code`/
`get_reel_landing`/`resolve_reel_link` call sites were already correct; the
break was entirely on the DB/RPC/pipeline side.

## Deviations from spec

- Issue said "26 rows total" between the two tables; live count is 23
  distinct deal pages (23 biddeed_reels rows; the 21 reel_variants rows all
  belong to 5 of those same 23 reels, they don't add new pages). Reported
  per CC_META_PROMPT §1.2, not silently reconciled to 26.
- Issue's stated symptom ("`/r/<code>` redirects straight to the raw
  Supabase storage MP4") turned out to be exactly right, but the actual
  live function responsible was not the one the migration-filename dates
  would suggest — see root cause #3 above. Fixed regardless; flagged
  because it means this repo's migration file dates cannot be trusted as
  "applied order" for any future debugging session.
- Added `property_address` to the page (Part 1's own minimum-fields list
  named "address" but the field was never wired) — in scope of "reuse
  whatever page template already exists ... do not design a new one from
  scratch," this is a one-field addition to the existing template, not a
  new design.
- Did not flip any `biddeed_reels.status` or `reel_variants.status` value —
  M8 compliant throughout. Did not touch `social_content_queue`,
  `ff_batches`, or any M1/M2 protected object.

## Findings (not part of the task, surfaced per CC_META_PROMPT §6)

- **Migration filename date ≠ applied order** in this repo's Supabase
  project history (root cause #3). At least two migrations
  (`20260903f_cmo_factory_cp3g_distribution_lane.sql`,
  `20260903g_reel_landing_sticky_wiring.sql`) that redefine
  `resolve_reel_link()` to a simpler, already-superseded behavior exist in
  the repo but were not the live version before this session. Any future
  session debugging an RPC by reading `supabase/migrations/*.sql` in
  filename order should verify the live function body first
  (`pg_get_functiondef`) rather than trust file order.
- **Pre-existing, out-of-scope bug found while verifying**: `get_reel_landing()`
  has never returned a `phase` field (true in every prior version of this
  function too, not introduced by this session), so
  `src/worker.js`'s `if (reel.phase === 'presale') ... buildPresaleDealHtml`
  branch is unreachable via a direct `/deal/...` visit — `buildDealLandingHtml`
  (the postsale template) renders for presale rows too, e.g.
  `/deal/polk/2026ca000684a000ba` (a live presale row, auction not yet held)
  shows "Sold Price: —" instead of an opening-bid figure. Still 200, still
  has address/county/headline number/email capture (DoD met), just the
  wrong stat label for a presale property. Left unfixed — it's
  `#19761`/`#19786` presale-template territory, and #19796's own non-goals
  exclude "progressive-disclosure gating logic." Flagging for whoever owns
  that lane next.
- `winnerdata.biddeed_reels` has no click-to-approve mechanism at all
  (unlike `winnerdata.ff_batches`'s LMS `approved_at`). All 23 rows have
  been `pending_approval` since creation with no path to `approved` short of
  a manual `UPDATE`, which no session may run under M8. If this table is
  meant to ever ship an `approved`/`posted` reel, that approval UI/flow
  does not exist yet and is out of this issue's scope.
