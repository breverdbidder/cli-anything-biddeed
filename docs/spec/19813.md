## What I found and fixed, in order

### 1. Root-caused the `Build OpenNext Worker` CI failure (comment's open question)
Pulled the real failing log for run `33781544029` (`gh run view ... --log-failed`) instead of
guessing from the comment's hypothesis list (missing `NEXT_PUBLIC_*` build vars). The actual
error:
```
Error: No `wrangler.(toml|json|jsonc)` config file found.
Create one at the project root before running the build, or skip this check with
`--skipWranglerConfigCheck` or `SKIP_WRANGLER_CONFIG_CHECK=yes`.
```
Cloned `biddeed-web` to `/tmp/biddeed-web`, installed Node 22 (available locally via `n`;
default `node` in this session is v20, which fails `npm ci` on this repo's `nanoid@6` engine
requirement), and reproduced the exact failure locally. Read
`node_modules/@opennextjs/cloudflare/dist/cli/commands/build.js` and
`.../commands/utils/utils.js`: `opennextjs-cloudflare build` resolves its Wrangler config via
`readWranglerConfig(args)` → `unstable_readConfig({ env: args.env, config: args.wranglerConfigPath })`,
and `wranglerConfigPath` only gets set from a `--config`/`-c` CLI flag — there is no
auto-discovery of a non-default-named file. This repo's config is `wrangler.staging.jsonc`
(confirmed via `git log --all --diff-filter=AD -- 'wrangler*'`: it was the only wrangler config
ever committed, so the issue's "npm run cf:build passed locally" claim does not reproduce as
written — most likely whoever ran it locally had an untracked `wrangler.jsonc` or ran a
different command). `npm run cf:build` was just `opennextjs-cloudflare build`, no `--config`
flag — so it always hit the default-file-not-found path in CI (non-interactive → hard fail
instead of the interactive create-one-for-me prompt).

**Fix** (`package.json`, commit `5d4c18e` on `cloudflare-staging`): pass
`--config wrangler.staging.jsonc --env staging` to every `opennextjs-cloudflare build` /
`preview` invocation (`cf:build`, `cf:preview`, `cf:deploy:staging`), matching the flags
`cf:deploy:staging` already passed to `wrangler deploy`. Verified locally before pushing:
`npm run cf:build` completes and produces `.open-next/worker.js` (Next 16.1.6, 29 routes,
OpenNext 1.20.6). Also added `.open-next/`/`.wrangler/` to `.gitignore` — `cf:build` never
completed before, so this build-output directory had no chance to be accidentally committed
until now.

**Live proof**: GHA run `33782366949` (push-triggered) — `Build OpenNext Worker` ✓, `Deploy
staging Worker` ✓, deployed `biddeed-web-staging` (confirmed by name in the deploy log — **not**
`worker-biddeed-staging` or `worker-damp-snowflake-cead`) to
`https://biddeed-web-staging.brevardbidderai.workers.dev`. `Total Upload: 7442.70 KiB / gzip:
1493.53 KiB` — well under both the Free (3 MiB) and Paid (10 MiB) Worker size limits.

### 2. Attempted `staging.biddeed.ai` custom domain, hit a real conflict, did not force it
The workflow's own smoke-check step still failed (`/  -> 404`) because nothing routes
`staging.biddeed.ai` to `biddeed-web-staging`. Tried the standard fix twice, both times
verified live against the real Cloudflare API (not guessed):
1. `routes: [{ pattern: "staging.biddeed.ai", custom_domain: true }]` (commit `99d89e8`) →
   deploy failed: `Hostname 'staging.biddeed.ai' already has externally managed DNS records
   (A, CNAME, etc). Delete them first or try a different hostname. [code: 100117]`. Confirmed by
   `dig`: `staging.biddeed.ai` already resolves to Cloudflare anycast IPs — a DNS record already
   exists and I have no instruction authorizing me to delete it.
2. Switched to a plain zone Route (no DNS ownership claim): `routes: [{ pattern:
   "staging.biddeed.ai/*", zone_name: "biddeed.ai" }]` (commit `e91dc46`) → deploy failed
   differently and more informatively: `Can't deploy routes that are assigned to another worker.
   "worker-biddeed-staging" is already assigned to routes: - staging.biddeed.ai/*`.

This is exactly the "legacy router" the issue itself warned not to confuse this deployment
with — except it turns out that legacy router **currently owns the production route for that
exact hostname**. Reassigning a route away from a currently-live Worker is the kind of
production-adjacent, hard-to-reverse action that this repo's own standing rules (M5: no
schema/production changes not named in the issue; boundaries enforcement: ask before touching
anything not explicitly authorized) say to stop on, not push through by assumption — the issue
body names deploying `biddeed-web-staging` and warns against confusing it with
`worker-biddeed-staging`, but never authorizes unassigning that worker's live route. **Reverted**
(commit `24b6585`) to the last known-good, workers_dev-only config — confirmed via a third live
GHA run (`33783139171`): `Build OpenNext Worker` ✓, `Deploy staging Worker` ✓ again, clean.

The workflow's "Public staging smoke checks" step still fails in CI (it hardcodes
`base='https://staging.biddeed.ai'`) — this is expected and correct given the above, not a bug
I introduced or should silently patch over by editing the smoke-check step's target URL. Per the
issue's own contingency instruction ("if the copied token lacks Zone:DNS:Edit... deploy to the
workers.dev URL, run all gates there, and report to Ariel exactly which scope is missing rather
than stalling"), I ran the full gate table manually against `workers.dev` instead (below) rather
than either faking a green CI run or stalling on Ariel's routing decision.
