### What this session actually did, in order

**1. Root-caused the real production architecture (this was previously unknown/assumed wrong).**
The issue's own framing — "single reversible change: repoint production Worker origin from Vercel
Next.js to Cloudflare OpenNext Worker" — undersold what `worker-damp-snowflake-cead` (the Worker
that owns the `biddeed.ai/*` zone route) actually is. Fetched its live script via the Cloudflare
API (read-only, `GET /accounts/{id}/workers/scripts/{name}`) and found: it is **not** a bare
reverse proxy. It's a ~7,900-line hand-rolled application serving 40+ routes directly (chat,
Stripe checkout, 67 county SEO pages, legal pages, lead capture) with 5 live secret bindings
(`ANTHROPIC_KEY`, `POSTHOG_PROJECT_KEY`, `RESEND_API_KEY`, `ROUTER_PROXY_KEY`,
`SUPABASE_SERVICE_KEY`). Buried in it is an already-built strangler-fig proxy: a single constant
`const RADAR_ORIGIN = "https://biddeed-web.vercel.app"` (line 1733) and a `proxyToRadar()` function
that forwards exactly `/`, `/radar*`, `/_next/*`, `/api/*`, `/success*`, `/order*`, `/sign-in*`,
`/sign-up*`, `/discover*`, `/alerts*` to that origin, unmodified since a 2026-08-20 cutover. This
confirmed the issue's "single reversible change" framing was in fact correct — it just needed the
actual constant found and the actual mechanism understood before touching it blind.

**2. Verified the safe redeploy mechanism empirically before touching the real script**, because
getting this wrong risks wiping 5 live secrets that this session has no way to reconstruct or
re-supply (never had their values, never will per this repo's CREDENTIAL HANDLING mandate):
- Confirmed via a disposable throwaway Worker that Cloudflare's `PUT .../workers/scripts/{name}`
  multipart upload with `metadata: {"main_module":"worker.js","keep_bindings":["secret_text"]}`
  replaces code while preserving existing `secret_text` bindings — proved by actually invoking the
  redeployed throwaway Worker and reading back its bound secret at runtime.
- Hit a real bug in that mechanism against the actual router script: curl's `-F "worker.js=@path"`
  defaults `filename=` to the **local file's basename**, not the field name — so uploading a file
  saved as `/tmp/router-original.js` produced `filename="router-original.js"`, which Cloudflare
  rejected with `"No such module: worker.js"` since `main_module` in the metadata didn't match.
  Fixed by adding an explicit `;filename=worker.js` to the multipart part. Verified the fix with a
  content-neutral redeploy of the *actual* unmodified router script (a real, live, safe operation:
  `success: true`, `biddeed.ai/` still 200 immediately after, all 5 bindings still present) before
  ever touching the `RADAR_ORIGIN` line.
