## What was actually broken (verified against live production, not assumed)

Playwright (real browser, pixel/computed-style based, not source grep) against
`https://biddeed.ai` at session start found the true state was **better than
the issue's Sep-3 02:25 UTC snapshot** — the catastrophic 1.1:1 white-on-cream
failures the issue screenshots described were **already partially fixed** by
an earlier session (the issue's own trailing comment references a CC run at
03:01:45Z). What I found live and fixed this session:

1. **`buildBlogIndex`/`buildBlogPost` (`/blog`, `/blog/:slug`)** — `h1`,
   `.post-title`, `.lead-box h3` hardcoded `color:white`; body text correctly
   used the shell's re-themed CSS variables, headings did not. Fixed using
   the exact pattern already proven live on `/counties`
   (`buildCountiesIndex` already had a second `:root` light-mode override
   block — I hadn't noticed until reading it closely that this is why
   `/counties` was the one page the issue marked "OK").
2. **`buildChatPage` (`/chat`)** — same class of bug on `.bd-brand h1`,
   `.cb-name`, `.cb-stat .num`, `.wl-title` (the welcome-screen title, visible
   by default), `.panel-hdr .pt`, `.pc-addr`, `.pc-val`, plus input
   backgrounds. This function already had a **partial** light-mode override
   block (someone had fixed the voice dock and one input but not the rest) —
   extended it rather than introducing a second pattern.
3. **Sidebar CSS bleed (`PUBLIC_SHELL_STYLE`, all wrapped pages)** — real bug,
   not in the issue's list: `.bd-shell-nav` set no `background`, so any page's
   own bare `nav{background:...}` selector (present in `buildBlogIndex`,
   `buildCountiesIndex`, `buildPioneersPage`, etc.) leaked into the shared
   sidebar nav at equal-or-lower specificity, making the "Home" link render
   dark-on-dark (measured 1.18:1 live on `/blog`, `/pioneers`). Fixed with one
   line: `.bd-shell-nav{background:none}` — class selector beats the page's
   bare-tag selector regardless of source order, so this closes the leak for
   every current and future page that uses the shared shell.
4. **Sidebar icon default color** — active-state icons had a light-mode
   color override, inactive/default icons did not (`#94a3b8` on cream =
   2.26:1). Added `html[data-theme=light] .bd-shell-icon{color:#655e56}`
   (5.14:1 measured).
5. **`buildReelsGalleryHtml` / `buildSingleReelHtml` (`/reels`, `/reels/:code`)
   and `REELS_PLAYER_CSS`** — no CSS variables at all here (literal hex
   throughout), unlike the blog/chat pattern. `h1{color:#fff}` fixed with a
   direct `html[data-theme=light] h1{color:#1f1b16}` override; `.reel-meta
   .price` and card background fixed the same way.
6. **`buildDealLandingHtml` / `buildPresaleDealHtml` (`/deal/:county/:slug`)**
   — same literal-hex pattern, but a bigger one: my first pass only flipped
   text color and made things **worse** (ink-on-navy, ~1.04:1) because the
   card backgrounds (`.deal-stat`, `.deal-locked`, `.deal-cta`, `.psale-*`
   equivalents) stayed dark navy. Caught this by rendering the actual patched
   template locally (see Verification method below) before treating it as
   done — re-fixed to flip surface + text together. Left as a residual
   reminder in a code comment for anyone extending this pattern to a new
   template.
7. **`buildProofCard` (`/proof/:slug`)** and **`buildPioneersPage`
   (`/pioneers`)** — same two patterns (var-based fixed the counties way,
   literal-hex fixed the reels/deal way) applied.
8. **5 legal pages** (`TERMS_HTML`, `PRIVACY_HTML`, `DISCLAIMER_HTML`,
   `DATA_RETENTION_HTML`, `SECURITY_HTML`) — identical shared CSS block
   across all 5, `h2`/`.box strong`/`nav.top a`/`th` hardcoded `#fff`. Fixed
   once, applied via `replace_all` since the block is byte-identical in all 5
   (verified — 3+2 `h2` variants, 5 `.box strong`, 5 `nav.top a`, 1 `th`).
9. **`/chat/api` `max_tokens`** — raised 1024 → 4096. Root cause of "table
   answers cut off": `claude-router/index.ts`'s `callClaude`/`callDeepSeek`
   pass the Worker's `max_tokens` straight through with **no floor**
   (unlike its OpenRouter path, which forces `>=1500`), so the Worker's own
   low value was the real ceiling on a verbose tabular answer.
10. **`/radar` missing `<h1>`** (biddeed-web) — `AuctionsLayout.tsx` had an
    `<h2>` ("Auction Intelligence") as its only heading and no `<h1>`
    anywhere on the page. Promoted it to `<h1>` — it already was the page's
    real primary heading semantically, nothing else needed to change.
11. **Voice mic button absent on home** (biddeed-web `Composer.tsx`) — was a
    permanently `disabled` button with title "Voice is coming — it is not
    connected on this page yet." Now navigates to `/chat`, where the real
    voice feature lives (see Voice section below) — a minimal, safe fix, not
    a UI dead-end.

## What I found was NOT actually broken (methodology corrections, logged so
## nobody re-chases these as bugs)

- My first-pass contrast script read `getComputedStyle().backgroundColor`
  only. Two "1.00 ratio / literally invisible" findings it initially reported
  (`/chat` "Talk to Deed" button, `/` "Most chosen" badge) were **false
  positives** — both elements paint via `background-image: linear-gradient`
  or a semi-transparent `background-color` (e.g. `rgba(16,185,129,.15)`),
  which the naive check doesn't composite against the ancestor. Rewrote the
  script to average gradient stops as a proxy background before concluding a
  real bug (see `scripts/ui-contrast/check.mjs`). It still doesn't
  alpha-composite translucent backgrounds against their ancestor chain — a
  few residual "FAIL" lines in the before/after run below (`.save-badge` on
  `/subscribe`, `.ey` on `/pioneers`, `.qbtn.prime` on `/chat`) are this same
  known limitation, confirmed by reading the actual CSS (translucent tint,
  not a solid color), not real invisible-text bugs. Flagged as a TODO in the
  script rather than silently "fixed" by suppressing the false positive.
- `/answers/*` — does not exist anywhere in `worker.js` or `biddeed-web`.
  Nothing to fix; the issue's route list appears to include an aspirational
  or already-retired route.
- `buildHomepageHtml()` in `worker.js` (~line 6985) is **dead code** — `/` is
  proxied to biddeed-web (`proxyToRadar`) earlier in `handleRequest`'s
  routing table, so this function's own hardcoded-dark-theme markup (which
  also has the white-text bug) is unreachable. Left alone per K3 (mention,
  don't delete unrelated dead code) — flagging here as a real finding worth a
  cleanup PR.
- The Deed voice widget on `/chat` is **not** "absent" — it's a fully
  implemented, working, raw WebSocket ElevenLabs Conversational AI
  integration (`AGENT_ID` configured, signed-URL fetch to a Supabase edge
  function, PCM audio encode/decode, email-gate, session-cap timer — ~400
  lines in `worker.js` around line 5277+). **Verified live end-to-end** with
  Playwright + fake audio device: click → email gate shows → submit → `200`
  from `elevenlabs-signed-url` → WebSocket opens → button becomes "⏹ Stop",
  status shows "🎙️ Listening…". The issue's DoD ("Playwright: click → widget
  iframe present") describes the wrong mechanism — there is no iframe, it's a
  direct WebSocket/Web Audio session. What was genuinely missing is only the
  **home page** entry point (item 11 above) — a completely separate,
  React-based codebase (biddeed-web) with no port of this logic yet.
