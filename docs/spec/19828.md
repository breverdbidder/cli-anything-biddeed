## What was actually broken (verified against live production, not assumed)

Playwright (real browser, pixel/computed-style based, not source grep) against
`https://biddeed.ai` at session start found the true state was **better than
the issue's Sep-3 02:25 UTC snapshot** — the catastrophic 1.1:1 white-on-cream

03:01:45Z). What I found live and fixed this session:

1. **`buildBlogIndex`/`buildBlogPost` (`/blog`, `/blog/:slug`)** — `h1`,
   `.post-title`, `.lead-box h3` hardcoded `color:white`; body text correctly
   used the shell's re-themed CSS variables, headings did not. Fixed using
   the exact pattern already proven live on `/counties`
   (`buildCountiesIndex` already had a second `:root` light-mode override
   block — I hadn't noticed until reading it closely that this is why
   `/counties` was the one page the issue marked "OK").
2. **`buildChatPage` (`/chat`)** — same class of bug on `.bd-brand h1`,
   `.cb-name`, `.cb-stat .num`, `.wl-title` (the welcome-screen title, visible
   by default), `.panel-hdr .pt`, `.pc-addr`, `.pc-val`, plus input
   backgrounds. This function already had a **partial** light-mode override
   block (someone had fixed the voice dock and one input but not the rest) —
   extended it rather than introducing a second pattern.
3. **Sidebar CSS bleed (`PUBLIC_SHELL_STYLE`, all wrapped pages)** — real bug,
   not in the issue's list: `.bd-shell-nav` set no `background`, so any page's
   own bare `nav{background:...}` selector (present in `buildBlogIndex`,
   `buildCountiesIndex`, `buildPioneersPage`, etc.) leaked into the shared

   dark-on-dark (measured 1.18:1 live on `/blog`, `/pioneers`). Fixed with one
   line: `.bd-shell-nav{background:none}` — class selector beats the page's
   bare-tag selector regardless of source order, so this closes the leak for
   every current and future page that uses the shared shell.
4. **Sidebar icon default color** — active-state icons had a light-mode
   color override, inactive/default icons did not (`#94a3b8` on cream =
   2.26:1). Added `html[data-theme=light] .bd-shell-icon{color:#655e56}`
   (5.14:1 measured).

7. **`buildProofCard` (`/proof/:slug`)** and **`buildPioneersPage`
   (`/pioneers`)** — same two patterns (var-based fixed the counties way,
   literal-hex fixed the reels/deal way) applied.
8. **5 legal pages** (`TERMS_HTML`, `PRIVACY_HTML`, `DISCLAIMER_HTML`,

## What I found was NOT actually broken (methodology corrections, logged so
## nobody re-chases these as bugs)

  only. Two "1.00 ratio / literally invisible" findings it initially reported
  (`/chat` "Talk to Deed" button, `/` "Most chosen" badge) were **false
  positives** — both elements paint via `background-image: linear-gradient`

  script to average gradient stops as a proxy background before concluding a

  few residual "FAIL" lines in the before/after run below (`.save-badge` on
  `/subscribe`, `.ey` on `/pioneers`, `.qbtn.prime` on `/chat`) are this same
  known limitation, confirmed by reading the actual CSS (translucent tint,
  not a solid color), not real invisible-text bugs. Flagged as a TODO in the
  script rather than silently "fixed" by suppressing the false positive.
- `/answers/*` — does not exist anywhere in `worker.js` or `biddeed-web`.
  Nothing to fix; the issue's route list appears to include an aspirational
  or already-retired route.
- `buildHomepageHtml()` in `worker.js` (~line 6985) is **dead code** — `/` is
  proxied to biddeed-web (`proxyToRadar`) earlier in `handleRequest`'s

  also has the white-text bug) is unreachable. Left alone per K3 (mention,

### A3 (hex/`:root` dedup) — real progress, not full completion, with a
### documented reason the PASS 4 target ("1 `:root` block") isn't reachable
### the way it's phrased without live-browser verification

**A real architectural finding, verified by reading source and computing
CSS specificity by hand (not assumed):** `PUBLIC_SHELL_STYLE`'s
`html[data-theme=light]{--navy:...;--orange:...;--text:...;--muted:...;
--border:...}` rule — injected into every `withPublicShell()`-wrapped page
right before `</head>`, i.e. **after** that page's own `<style>` block —
has specificity `(0,1,0,1)` (attribute selector `[data-theme=light]` + type
selector `html`). A page's own local `:root{...}` override (the "second
unconditional `:root`" pattern already present in `buildBlogIndex`,
`buildBlogPost`, `buildCountiesIndex`, etc.) has specificity `(0,1,0,0)`.
**The shell's rule wins regardless of source order**, for every one of the
8 custom properties both define. Since `apply('light')` runs synchronously
in an inline `<script>` immediately after the shell markup, `data-theme=
light` is active almost immediately on every page load. This means: for
every `withPublicShell`-wrapped page (which is nearly all of them — grep
confirmed `TERMS_HTML`, `PRIVACY_HTML`, `DISCLAIMER_HTML`, `SECURITY_HTML`,
`DATA_RETENTION_HTML`, `BUY_REPORT_HTML`, `buildFreeReportFormHtml`,

returned raw, unwrapped), the page's own local `--navy`/`--orange`/`--text`/

once `data-theme=light` is set, regardless of what the page's own `:root`
says. This pre-exists in current `main` — nothing in this session's edits
introduced it or would have changed it either way.

### A8 (`/chat/api` real streaming) — completed and verified live, not assumed

Root cause (confirmed by both sessions 1 and 2 by reading source): `claude-
router/index.ts` had **zero** streaming support — grep for `"stream"` in
its 739 lines matched only the inert `stream: false` field name. Every
non-Gemini-fallback `/chat/api` call (the primary path most paid users hit)
called `callClaude`/`callDeepSeek` with a plain buffered fetch, got the
full completion back as one JSON `{text: "..."}` payload, then worker.js
wrapped that single string as one SSE `data:` event — so answers arrived
all at once, with no incremental rendering, regardless of length.

**Fix:** added an additive `stream: true` request mode to claude-router.
Existing callers (anything that doesn't set `stream: true`, i.e. the MCP
tools in `packages/biddeed-mcp`/`packages/zonewise-mcp` and any other
caller) get **byte-identical behavior** — the new code lives entirely on a
new early-return branch (`if (wantStream && !hasImages) return await
handleStreamingText(...)`) that non-streaming callers never enter. For each
tier in the existing cascade order (T1 Gemini free → T1.5 DeepSeek cheap →
T2 Claude OAuth last-resort), the streaming variant calls the provider's
own native streaming endpoint and checks `res.ok` **before** consuming the
body — exactly mirroring the non-streaming cascade's "try, check, fall back
to next tier" pattern, so fallback safety is preserved right up to the
point a tier is committed to. Once committed, that tier's SSE is parsed by
a per-provider extractor and **re-emitted as a normalized `{text: <delta>}`
shape**, so worker.js needed zero parsing changes — its existing `typeof
evt.text === 'string' ? evt.text : null` fallback (already there for a
future non-Gemini streaming path that never existed until now) matches
exactly. Cache-hit responses for `stream: true` callers get wrapped as a
single-chunk SSE response so the response shape is always SSE for
streaming callers, never a shape-switch on cache state.

**Verified live against the deployed function, not assumed:**
- **Gemini's SSE delta semantics were tested, not assumed**, and the
  initial assumption was wrong: I first assumed Gemini's streaming `text`
  field was a cumulative snapshot of the answer-so-far (common in some
  streaming APIs) and wrote diff-against-previous logic for it. A direct
  live test (essay-length prompt, 18 SSE chunks) showed the chunks
  concatenate cleanly into the full text with no overlap — i.e. Gemini's
  deltas are incremental, same as Claude/DeepSeek. Caught and fixed before
  shipping, not after — this would have corrupted or duplicated every
  Gemini-tier streamed response in production had it shipped as first
  written.
- **Claude's SSE shape was tested live** (not inferred from docs alone):
  `message_start.message.usage.input_tokens`, incremental
  `content_block_delta.delta.text`, cumulative `message_delta.usage.

- **DeepSeek's SSE shape (OpenAI-compatible `choices[0].delta.content`) is
