# Spec — issue #20077 — P0: public deal/reels pages leaked PREVIEW banner + wrong-county chip

## Intent reference
None at `docs/intent/20077.md` — the issue body was the only brief, per M6.

## Session type
Build session, headless (`claude -p`, cc-runner), 2026-09-06/07. All work is
confined to `src/worker.js` (the Cloudflare Worker that serves `biddeed.ai`'s
`/deal/:county/:slug`, `/reels`, `/reels/:code` routes — confirmed there is no
Next.js app in this repo; the `biddeed-web` app referenced in `docs/spec/20053.md`
is a different repo and does not implement these routes). Deployed twice —
the first deploy shipped a real regression that was caught and fixed within
the same session; see "Self-caught regression" below.

## Root cause (CONFIRMED)

1. **PREVIEW leak.** The `/deal/:county/:slug` and `/reels/:code` route
   handlers' own comments already claimed "`pending_approval` rows only
   render with `?preview=<row id>`", but the PREVIEW banner was gated purely
   on `reel.status === 'pending_approval'`, with no check that a preview id
   had even been supplied. A signed-out request with zero query params on
   `/deal/martin/25001204caaxmx` and `/reels/O7EPH7` rendered the pending
   row's "PREVIEW — pending approval, not yet public" banner.
2. **Wrong-county chip.** `dealPageStickyScript()`'s returning-visitor
   greeting used `d.first_county` — the visitor's own history, tracked
   server-side by `upsert_visitor_profile()` — with no comparison against
   the county of the page currently being viewed. A visitor whose stored
   history started on a Lee County page and later loads an unrelated Martin
   County page got a chip reading "N more Lee auctions since you were here"
   on the Martin page.
3. **Player read as a static image.** `.reel-cta-overlay` (link text
   "biddeed.ai →") was `opacity:0`/`pointer-events:none` until the JS
   `timeupdate` handler detected the video was within 3s of ending, and
   there was no play-icon affordance at all — a visitor who never triggered
   play (Ariel's report: he never played it) saw only the poster image with
   no indication it was a video or that it was clickable.

## What was built (all in `src/worker.js`)

- **`isValidPreviewId()`** (new helper, next to `extractApiKey`) — a
  `?preview=` value must match a UUID shape.
- **Banner-only gate.** Route handlers for `/deal/:county/:slug` and
  `/reels/:code` compute `showPreviewBanner = reel.status ===
  'pending_approval' && isValidPreviewId(previewId)` and pass it through to
  `buildDealLandingHtml` / `buildPresaleDealHtml` / `buildSingleReelHtml`,
  which now key the banner div off that flag instead of off `reel.status`
  directly. **The page itself always renders regardless of status** — only
  the banner is gated. See "Self-caught regression" for why this matters.
- **County-chip guard** in `dealPageStickyScript()` — normalizes both
  `d.first_county` and the current page's own `county` (case/`_`-insensitive)
  and only renders the greeting when they match; otherwise the chip renders
  nothing, per the issue's exact spec.
- **Reel player** (`reelCardHtml` / `REELS_PLAYER_CSS` / `reelPlayerScript`):
  added an always-visible `.reel-play-btn` (▶) overlay that hides only while
  the video's `play` event has fired and reappears on `pause`; changed
  `.reel-cta-overlay` to render at rest instead of only near the video's end
  (still absolutely positioned inside the 9:16 video box, so it's on-screen
  without scrolling at any viewport ≥ ~300px wide, including 390px); renamed
  its label from "biddeed.ai →" to "See this deal →" to match the reel end
  card (M9). Removed the now-dead `timeupdate`-driven `.show` class toggle
  and its now-unused `overlay` variable (orphaned by the CSS change, not
  pre-existing dead code).

## Self-caught regression (disclosed per Honesty Protocol / SHIP GATE)

The **first** deploy of this fix (commit `899dbfcf`) implemented the PREVIEW
gate by 404ing the entire `/deal` or `/reels/:code` response when
`reel.status === 'pending_approval'` and no valid preview id was present —
i.e. treating a pending row exactly like a nonexistent one, not just hiding
its banner. This was over-scoped relative to the issue's literal wording
("Default public render = no banner, **regardless of the reel variant's
approval status**") and broke production immediately: it turns out
`pending_approval` is the *normal* current state of real, live,
publicly-linked rows right now (not an internal-only draft state) — all 3 of
the canonical deal pages used by the pre-existing `#20058` brand-check gate
(`deal/polk/2024ca000341000000`, `deal/lee/2026000141`,
`deal/broward/cace-24-008115`) started returning `404 Not found` post-deploy.

Caught within the same session by the pre-existing `#20058` GHA gate going
red (GHA run
[`34068954085`](https://github.com/breverdbidder/cli-anything-biddeed/actions/runs/34068954085),
`FAIL: .../deal/polk/... does not contain 'SIGNAL$ Max Bid'` ×3) immediately
after the deploy step. Live `curl` confirmed all three were 404ing. Root
cause diagnosed and fixed in commit `be8a04c7` (banner-only gate, described
above), re-deployed, and GHA run
[`34069189798`](https://github.com/breverdbidder/cli-anything-biddeed/actions/runs/34069189798)
— re-run once for edge-cache propagation lag on the first attempt — passed
both the GTM-7 short-link gate and the `#20058` brand gate. **Approximate
production impact window: ~5 minutes** (deploy of `899dbfcf` completed
2026-09-07T00:09:22Z per GHA; fix deployed and verified green by
2026-09-07T00:16Z). Logged to `public.agent_ops_log`
(`id=0d9ee083-4fb4-48a3-85c4-36461388254f`, `status='VERIFIED'`, includes the
full incident narrative).

## Tests

`tests/deal-reel-preview.test.js` (Node's built-in `node:test`, same pattern
as `tests/support-bot.test.js` — mocks `fetch` for the Supabase RPC calls,
calls `worker.fetch()` directly). 9 assertions, all passing locally
(`npm run test:worker` — 17/17 total across both test files, `node --check
src/worker.js` clean):

- signed-out `/deal/...` renders 200 (page intact) but never leaks the
  PREVIEW banner for a `pending_approval` row with no `?preview=`
- a malformed `?preview=not-a-uuid` does not unlock the banner
- a valid `?preview=<uuid>` renders the banner
- an approved (`posted`) deal page never renders the banner
- signed-out `/reels/:code` renders 200 without leaking the banner
- `/reels/:code` with a valid `?preview=<uuid>` renders the banner
- **county chip renders nothing on a Martin page given a stale Lee visit
  history** (the exact reproduction case named in the issue) — extracts and
  executes the real `<script>` the route emits (not a reimplementation) in a
  `vm` sandbox with minimal `document`/`localStorage`/`fetch` shims
- county chip renders correctly when the visitor history county matches the
  current page

## Residual / follow-ups

- If a future session revisits item 4: reuse this session's
  `isValidPreviewId`/`showPreviewBanner` logic conceptually — a
  workflow-level curl check for the literal banner copy (`PREVIEW — pending
  approval, not yet public` / `PREVIEW MODE`) rather than a bare `grep -qi
  PREVIEW`, which false-positives on the `.deal-preview-banner`/
  `.reels-preview-banner` CSS class names that are always present in the
  stylesheet regardless of whether the banner div renders (discovered while
  writing the unit test in this session). **Do not gate the whole page on
  `pending_approval`** — that is the exact regression this session shipped
  and reverted; `pending_approval` is evidently the normal state of live,
  linkable rows, not an internal draft state.
- "Authenticated admin" as an alternate PREVIEW-banner path (mentioned in
  the issue's Fix item 1) was not implemented — this Worker has no
  cookie/session mechanism at all (confirmed: `extractApiKey`'s own comment,
  `no cookie/session login anywhere in this Worker`). Only the
  `?preview=<uuid>` path exists. Flagging as INFERRED-not-built rather than
  silently assuming it's covered.
- No browser screenshot of the Martin page's county chip was captured this
  session (headless, no browser automation tool invoked) — the unit test's
  `vm`-sandboxed execution of the actual shipped script is the evidence
  produced instead; a screenshot is a same-effort residual for a session
  with browser tooling available.
- This session's pushes repeatedly raced an unrelated, actively-recurring
  "house brand" palette rewrite/revert war on `main` (see `docs/spec/20070.md`
  "Critical finding" and `docs/spec/20076.md`) touching the same file. Not
  this issue's lane (M5) — resolved merge conflicts by always keeping
  whichever palette values were live on `main` at rebase time and never
  introducing new brand colors myself (the one new visual element,
  `.reel-play-btn`, uses palette-neutral `rgba(0,0,0,.55)` so it doesn't take
  a side in that fight).
