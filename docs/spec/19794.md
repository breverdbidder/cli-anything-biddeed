## Headline finding — the issue's OWN premise needed correcting

The issue's framing ("11,396 clerk-SSOT tax-deed rows exist, reels pipeline reads 3 — wiring gap,
not a data gap") is **half right**. Verified live 2026-09-03 against Supabase (PostgREST +
Management API, `SUPABASE_ACCESS_TOKEN`/`SUPABASE_SERVICE_ROLE_KEY` — direct psql unavailable per
documented constraint, decision_log ids 169/205/287):

1. **It IS a wiring gap** — but the gap is that `biddeed_reels_pipeline.py` only ever queried a
   SINGLE `auction_date`, never a rolling window. `public.auction_buyer_sightings` (the table the
   pipeline already reads) had **88 tax_deed/third_party candidates in the trailing 14 days across
   9 counties** the whole time — vs. the 3 rows that ever made it into `winnerdata.biddeed_reels`.
   Widening the query to a date range is the actual, verified fix (see "Fix 1" below).
2. **`clerk_ssot_sale_rows` itself is NOT a usable standalone reel source.** It is a
   clerk-scraped sale **calendar/docket** table, built for calendar parity, not a results table.
   It has **no `sold_amount` column at all**. Its 11,396 tax_deed rows carry only
   `case_number, county_slug, sale_type, sale_date, cancelled, raw_comment, case_title,
   source_url` — see Schema Report below. Price and parcel-identifier signals, where they exist
   at all, live in inconsistent per-county free text inside `raw_comment`, and — this is the
   load-bearing finding — **price and a joinable parcel never co-occur at meaningful volume in
   the same county.** Wiring it in as an ADDITIVE source (done, see Fix 2) contributes **0 rows**
   against live data as of this session, because of that gap. This is reported honestly rather
   than papered over.

Both fixes are implemented in code (not just analyzed) — see "Files touched."

## DoD Item 5 — Absolute-auction data-quality assertion

Documented in `docs/gtm/REEL_SPEC_BOLT32.md` ("Absolute Auction Data-Quality Assertion" section,
added this session) and enforced in code: `get_reel_candidates()`'s `mca_source` CTE requires
`buyer_type='third_party'` for `foreclosure` rows only; for `tax_deed` rows it accepts
`buyer_type IS NULL OR buyer_type='third_party'` (excluding an explicit `'plaintiff'`
classification, which would mean a reclaim — though tax deed structurally has no plaintiff to
reclaim via). This is a real, previously-live bug fix, not just documentation: **7 real Flagler
County tax_deed sales** (sold_amount populated, e.g. $208,900.00 on 2025-08-12) were sitting in
`auction_buyer_sightings` with `buyer_type IS NULL` and were invisible to the old query.

Negative test (c) — "foreclosure-specific validation (winning_bidder ambiguity checks) is not
applied to a tax_deed row" — is satisfied by this same change, and the reverse direction is also
handled: `agents/reel_studio/hook_writer.py`'s new `compute_archetype_priority()` never
prioritizes `bank_vs_house` for a `tax_deed` row, because that archetype's own data-match check
(`check_archetype_data_match`) requires a confirmed bank/lender **plaintiff**, a concept that does
not exist for tax deed cases at all.

## DoD Item 6 — Discount-percent vs dollar-amount framing rule (Hook Writer)

Added `agents/reel_studio/hook_writer.py::compute_archetype_priority()` /
`_select_archetypes()`, wired into `generate_variants_for_reel()`'s archetype sampling (was pure
`random.sample(ARCHETYPES, k)`, now guarantees a data-justified archetype a slot when the row's
own numbers clear a real threshold, falls back to unbiased random otherwise — "never force one
onto weak data," per the issue).

Real thresholds (VERIFIED live against `public.multi_county_auctions`, `sold_amount > 0 and
assessed_value > 0`, 2026-09-03 — methodology note: `avg(sold_amount)/avg(assessed_value)`
reproduces the issue's own ~40%/~61% headline figures; a per-row average of `sold/assessed`
ratios is skewed by near-zero-assessed outliers and is unusable for this comparison):

| sale_type | n | avg sold | avg assessed | avg-sold/avg-assessed | p75 dollar_delta (→ threshold) | p75 pct_below_assessed (→ threshold) |
|---|---|---|---|---|---|---|
| foreclosure | 1,606 | $161,208 | $266,540 | 60.5% | $151,758 → **$150,000** | 80.0% → **75%** |
| tax_deed | 1,183 | $17,263 | $43,241 | 39.9% | $20,185 → **$20,000** | 62.6% → **60%** |

Rule: `dollar_delta = assessed_value - sold_amount` ≥ sale_type's dollar threshold →
`shock_number`. `pct_below_assessed = dollar_delta/assessed_value*100` ≥ sale_type's pct
threshold → `hidden_value_reveal` (+ `bank_vs_house`, foreclosure only). Verified with synthetic
rows: a tax_deed row at 90%-below/$45K-delta correctly prioritizes both `shock_number` and
`hidden_value_reveal`; a row clearing neither threshold correctly returns `[]` and falls through
to plain random sampling.
