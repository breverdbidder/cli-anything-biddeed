## Headline: TASK — PARTIAL (see DoD status table)

The issue's own framing ("it is a pipeline-wiring gap, not a data gap") is
**half right**. Re-derived live 2026-09-03:

- `public.clerk_ssot_sale_rows` carries **11,396** `tax_deed` rows across
  **17** counties — confirmed, matches the issue.
- It carries **no `sold_amount`, `parcel_id`, or `property_address` column
  at all** — schema is `id, county_slug, sale_type, case_number, sale_date,
  cancelled, raw_comment, case_title, source_url, parsed_at, created_at`.
  Price/parcel data only exists in `public.multi_county_auctions`, reached
  by joining on `(case_number, county)`.
- Of the 7,923 non-cancelled tax_deed rows, only **723 (9.1%)** join to
  `multi_county_auctions` by case_number at all. The join rate is 90-100%
  for 10 of the 17 counties (calhoun, desoto, gadsden, jefferson, st_johns,
  st_lucie, sumter, wakulla, walton, and levy at 93.8%) — genuinely a pure
  wiring gap there. But the two counties that hold **94.7%** of
  clerk_ssot's own tax_deed volume join far worse: **highlands 7.6%**
  (331/4,362), **nassau 2.1%** (67/3,162). For those two, `multi_county_
  auctions` simply hasn't scraped/priced most of what clerk_ssot already
  knows is a real case — a data-completeness gap, not something the join
  fixes. Non-goals rule out a new scraper, so this gap is documented, not
  closed, this session.
- After the join, a genuine third-party-sold + real-priced + parcel-
  identified candidate exists for **222** of the 11,396 rows (all-time),
  concentrated: highlands 153, nassau 53, gulf 8, walton 8.
- In the most recent 14 days: **81** qualifying candidates (highlands 75,
  walton 6) before the parcel-outline join check; see the audit run below
  for the pass/fail split.
- In the most recent 28 days, combined with the existing
  `auction_buyer_sightings` source (deduped): **196** candidates vs **88**
  from the old source alone — a **+123%** increase — but still concentrated
  on Tue/Wed/Thu/Mon only; **zero** candidates fell on any Fri/Sat/Sun in
  this window from either source. The #19793 starvation ladder is **still
  needed** (see "Corrected 4-week starvation forecast" below).

`case_title` embeds full plaintiff/defendant names for several counties
(st_johns, st_lucie, levy, walton, gadsden) — **never read into anything
user-facing**, only `case_number` is safe (M7).

`sale_date` is populated for only **1,282 of 11,396 (11%)** tax_deed rows —
the other 89% have `sale_date IS NULL`; the backfill query falls back to
`multi_county_auctions.auction_date`/`sale_date` for those.

Conclusion: **clerk_ssot_sale_rows does not itself carry what a reel
needs.** The only fix that produces a real price/parcel is the join to
`multi_county_auctions`, and that join's coverage is exactly the
completeness gap described above.

## Step 3 — Extended candidate query + backfill

New file: `scripts/biddeed_reels_clerk_ssot_taxdeed_backfill.py`.
`get_clerk_ssot_tax_deed_candidates(days)` runs (server-side, via the
Supabase Management API, which — unlike PostgREST — reaches `public.*`
tables directly with a single join instead of N paginated client-side
fetches):

```sql
with clerk_qualifying as (
  select c.case_number, c.county_slug as county, c.sale_type,
         coalesce(c.sale_date, m.auction_date, m.sale_date) as auction_date,
         m.property_address,
         case when coalesce(m.sold_amount,0) > 0 then m.sold_amount else m.tier1_sold_amount end as sold_amount
  from public.clerk_ssot_sale_rows c
  join public.multi_county_auctions m
    on m.case_number = c.case_number and m.county = c.county_slug
  where c.sale_type = 'tax_deed'
    and c.cancelled = false
    and coalesce(c.raw_comment,'') !~* '(REDEEM|CANCEL|APPLICANT|DEFAULT|PENDING|SCHEDULED|FOR SALE)'
    and (m.sale_result = 'SOLD_THIRD_PARTY' or upper(coalesce(m.tier1_sale_status,'')) = 'SOLD')
    and (coalesce(m.sold_amount,0) > 0 or coalesce(m.tier1_sold_amount,0) > 0)
    and m.parcel_id is not null
),
already_sourced as (
  select case_number, county from public.auction_buyer_sightings
  where buyer_type = 'third_party' and sale_type = 'tax_deed'
)
select cq.* from clerk_qualifying cq
left join already_sourced a on a.case_number = cq.case_number and a.county = cq.county
where a.case_number is null
  and cq.auction_date >= current_date - interval '{days} days' and cq.auction_date <= current_date;
```

The `left join already_sourced ... where a.case_number is null` clause is
negative test (b) enforced in SQL, not just documented: a case already
sourced via `auction_buyer_sightings` is never re-emitted as a
clerk_ssot-sourced candidate. `winnerdata.biddeed_reels`'s own unique
constraint on `(case_number, county)` is the second layer.

Each surviving candidate is fed through the **existing**
`biddeed_reels_pipeline.process_row()` unchanged (imported, not
duplicated) — this is a new candidate SOURCE, not a new render path. A
candidate whose `lib.match_parcel()` call fails is never rendered
(negative test (a)).

No foreclosure-style `winning_bidder`-ambiguity check is applied to any
tax_deed row in this script (negative test (c)) — see the new "Sale-Type-
Specific Data-Quality Rules" section added to `docs/gtm/REEL_SPEC_BOLT32.md`
for why that check does not apply to an absolute auction, and why that is
NOT the same thing as skipping the "did a sale actually happen" filter
(REDEEMED/SCHEDULED/APPLICANT rows are still excluded above).

**Answer to the issue's own question ("confirm whether the starvation
ladder ... is still needed, or whether slot 2 can now fill from same-day
inventory on most weekdays"): the ladder is still needed.** The fix is a
real, large improvement (+123% candidate volume over 28 days, and it adds
two brand-new supply days — 8/11 and 8/18 — that had zero candidates from
the old source), but same-day fill only works on Tue/Wed/Thu, and even
those aren't hit every week. Zero candidates existed on any Friday,
Saturday, or Sunday in this 28-day window from either source, because
Highlands' and Nassau's tax-deed auction calendars run on a roughly
biweekly Tue/Wed cadence, not daily. #19793's cadence/ladder logic is not
obsoleted by this fix — it is now backed by a materially bigger real pool.
