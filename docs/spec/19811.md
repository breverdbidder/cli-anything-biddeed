### Layer 4 — Standing guard: extend #19765's daily-close alert

Same migration file, extending `finance.daily_close()` (owned by #19765) with one new step:

- **`finance.check_vendor_spend_anomalies(p_since date default current_date - 1)`** — SQL,
  `SECURITY DEFINER`, `EXECUTE` explicitly revoked from `PUBLIC` and re-granted to `service_role`
  only (see security-advisor finding below). Flags, per vendor, any charge posted on/after
  `p_since` that is either (a) from a vendor with **zero** prior charges in the trailing 90 days
  (`new_vendor_charge`), or (b) **>150% of that vendor's own trailing-90-day median** charge
  (`vendor_spend_over_150pct_median`).
- **`finance.daily_close()`** — new step (g), between the cost-view liveness check and the final
  balance re-check: calls the function above for `current_date - 1`, appends a formatted
  `vendor_spend_anomaly: ...` string to `alert_reasons` for each hit, adds a
  `vendor_spend_anomalies` count to the returned summary. Every other line of #19765's function is
  byte-for-byte unchanged — this was a surgical addition, not a rewrite (Karpathy K3 per
  CLAUDE.md). Alert delivery reuses the existing `finance._send_close_alert()` → Resend →
  `everestcapital8@gmail.com` path unmodified.

**Stated limitation, not glossed over:** this is a **lagging, ledger-based** signal. It can only
fire the day a charge posts to a bank account this system already ingests via SimpleFIN — it
cannot pre-empt a charge the way Vercel/Railway/Supabase's own dashboard caps can. The Vercel
$82.20 overage line itself has not appeared in the personal-account ledger as of this session (the
ledger only shows the flat $20 Pro-seat charges) — proof that this alert, while real and now live,
would **not** have caught this specific incident on its own. It is a genuine complement to Layer 1
and 3, not a substitute for either.
