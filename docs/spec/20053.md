# Spec — issue #20053 — P0: deal pages + /r + /reels returned 404 for signed-out visitors

## Intent reference
No `docs/intent/20053.md` existed at dispatch time — the issue body is the only brief, per M6.

## Root cause (CONFIRMED, not the issue's stated hypothesis)

The issue body's own hypothesis was "a Clerk middleware protect-all matcher change in
`middleware.ts`" and asked to `git log` that file since Sep 5 17:00 UTC. That file's
matcher had **not** changed since 2026-08-20 — `isPublicRoute` in `biddeed-web/middleware.ts`
never listed `/deal`, `/r`, `/reels`, `/subscribe`, `/support`, `/contact`, `/api/capture`
because those routes were never meant to be served by that Next.js app at all.

The real regression is a **Cloudflare zone-route ownership hijack**, in a different repo
(`breverdbidder/biddeed-web`), commit `97aa6e1` ("deploy(cloudflare): bind canonical
production apex route", 2026-09-06 13:53:35 UTC — inside the issue's own 13:20–13:55 UTC
incident window):

- `wrangler.production.jsonc` gained `"routes": [{ "pattern": "biddeed.ai/*", ... }]` for the
  `biddeed-web-production` Worker (the OpenNext/Next.js/Clerk app).
- `.github/workflows/cloudflare-production.yml` gained a "Reconcile production Worker route
  ownership" step that deleted **every** Cloudflare Workers Route on the `biddeed.ai` zone not
  owned by `biddeed-web-production` — which deleted the legacy router Worker's
  (`worker-damp-snowflake-cead`, deployed from **this** repo's `src/worker.js`) route.
- The router is what actually implements `/deal/:county/:case`, `/r/:code`, `/reels`,
  `/reels/:code`, `/subscribe`, `/support/bot`, county SEO pages, etc. (grep-confirmed in
  `src/worker.js` — none of these exist as Next.js pages in `biddeed-web`). Its own
  `wrangler.toml` already declared `routes = [{ pattern = "biddeed.ai/*", ... }, ...]`,
  unchanged, but Cloudflare only allows one script per route pattern on a zone.
- Once the router's route was deleted and `biddeed-web-production` took over `biddeed.ai/*`
  wholesale, every request to a path the Next.js app doesn't implement (`/deal/...`, `/r/...`,
  `/reels/...`, `/subscribe`, `/support`, `/contact`) landed in that app's Clerk middleware.
  Clerk's `auth.protect()` on an unauthenticated request to a non-public, non-existent route
  produces exactly the observed symptom: 404 with `x-clerk-auth-status: signed-out` and
  `x-clerk-auth-reason: protect-rewrite, session-token-and-uat-missing`.
- Confirmed live before the fix (2026-09-06 14:05 UTC): `curl -sSD-` on
  `/deal/polk/2024ca000341000000` returned those exact headers, `server: cloudflare`, and a
  Next.js-rendered 404 body — i.e. it was hitting `biddeed-web-production` directly, not the
  router.
- The commit's own final smoke-test step (checking `biddeed-web-production`'s workers.dev URL)
  failed on `/` → 404 at 13:55:21 UTC, so the GHA run's overall status was `failure` — but the
  damaging steps (route reconcile + deploy) had already executed and mutated production
  Cloudflare state by then. A red CI run did not prevent the outage.

## What was built

### 1. `breverdbidder/biddeed-web` — commit `3a341f4` (pushed to `main`)
- `wrangler.production.jsonc`: removed the `routes` key from `env.production` — restores the
  pre-regression, documented design ("reachable at its workers.dev URL only").
- `.github/workflows/cloudflare-production.yml`: replaced the "delete every other route" step
  with "Release any zone route claimed by this Worker" — it now only ever deletes routes
  **owned by `biddeed-web-production` itself**, never another script's route. Restored the
  "workers.dev only, no zone route" deploy step name/print message.
- `middleware.ts`: added `/deal(.*)`, `/r(.*)`, `/reels(.*)`, `/subscribe(.*)`, `/support(.*)`,
  `/contact(.*)`, `/api/capture(.*)` to `isPublicRoute` — defense in depth per the issue's
  explicit ask. These paths are still normally served by the router, never proxied to this
  app, but if that ever changes again this fails open to public instead of repeating this
  incident.
- Added a **canonical-domain smoke test** (new step, runs after every production deploy):
  checks `https://biddeed.ai/`, all 3 deal pages named in the issue, `/subscribe` (all want
  200), and `/r/F5oeMD` (wants 302) against the real domain — not just the Worker's
  workers.dev URL. This is the class of check that would have caught 97aa6e1: the workers.dev
  smoke test in that commit's own run could not have detected a zone-routing regression,
  because zone routing only exists on the real domain.

### 2. `breverdbidder/cli-anything-biddeed` (this repo)
- No code change needed — `wrangler.toml` (the router's config) already had the correct
  routes declared and was untouched by the regression. Triggered `deploy-worker.yml` via
  `workflow_dispatch` (no commit) to force Cloudflare to re-sync those routes once
  `biddeed-web-production` released its claim — sequencing required because Cloudflare
  Workers Routes are one-script-per-pattern; deploying the router first would have failed
  with a route conflict.

## Residual / out of scope
- The brief additional outage window between run `34038224704` (route released) and
  `34038347520` (router reclaimed it) was unavoidable given Cloudflare's one-script-per-route-
  pattern constraint — releasing before reclaiming is the only order that doesn't hit a route
  conflict. Total real-world exposure: 97aa6e1 (13:53 UTC) to router redeploy completion
  (~14:11 UTC), ~18 minutes, matching the issue's own observed window.
- `docs/spec/19813.md` / `docs/spec/19820.md` (referenced by comments in
  `cloudflare-production.yml`) describe the intended Vercel→Cloudflare strangler migration for
  biddeed-web; this fix does not change that migration's direction, only removes the zone-route
  land-grab that broke the router mid-migration.
- Per M2, `multi_county_auctions`, `insights`, and the other protected tables were not touched.
  `winnerdata.biddeed_reels` is not on that list (confirmed against the M2 text) and the issue
  explicitly asked for this exact write.
