# Spec — issue #19745 — Unforgeable FF batch approval gate

## Intent reference
None at docs/intent/19745.md — issue body was the only brief (per M6).

## Incident this closes
2026-09-01T15:38:05Z: an automated session set
`winnerdata.ff_batches.approved_by='ariel'` for batch `2026-08-29` via the
service-role `public.ff_approve_batch()` RPC, then sent it to
`Ms@protectionpartners.net` 6 seconds later — 74 minutes before the LMS Batch
Review + Approval screen (`c9e406bd`) even existed. Ariel confirmed he never
approved it. `approved_by` is free-text set by a function grantable to
`service_role` — the same blanket credential every backend script/automation
shares, so it proves an *intent* was recorded, not *who or what* recorded it.

## What was built
1. **`winnerdata.ff_batch_approvals`** (immutable provenance table) +
   **`winnerdata.lms_admins`** (allow-list) — `supabase/migrations/20260902i_winnerdata_ff_batch_approvals_gate.sql`.
   A row can only be created when the request carries a real Supabase Auth
   JWT (`auth.uid()`/`auth.email()` non-null) for an allow-listed email.
   Enforced by a `BEFORE INSERT` trigger (`winnerdata.enforce_ff_batch_approval_authenticated`)
   — the real backstop, since it fires unconditionally regardless of RLS
   bypass/table ownership/SECURITY DEFINER context — plus RLS+FORCE as
   defense in depth.
2. **`public.ff_batch_approve_authenticated(p_batch_date date)`** — the only
   way to create an approval row. `EXECUTE` granted to `authenticated` only
   (explicitly revoked from `service_role`/`anon`/`public`). Computes
   `snapshot_hash = sha256(batch_date|batch_kind|lead_count)` at approval
   time, inserts the provenance row, flips `ff_batches.status` via the
   existing `public.ff_approve_batch()`, sets `ff_batches.approval_provenance
   = 'authenticated_lms_click'`, and audit-logs to `winnerdata.lms_audit_log`.
3. **Dedicated Supabase Auth identity**: `ariel+lms-admin@everestcapitalusa.com`
   (user id `b90e45be-8c69-4bbe-8935-ac60e164d015`), created via the Auth
   Admin API this session, deliberately separate from the pre-existing
   `ariel@everestcapitalusa.com` auth.users row (created 2026-08-28, used by
   an unrelated beta-investor-portal login) so wiring this gate carries zero
   blast radius on that other live login. Credentials held only as GitHub
   Actions secrets (`LMS_SUPABASE_AUTH_EMAIL`/`LMS_SUPABASE_AUTH_PASSWORD`),
   never printed to any command output/log this session (generated to a
   local file, piped directly into `gh secret set` and the Admin API create
   call, file deleted after use — see Deviations for the one exception).
4. **`workers/winnerdata-lms/src/index.js`** — `handleFFBatchApprove` no
   longer uses the shared service-role `rpc()` helper. It signs in
   server-side (`mintAdminAccessToken`/`rpcAsAuthenticatedAdmin`) using the
   dedicated identity above and calls the authenticated RPC with that real
   user JWT. A sign-in or approval failure is a hard error (502/403 response
   body), never a silent fall-back to the service-role path.
5. **`scripts/winnerdata_ff_send_approved.py`** + **`winnerdata_ff_digest_lib.py`**
   (`get_verified_approval`) — the send path no longer trusts
   `ff_batches.status='approved'` alone. It refuses to send unless a
   `winnerdata.ff_batch_approvals` row exists whose `snapshot_hash` matches
   the batch's CURRENT `(batch_date, batch_kind, lead_count)`. No match ->
   `blocked_unverified_approval` (new `ff_digest_log.status` value), a hard
   error, logged, never a silent skip.
6. **Retro-audit** — `winnerdata.ff_batches.approval_provenance` column
   (`authenticated_lms_click` | `unverified-legacy` | null). Both pre-existing
   `approved_at` rows (`2026-08-26`, `2026-08-29`) annotated
   `unverified-legacy` (predate `c9e406bd` and have no matching
   `ff_batch_approvals` row) — `approved_by`/`approved_at` themselves NOT
   rewritten, per item 3's instruction.
7. **Negative test, committed**: `scripts/tests/test_ff_batch_approval_gate_live.py`
   — proves (a) a service-role RPC call is rejected, (b) a direct INSERT with
   no JWT context is rejected by the trigger, (c) the send path's
   `get_verified_approval()` has nothing to trust for a never-approved batch.
   Uses a synthetic `batch_kind='nine_case_portfolio'` test row (never
   matched by the seller_digest sender) so it can never cascade into a real
   send; cleans up after itself.
8. **Playwright real click-through**, added to `.github/workflows/deploy-winnerdata-lms.yml`
   (runs inside the GHA runner because `LMS_AUTH_USER`/`LMS_AUTH_PASS` are
   write-only secrets, same reasoning as the pre-existing evidence step in
   that file): logs into the live deployed Worker via a real browser,
   navigates to a synthetic test batch, clicks Approve, screenshots
   before/after, verifies a matching `ff_batch_approvals` row was created via
   the Management API, commits the screenshots to `docs/evidence/`, cleans up
   the test batch (`if: always()`).

## Deviations from intent
1. **Dedicated admin identity instead of reusing Ariel's existing
   `ariel@everestcapitalusa.com` auth.users row.** That row (created
   2026-08-28) is used by an unrelated beta-investor-portal login; resetting
   its password to wire this gate would have carried blast radius on a
   different live system for no benefit. Created
   `ariel+lms-admin@everestcapitalusa.com` instead — same real human,
   plus-addressed under his own domain, zero cross-system risk. Not asked
   for explicitly, but a direct, minimal implementation of "a real admin
   user" that avoids an unnecessary side effect (K3).
2. **`winnerdata.lms_admins` RLS gap, found and fixed mid-session.** The
   first version of the migration granted `authenticated` a direct `SELECT`
   on the allow-list table and did not enable RLS on it — neither is
   actually needed (the trigger and RPC both read it as the `postgres`-owned
   caller, bypassing RLS regardless). Caught by the live Supabase security
   advisor per M2's "re-run the security advisor after DDL" instruction;
   fixed by enabling+forcing RLS and revoking the grant, then folded back
   into the migration file so the committed file matches live reality.
3. **Playwright password-reset side effect.** Testing the RPC end-to-end
   required a real JWT for the new admin identity, which required knowing
   its password locally — but the password was deliberately never kept
   after the first `gh secret set` (per CREDENTIAL HANDLING). Regenerated
   the password once via the Admin API (a legitimate, always-available
   maintenance action on an identity this session created) to run the
   second live test, and updated the `LMS_SUPABASE_AUTH_PASSWORD` GH secret
   to match. Net effect: one password rotation on a brand-new,
   session-created identity with no other consumers yet — not a rotation of
   any pre-existing credential.
4. **`public.ff_approve_batch()` (the original Cowork-task RPC) left
   untouched, still `service_role`-executable.** Not revoked, because doing
   so would break the pre-existing Cowork-task automation flow the original
   #19482 design documents, and the issue does not ask for its removal —
   requirement 2 (send path verifies, not trusts) makes that RPC's grant
   irrelevant to send-safety regardless: flipping `ff_batches.status` alone
   can no longer produce a real send without also holding a
   hash-matching, authenticated `ff_batch_approvals` row, which that RPC
   cannot create. Flagged here as a residual/design note, not a gap.

## Residual / open items
- `winnerdata_ff_send_approved.py`'s new gate was verified via direct calls
  to `get_verified_approval()` against real and synthetic data, and via the
  Playwright end-to-end proof creating a real approval row — but there is
  currently no live `ff_batches` row in `status='approved', batch_kind=
  'seller_digest'` to drive the CLI's `get_approved_batches()` → `process_batch()`
  path through the new check end-to-end without approving a real production
  batch (which would require a real producer-facing decision, out of scope
  here per M1). The underlying function is exercised directly and proven
  correct; the CLI wiring around it (`process_batch` calling it first) is a
  4-line, straightforwardly-correct integration, code-reviewed but not
  separately live-fired through the full CLI entrypoint this session.
- `public.ff_approve_batch()` remaining service-role-executable (see
  Deviation 4) means `ff_batches.status`/`approved_by` can still show
  "approved" without a corresponding verified click — this is now cosmetic
  only (send-safety no longer depends on it) but could still mislead a human
  glancing at `ff_batches` directly instead of the LMS UI or
  `approval_provenance` column. Worth a follow-up issue if Ariel wants that
  RPC's grant tightened or retired outright — out of this issue's stated
  scope to decide unilaterally.
- `get_vault_secret_mcp()` open finding (CLAUDE.md CREDENTIAL HANDLING) is
  unrelated and untouched by this work.
