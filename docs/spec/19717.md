## Negative test result

  (`aws-0-us-west-2.pooler.supabase.com:6543`, `:5432`, `db.mocerqjnksmhcjzxrewo.supabase.co:5432`)
  — `password authentication failed for user "postgres"` on all three, matching the
  already-documented 2026-07-19 finding. Not re-diagnosed further per standing instruction;
  routed around via Management API (`/v1/projects/{ref}/database/query`, works) and Edge
  Function-internal `SUPABASE_DB_URL` (auto-injected, works — this is how the actual
  migration+backfill ran).
- **Ran the brief's literal DoD query verbatim**: `select count(*) from stripe.charges where
  created >= '2026-01-01'` → errors `22P02: invalid input syntax for type bigint: "2026-01-01"`.
  `stripe.*` tables store `created` as `bigint` (Unix epoch), not `timestamptz` — this is how
  `@stripe/sync-engine` models every Stripe object (matches Stripe's own API representation).
  Corrected query used everywhere in this doc: `created >= 1767225600` (2026-01-01T00:00:00Z).
  Logged per CC_META_PROMPT §2.3 (brief's own verification query can be wrong) rather than
  silently substituting and reporting green.
- **Confirmed `stripe-webhook` and `biddeed-checkout` unmodified**: both still `ACTIVE`,
  fetched via Management API before touching anything and again at the end — identical.
- **Confirmed the restricted key was never widened**: no Stripe dashboard permission calls were
  made (there is no API to do that anyway — it's dashboard-only, which is exactly why it's
  Ariel-only per CREDENTIAL HANDLING "never rotate a credential yourself").

## Deviations from intent
1. **Did not run the brief's literal preferred-path CLI command.** `npx stripe-experiment-sync
   supabase install --token ... --project ... --stripe-key ...` (package now published as
   `@stripe/sync-engine`, confirmed current per `npm view`) internally hardcodes
   `deployFunction("stripe-webhook", ...)` / `deployFunction("stripe-worker", ...)` and a
   webhook-registration URL of `${SUPABASE_URL}/functions/v1/stripe-webhook` — all three collide
   exactly with the live `stripe-webhook` function that runs `biddeed-checkout`'s payment flow,
   which the brief explicitly forbids touching. There is no CLI flag or config option to rename
   the deployed function slugs. Verified this by extracting and reading the CLI's actual
   `SupabaseSetupClient.install()` source (not guessing from docs). **Fix applied**: reused the
   exact same official function source (`setupFunctionCode`/`webhookFunctionCode`/
   `workerFunctionCode`, imported from the published package, zero hand-written Deno logic)
   but deployed under `stripe-sync-*` slugs, with the 5 hardcoded slug references inside the
   setup function's own source patched to match. This is the "library path" fallback the brief
   itself names ("deploy the webhook handler as a Supabase Edge Function... register the webhook
   endpoint... via API") adapted for the actual collision found, not invented from scratch.
2. **`SUPABASE_DB_PASSWORD` / direct psql confirmed dead** (see Negative test result) — routed
   entirely through the Management API + Edge-Function-internal `SUPABASE_DB_URL`, per the
   dispatch prompt's explicit pre-authorization to do so.
3. **`STRIPE_SECRET_KEY` GHA env var was present but empty** (`length 0`, not unset) — first
   `stripe-sync-setup` invocation failed with the Stripe SDK's own "Neither apiKey nor
   config.authenticator provided". Fetched the real key from `vault.stripe_secret_key` via the
   sanctioned `public.vault_secret()` RPC (service-role gated, not the retired
   `vault.decrypted_secrets` direct-SELECT pattern) and set it as the Edge Function project
   secret instead. Never printed the value; only length/prefix (`rk_live`) logged for diagnosis,
   which Stripe's own error messages also echo unredacted-prefix by default.
4. **The vault `stripe_secret_key` is NOT "full-access"** as the brief's Decision section
   assumed — it's a restricted key (`rk_live_...ossE`) missing at minimum: `connected_account_read`
   (worked around via `stripeAccountId` config, see below), `balance_read`, `payout_read`,
   `dispute_read`, `webhook_read`, `webhook_write`. Everything else tested (customers, charges,
   payment_intents, invoices, subscriptions, refunds, products, prices, plans, coupons,
   checkout_sessions, setup_intents, payment_methods, tax_ids, credit_notes,
   early_fraud_warnings list/read) works. This is a factual correction to the brief, not a
   guess — every missing scope was independently reproduced with a direct, unauthenticated-by-me
   `curl` to the real Stripe endpoint, and Stripe's own error text names the exact missing
   permission each time.
5. **Bypassed `stripe.accounts.retrieve()` via `stripeAccountId` config** (officially-supported
   field in `StripeSyncConfig`, not a workaround of application logic — just supplying data the
   library says it will otherwise fetch from the API). Avoided needing `connected_account_read`
   entirely, since the account ID was already known from the brief (`acct_1LPHtNKaSTwZgYdf`).
6. **Did not enable Stripe Sigma** to get `payouts`/`balance_transactions`. Sigma is a distinct,
   metered Stripe product (`stripe.rawRequest("POST", "/v1/sigma/query_runs", ...)`) — enabling
   it would be a cost/scope decision beyond "install the sync engine," and the key still lacks
   the read scopes those objects need regardless of Sigma.
7. **Did not set up `pg_cron`/`pgmq` continuous polling.** The brief's own scope line allows
   "otherwise `backfill` command per object" as the fallback when CLI-cron install isn't used.
   This session instead invoked `stripe-sync-worker` synchronously in a loop (17 invocations)
   until every unblocked object's `_sync_obj_runs` rows reached `status='complete'`. No
   recurring schedule exists yet — one-time backfill only, matching the fallback language.
