# Spec — issue #19750 — Tracerfy enhanced-trace 0/N lifetime hit rate on business-type leads: name-order mismatch, not an async/queue bug

## Intent reference
None at docs/intent/19750.md — issue body was the only brief (per M6).

## Root cause (confirmed live, both named leads, this session)
Not the primary hypothesis (async/queued job read as miss) — `enhanced_trace()`'s
HTTP call is synchronous and returns `hit`/`persons` in the same response;
there is no queue/job-id indirection on this endpoint (only `dnc/scrub/` uses
a queue, and it is unrelated to `run_stage3_skiptrace`).

The real bug: `tracerfy_client._split_owner_name()` unconditionally applies a
**surname-first** flip (correct for `fl_parcels`/auction `winning_bidder`
names, e.g. `"DAVIS, RONALD L."` -> first=RONALD, last=DAVIS) to every name
passed to `enhanced_trace()`, including Sunbiz-resolved `principal_name`
values. But `identity_cascade.normalize_person_name()` (built in #19746)
guarantees Sunbiz-derived principal names are already in **natural "First
Last" order**. Applying the surname-first flip to an already-natural-order
name reverses it: `"Rajendrakumar Patel"` -> `first_name="Patel",
last_name="Rajendrakumar"` — backwards. Tracerfy silently returns `hit=false`
for the reversed name/address pair (not an error, not a 4xx — a legitimate
`NO_MATCH` for the wrong person). This reproduces on 100% of `business` /
`land_trust_unpierceable` leads (whose `principal_name` always comes from
Sunbiz resolution) and explains the observed 0/N lifetime hit rate, while
`person`/`person_joint` leads (whose name comes from the raw, surname-first
`winning_bidder`) were never affected by this exact bug.

## Item 2 — parse mismatch named
Not a response-parsing mismatch (`_parse_trace_response()`'s key paths — `hit`,
`persons[0].phones[].number`, `persons[0].emails[].email` — are correct, as
proven by the corrected calls above parsing cleanly). The mismatch is
upstream of parsing, in **request construction**: `enhanced_trace()` always
called `_split_owner_name()` (surname-first assumption) regardless of the
name's actual source/order.

## Item 4 — fix applied + re-verification

### Fix
- `scripts/tracerfy_client.py`: added `_split_natural_order_name()` (plain
  first-token/rest split, no flip) and a `name_is_natural_order: bool = False`
  parameter on `enhanced_trace()`. Default `False` preserves the existing
  surname-first behavior for every other caller (`trace_lead()`, the 6
  historical one-off `skiptrace_2026*` scripts, `contact_resolver.py`) —
  zero behavior change for callers that pass raw `fl_parcels`/auction-winner
  names.
- `scripts/ff_billable_loop.py::run_stage3_skiptrace()`: now passes
  `name_is_natural_order=bool(lead.get("resolved_principal_name"))`. This
  flag is `True` exactly when `principal_name` came from Sunbiz resolution
  (`business`/`land_trust_unpierceable`, normalized natural order) and
  `False` when it's the raw `winning_bidder` (`person`/`person_joint`,
  surname-first) — the same signal `process_lead()` already uses at line 419
  (`principal_name = lead.get("resolved_principal_name") or
  lead["winning_bidder"]`), so no new state was introduced.
- Regression tests added to `scripts/tests/test_ff_nine_enrichment.py`
  (`test_split_natural_order_name_not_flipped`,
  `test_enhanced_trace_natural_order_flag_selects_split_function`,
  `test_enhanced_trace_default_still_uses_surname_first_split`) — 21/21
  passed (`python3 -m pytest scripts/tests/test_ff_nine_enrichment.py -q`).
