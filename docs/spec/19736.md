## Deviations from intent
1. **Storage bucket, not R2** — carried over from the prior session's own documented deviation
   (no R2 bucket/credentials exist anywhere in this org, live-verified before that session built
   this). Reconfirmed live this session (`GET /storage/v1/bucket/biddeed-reels` → `200`), not
   re-litigated.
2. **Gemini key priority reordered from the directive's literal phrasing.** Ariel's comment says
   "vault: `gemini_api_key` / `gemini_api_key_biddeed`". Live-tested both this session:
   `gemini_api_key` (== the existing `GEMINI_API_KEY` GH secret, confirmed by matching key
   prefix) returns `429 RESOURCE_EXHAUSTED` — **"Your prepayment credits are depleted"** — a
   permanent billing exhaustion, not a transient limit. `gemini_api_key_biddeed` returns real
   vision output. `gemini_api_key_biddeed` is tried first; `gemini_api_key` stays in the
   fallback chain only in case its billing gets topped up later. This is a materially different
   ordering than the directive's literal list order, done because the literal order doesn't
   work at all right now — logged here rather than silently reordered without comment.
3. **`gemini_api_key_biddeed` hit the Gemini free tier's own request-rate quota repeatedly
   during this session.** Exact error observed: `429 RESOURCE_EXHAUSTED`, `"Quota exceeded for
   metric: generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20,
   model: gemini-2.5-flash"`, with a server-suggested `"Please retry in Ns"` (values seen: 58s).
   This reads as a genuine per-minute free-tier cap (the retry hint is seconds, not hours), and
   this session's own repeated manual smoke-testing (needed to distinguish this from the
   billing-exhaustion case above) consumed a meaningful share of that window before the real T9
   run started. `score_condition()` now retries the same key up to twice with the server's
   suggested backoff before falling through — implemented and live-verified to fire correctly,
   but the underlying quota is a real external constraint this session cannot lift. See T9
   results for how many rows this affected in practice.
4. **A distinct, more serious bug found and fixed live: Gemini's extended-thinking tokens were
   silently truncating the JSON response.** First real-row test (case `01 2025 CA 003415`,
   alachua) failed with `Unterminated string starting at: line 15 column 5 (char 600)` — not a
   quota error. Root cause, confirmed via a standalone diagnostic call: `gemini-2.5-flash`
   defaults to extended thinking mode, and a trivial 1x1 test image alone produced
   `thoughtsTokenCount: 657` against a `maxOutputTokens: 1024` cap, leaving no budget for the
   actual JSON answer. Fixed by setting `generationConfig.thinkingConfig.thinkingBudget: 0` and
   raising `maxOutputTokens` to 2048. This is a correctness bug that would have intermittently
   broken every row regardless of quota, not just the 4 geocode-fallback rows — worth flagging
   as a Finding for any other pipeline in this repo that calls `gemini-2.5-flash` vision/JSON
   endpoints the same way.
