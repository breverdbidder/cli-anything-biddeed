### Root cause for pasco's false certification

`gold_standard_certify()` (current live definition:
`migrations/20260720_architect_triage_12866_certify_tiebreak_fix.sql` —
confirmed the latest `CREATE OR REPLACE` for this function, no later
migration redefines it) requires, beyond 10/10 PASS on the latest
`gold_standard_county_status` run:

```sql
latest_audit AS (
  SELECT DISTINCT ON (county_slug, letter) county_slug, letter, survived
  FROM gold_standard_ultraloop_audit
  WHERE created_at > now() - interval '7 days'
  ORDER BY county_slug, letter, created_at DESC, survived ASC, id DESC
)
```

survived=true evidence for **all 10 letters within a rolling 7-day window**.
Checked the freshest survived=true row per letter for pasco (live query,
2026-09-03T22:28Z): 9 of 10 letters fresh. Letter **B**'s freshest row
(id=18687) was created `2026-08-27T13:28:14Z` — about **9 hours** before the
7-day cutoff relative to this session's clock. It aged out sometime between
the 19:30Z automated certify run and this session. Precert guards
(`calendar_parity`, `denominator_integrity`) were both fresh (2026-09-01),
so they were not the blocker.

This is the **identical bug class** documented in
`supabase/migrations/20260815_architect_triage_19073_pasco_citrus_certify_freshness_refresh.sql`
(issue #19073, 19 days earlier, also pasco) — evidence for an
already-passing letter simply outlives the 7-day window because nothing
re-touches it on a tighter cadence. It is a false-revocation mechanic, not
a data defect.

## Why gold_standard_loop()/gold_standard_certify() were NOT run this session

Fixing the evidence row alone does not flip `certified=true` — certify()'s
idempotency guard (`WHERE c.last_verified_run IS DISTINCT FROM v_run`,
from `20260710_architect_triage_11368_certify_idempotency_guard.sql`) is a
no-op for pasco until a **new** `loop_run_id` exists. Creating one requires
running `gold_standard_loop()`, which — together with `certify()` — operates
**fleet-wide**, not per-county.

Pre-flight blast-radius check (live query, this session): 15 OTHER counties
(glades, gulf, hernando, hillsborough, monroe, orange, palm_beach, bay,
desoto, duval, flagler, franklin, sarasota, volusia, hendry) currently sit
at `consecutive_non_gold=2, certified=true` — one non-gold evaluation away
from the N=3 hysteresis revocation threshold
(`20260719g_gtm22h_certify_n3_strikes_reason_log.sql`). Forcing an
out-of-band loop+certify cycle under this issue's narrow 3-county mandate
risks revoking any of those 15 unrelated, currently-certified counties
(plausibly for the identical stale-evidence bug class — unverified for any
of them, and out of scope to check 15 additional counties under a
3-county-shard triage). Issue #19807's own PARALLEL-FLEET RULES explicitly
instruct against running the loop mid-session when other shards may be
mid-flight, precisely to avoid this class of collateral damage. Even in the
best case, forcing one cycle now only advances pasco's `consecutive_gold`
0→1 (not to certified, which needs ≥2 consecutive gold runs) — an
asymmetric risk/reward that does not justify the blast radius.

Cross-referenced `.github/workflows/*.yml`: essentially every shard's
session runs `gold_standard_loop()`+`certify()` at its own close-out, so
this fix is very likely to be picked up naturally within hours by another
concurrently-running shard session, without a second architect dispatch.
