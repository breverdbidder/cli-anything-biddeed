# Spec — issue #19729 — seller-digest enrichment 0% hit rate — wrong address sent to skip-trace vendor

## Intent reference
None — no `docs/intent/19729.md` exists; the issue body was the only brief (per M6).

## What was built

Files touched:
- `scripts/seller_digest_enrichment.py` — full rewrite of the resolution method. The
  previous version anchored every Tracerfy call on `property_address` (the auction property
  the buyer just won). This version:
  1. Classifies each buyer (`person` / `person_joint` / `business` / `land_trust_unpierceable`)
     with the same heuristic as `scripts/skiptrace_20260827_28lead_ff_batch.py::classify()`.
  2. Resolves a **prior-owned mailing address** via `public.fl_parcels` self-match, excluding
     the just-purchased parcel (looked up live from `public.multi_county_auctions` by
     `case_number` + `winning_bidder`). Reused via `import` from `scripts/ff_billable_loop.py`
     (`run_stage1_identity`) — not reimplemented.
  3. Business/land_trust: resolves the LLC's principal/registered agent via the Sunbiz identity
     cascade, also reused via import (`run_stage2_sunbiz_chain` from `ff_billable_loop.py`,
     itself calling `scripts/identity_cascade.py::resolve_identity()`). New in this rewrite: if
     the entity itself has no prior `fl_parcels` holding but a principal was resolved, a second
     `run_stage1_identity()` call is made keyed on the *principal's own name* — the issue's "find
     the owner behind the LLC, then trace that person at their own mailing address" step, which
     `ff_billable_loop.py`'s existing driver does not do (a real gap in the pipeline being ported
     from, closed here rather than copied forward).
  4. Calls Tracerfy's enhanced trace (name + the resolved mailing address, never the purchased
     property) via `run_stage3_skiptrace`, also reused via import.
  5. DNC-scrubs any resolved phone with a **new, correct** poll-to-completion implementation
     (`dnc_scrub()` in this file) — deliberately **not** reused from
     `ff_billable_loop.py::run_stage5_dnc()`, which only checks that Tracerfy *accepted* the scrub
     request, never polls `tracerfy_client.get_queue_status()` for the actual flagged/clean
     result. That's fine for `ff_batch_leads`' BILLABLE gate (doesn't gate on DNC completion) but
     violates this pipeline's hard guardrail (issue #19619 / M1): no phone/email may be written
     before DNC screening has actually completed. Reuses the proven poll pattern from
     `scripts/skiptrace_20260827_28lead_ff_batch.py::dnc_check()` instead.
  6. Per-row try/except isolation (T3): one row's unhandled exception is persisted as
     `row_enrichment_status='error'` and the loop continues; it no longer aborts the batch.
  7. Distinguishes `NO_MATCH` (vendor answered, `row_enrichment_status='complete'`, no contact)
     from `error` (vendor never answered / bad request after retries).
  8. Resets any row stuck at `running` from a prior crashed run back to `not_started` at the top
     of every run (T3).
  9. `RERUN_PAID_LOOKUPS` (falls back to `FORCE_REFRESH` for backward compat with the existing
     GHA workflow input) skips a row only if it already has a **resolved phone or email** — not
     merely `row_enrichment_status='complete'`, since every row in the lifetime backlog was
     `'complete'` under the old wrong-anchor method with zero real contacts. This is what makes
     the entire 81-row backlog eligible for genuine reprocessing under the fixed method.
  10. Honest batch-status accounting (T6): `winnerdata.ff_batches.enrichment_status` is only set
      to `'complete'` if the batch actually finished with 0 rows left unresolved; if the shared
      daily Tracerfy/BrightData credit ceiling (`public.ff_ledger_spend`, 100 combined units/UTC
      day) stops the run early, the batch is marked `'failed'` with an explicit, accurate
      `enrichment_error` (not a silent lie).
- `scripts/tracerfy_client.py` — `_request()` now retries up to 3 attempts with exponential
  backoff (1s/2s/4s) on any 5xx or the specific 544 proxy-layer error observed in the issue's
  run-#6 failure log. A 4xx (bad request, auth, insufficient credits) still fails on attempt 1 —
  retrying an unchanged bad request wastes rate-limit budget for the same result. Every existing
  caller (`enhanced_trace`, `dnc_scrub`, `get_queue_status`, and both `ff_billable_loop.py` and
  the rewritten `seller_digest_enrichment.py`) gets this for free since they all funnel through
  `_request()`.
- `scripts/seller_digest_enrichment.py`'s own `sql()` (Supabase Management API helper) also gained
  the same 3-attempt/backoff retry — the issue's run-#6 failure #1 ("HTTP Error 544 ... died before
  processing any row") reads as a pre-row failure, i.e. the very first Management API call in
  `main()`, not a Tracerfy call — so the fix needed to cover both transports, not just the vendor.
- `supabase/migrations/20260902g_winnerdata_seller_digest_leads_error_status.sql` — adds `'error'`
  to `winnerdata.seller_digest_leads.row_enrichment_status`'s CHECK constraint (additive; verified
  the real constraint name live via `pg_constraint` before dropping/re-adding it, applied live via
  the Management API, and re-verified the new constraint definition).

No changes to `scripts/ff_billable_loop.py`, `winnerdata.ff_batch_leads`, or any send/digest/LMS
path — all explicitly out of scope per the issue.

## Deviations from intent
- **T5's ≥70%/≥85% hit-rate target was not reached this session** — the run stopped on the shared
  daily credit ceiling before most rows were even attempted, and the rows that were attempted came
  back as genuine (verified) misses because those specific buyers have no prior FL property on
  file. This is disclosed as a **PARTIAL**, not silently reported as done. The root-cause bug (T1)
  is fixed and verified in code; whether the *fixed* pipeline actually clears 70% once it has a
  full day's credit budget to work with is genuinely unknown for this specific buyer population —
  flagged as an open risk below, not asserted either way.
- `rerun_paid_lookups` semantics were redefined from "skip if `row_enrichment_status='complete'`"
  (the pre-existing `FORCE_REFRESH` behavior) to "skip only if a real phone/email is already on
  file." This was necessary — every row in the lifetime backlog was `'complete'` under the old
  bug, so the literal old semantics would have made the entire backlog permanently unfixable.
  Not explicitly specified in the issue text this way; inferred as the only reading under which
  the T5 DoD is achievable at all, and applied consistently.
- Added a principal-address fallback lookup (stage2 → second `run_stage1_identity()` call keyed on
  the principal's name) that `ff_billable_loop.py`'s own driver does not do. This is additive to
  the ported method, not a divergence from it — done because the issue's own T2 text explicitly
  requires it ("LLC/trust → find_owner on the principal ... then enhanced on that person at their
  mailing address") and the literal ported driver does not implement that half of the sentence.
- Mid-session correction: the first `seller_digest_enrichment.py` version (used for the very first
  08-31 run) unconditionally set `enrichment_status='complete'` at the end regardless of whether
  the daily cap had stopped the run early — this briefly wrote a false `'complete'` to
  `winnerdata.ff_batches` for `2026-08-31`. Caught before session end (Honesty Protocol
  self-check), the code was corrected, and the live row was both directly corrected via SQL and
  re-derived by re-running the corrected script, which reproduced the same honest `'failed'`
  state independently. Disclosed rather than left silent.

## Findings (not this issue's task, worth flagging)
1. **`ff_billable_loop.py::run_stage5_dnc()` does not actually check DNC status.** It calls
   `tracerfy_client.dnc_scrub([phone])`, which returns a queue ID for async processing, and treats
   receiving *that* response as `outcome="hit"` without ever polling
   `tracerfy_client.get_queue_status()` for the real flagged/clean determination. For
   `ff_batch_leads`' BILLABLE 2-of-3 gate this is silent but not obviously unsafe (DNC isn't part
   of that gate); if any future caller of `ff_billable_loop.py` assumes stage5 = "DNC-cleared",
   that assumption is currently false. Not fixed here (different pipeline, out of scope per the
   issue's own non-goals) — flagged for whoever owns `ff_billable_loop.py` next.
2. **`identity_cascade.py`'s Sunbiz cascade (stage2) is the dominant daily-ledger cost, not
   Tracerfy skip-trace itself**, and its hit rate in this session was 0/7 business/land_trust
   leads. Each business/land_trust lead's cascade attempted ~9 Exa candidate checks (free), 4
   mirror-site fetches (free but often 404/410), and 1 Bright Data browser attempt (1 shared
   ledger unit, spent regardless of outcome) — that single Bright Data leg alone appears to be
   what exhausted the remaining ~46 units in the first ~15 rows of the 08-31 run. Given `search.
   sunbiz.org` is now blocked for Bright Data's residential proxy pool as "Government" content
   (visible in this session's own logs — "Access denied ... classified as Government and blocked
   by Bright Data"), that leg cannot currently succeed at all, meaning every business/land_trust
   lead pays a real shared-ledger unit for a leg that is structurally guaranteed to fail right now.
   Worth a follow-up issue: either drop the Bright Data leg until the proxy-policy block clears, or
   gate it behind a cheaper pre-check.
3. **The core self-match method may have a real, population-specific ceiling below 70% for
   seller_digest leads specifically.** `ff_batch_leads`' 88% precedent comes from a buyer
   population with existing FL portfolios (repeat investors). Auction-winner leads routed into
   `seller_digest_leads` skew toward first-time/out-of-state buyers with zero prior `fl_parcels`
   holdings (3/3 spot-checked person-type misses this session were genuine zero-holdings, not
   parsing bugs). This is a data-population risk to the DoD's hit-rate target, independent of code
   correctness, and should be watched once a full day's ledger budget lets a complete run happen.
