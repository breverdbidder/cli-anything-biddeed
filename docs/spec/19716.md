## What was built
- `supabase/migrations/20260902_finance_ledger_v1.sql` — applied live to
  `mocerqjnksmhcjzxrewo` via Management API (`mgmt_sql.py`, the documented
  fallback since `SUPABASE_DB_PASSWORD` direct psql is a known-stale path).
  Creates 8 tables in `finance.*`: `accounts`, `journal_entries`, `postings`,
  `bank_connections`, `bank_accounts`, `bank_transactions`, `recon_matches`,
  `recon_exceptions`. All exactly match the column list in the issue body.
  RLS enabled + `cfo_agent_ro_select` policy (`USING (true)`) on every new
  table, matching the existing pattern on `revenue_ledger`/`expense_ledger`/
  `invoices` and the fix documented in checkpoint `cfo_agent_api_auth_fix_19688`
  (bug 3 of that fix: RLS-enabled-with-zero-policies silently returns
  200-empty via PostgREST). `finance` schema was already in
  `authenticator`'s `pgrst.db_schemas` from that same fix — no change needed
  there.
- `finance.assert_balanced()` — SQL function, returns entries where
  `SUM(debit_cents) <> SUM(credit_cents)`.
- `finance.check_posting_balance()` + `trg_postings_balance` — deferrable
  constraint trigger (`INITIALLY DEFERRED`) on `finance.postings`, fires at
  commit so a debit+credit pair inserted in the same transaction is fully
  visible when checked.
- Standard chart of accounts (11 accounts x 5 entities = 55 rows) seeded into
  `finance.accounts`, driven from a `cross join` against live
  `finance.entities` (not hardcoded per-entity), so a 6th entity added later
  gets the same chart automatically on the next run of that block.
- `finance.post_revenue(uuid)` / `finance.post_expense(uuid)` — posting
  rules per the issue's DR/CR spec, idempotent via a unique index on
  `journal_entries(ref_table, ref_id)`, litigation-gated via
  `finance._litigation_gated(entity_code)` (see Deviations).
- Backfill `DO` block: ran every existing `revenue_ledger`/`expense_ledger`
  row through the posting functions.
- Two rows inserted into `finance.cfo_checkpoints` (CP2, CP5, both
  `status='verified'`) and one row into `public.agent_ops_log`
  (`dispatch_id='19716'`, `status='VERIFIED'`).

## Negative test result
Attempted to commit a single unbalanced posting (`debit_cents=100`, no
matching credit) inside one transaction against `finance.postings`. The
deferred constraint trigger fired at commit time and raised `P0001`,
rejecting the whole transaction. Re-checked `journal_entries` for the test's
memo string afterward: 0 rows. Re-ran `finance.assert_balanced()`: still 0
rows, confirming no partial state survived.

## Deviations from intent
1. **`EVEREST_CFO_V1_META_PROMPT.md` does not exist in this repo.** Followed
   `CC_META_PROMPT.md` (which does exist and is referenced identically) plus
   the issue body verbatim instead. Not blocking — the issue body's CP2/CP5
   section was fully self-contained.
2. **Backfill did not post the 13 `revenue_ledger` rows as revenue.** All 13
   are `status='void'`, voided 2026-09-01 per issue #19659 because the
   source `billable_ff_events` rows lacked a confirmed real send (predate
   the confirmed-send billing standard — this is the same M1-class guardrail
   this dispatch's standing mandates enforce). Posting void rows as CR
   4100 Revenue would create $117.00 of phantom revenue for FF sends that
   never actually happened, which is a worse outcome than a literal reading
   of "post ALL existing revenue_ledger (13 rows)". `finance.post_revenue()`
   was still called on all 13 rows during backfill (satisfying "post ALL"
   as "run the posting function over all rows") but correctly no-ops on
   `status='void'`, returning `NULL` and creating zero journal entries. If
   this judgment call should be reversed (i.e. void revenue should still hit
   the books, perhaps to a suspense/write-off account), that is a one-line
   change to the `if v_row.status = 'void' then return null; end if;` guard
   in `finance.post_revenue` — flagging for Ariel rather than deciding
   unilaterally to fabricate revenue.
3. **Litigation-gated entity code.** The issue says `entity
   everest_capital_brevard (or whatever the exact code is — read
   finance.entities)`. Live `finance.entities` has no `everest_capital_brevard`
   row — only `everest_capital` ("Everest Capital USA / Development"), which
   is the entity under litigation per `docs/EVEREST_CFO_AGENT_PLAN.md` §2
   ("Abreu v. Everest Capital of Brevard"). Used `entity_code='everest_capital'`
   as the litigation gate. This is exercised live in the backfill: the
   GitHub expense row (`entity_code='everest_capital'`) posted with
   `posted_at=NULL` (draft) and `finance_ops_log.status='PARTIAL'`.
4. **Expense credit account defaults to 1000 Bank, never 2000 AP.**
   `finance.expense_ledger` has no paid/unpaid column (schema change to
   `expense_ledger` is an explicit non-goal), so there is no live signal to
   distinguish "paid" from "unpaid" expenses. `finance.post_expense()`
   always credits 1000 Bank. Both live rows are routine recurring SaaS costs,
   consistent with "paid."
5. **Expense category → 5xxx account map** was not given literally in the
   issue (it says "DR 5xxx by category map" without listing the map). Built
   one from the two live category values (`saas_subscription`,
   `ai_tts_vendor` → both 5000 Infra & Tooling) plus reasonable guesses for
   `data_vendor` → 5100 and `stripe_fees` → 5200, with `5900 Other Expense`
   as the fallback for anything unmapped. Documented in the migration's
   `finance.post_expense` function body.
6. **`breverdbidder/everest-ledger` reuse check (CP0 instruction).**
   Confirmed the repo exists (`forked from radzserg/lefra`) via `gh repo
   view`. It is a separate TypeScript/Postgres project with its own
   `database/` migrations using different table/schema conventions (not
   `finance.*`). Reviewed at a high level; nothing was directly portable as
   SQL against this project's live `finance.*` naming/FK/RLS conventions, so
   this migration was written fresh against the CP2 spec and the live schema
   instead of copy-pasted.
