## RLS gate outcome explanation (issue's explicit ask)
The issue asks to "explain why #19716's gate failed while live tables show RLS on/anon
none; fix the gate or the tables, whichever is actually wrong." Investigated live:
`gh issue view 19718` (the one and only `rls-gate` labeled issue, closed) shows the gate
failure was **not** on any `finance.*` table from #19716 — it was 29 `stripe.*` tables
(`stripe.customers`, `stripe.charges`, etc.) with `no_rls`, all from **#19717** (Stripe
sync-engine install), caught on GHA run `33598231711`. The issue body's framing
("#19716's gate failed") is itself the thing that needed correcting, per
`CC_META_PROMPT.md` §2.3 ("the DoD query itself may be wrong — don't silently substitute
and report green"). #19717's own session fixed it in the same sitting (added
`cfo_agent_ro_select` RLS policies to all 29 tables), and the gate auto-closed the issue
("RLS gate clean — closing.") minutes later. `finance.*` tables from #19716 had RLS +
`cfo_agent_ro_select` from the moment they were created and never appeared in any gate
failure. **Conclusion: neither the gate nor any table needed a fix this session** — both
were already correct; the only bug was the issue body mis-attributing a #19717 finding to
#19716. Re-ran `rls_gate_check()` 4 times across this session (after every schema change):
`passed=true`, `new_violations=0` every time.

## Deviations from intent
1. **Migration filename**: issue asked for `20260902b_recon_v1.sql`; that name was already
   taken by an unrelated same-day migration (`20260902b_harvest_sale_result_derive_trigger_19720.sql`).
   Used `20260902k_recon_v1.sql` (next free same-day suffix) instead — noted at the top of
   the file itself.
2. **Fixture tagging**: issue asked for rows "clearly tagged `source=fixture`" —
   `finance.bank_transactions`/`bank_connections` have no literal `source` column (schema
   change to those tables was not requested and wasn't necessary). Used
   `bank_connections.status='fixture'` instead, which propagates identically through every
   join the dashboard/recon code uses — functionally equivalent, documented explicitly in
   both the migration and `PORTING_NOTES.md`.
3. **R1/R2 matching algorithm — bug caught and fixed during this session, not shipped
   broken.** A first draft used a naive "amount equal + date within ±3d" match, which
   produced many-to-many matches when two same-amount Stripe payouts landed within the ±3d
   window of each other (caught live: two $24.05 payouts 3 days apart, both bank rows
   qualified for both payouts). Fixed with a mutual-nearest-match (each side's #1 date-
   distance pick must be the other) before this was ever reported as done — see the R1/R2
   `WITH candidates AS (...)` CTEs in the migration.
4. **Second-opinion (reconifyhq/reconify) skipped**, per the issue's own >30-min allowance.
5. **everest-cfo-agent Stripe-integration status text is now stale but was not touched.**
   `agent.ts::getStripeStatus()` still says "No Stripe credentials configured... inert" —
   true when #19646 wrote it, false as of this issue's Part 1 (Stripe is now live-synced).
   Fixing it was outside this issue's Part 3 ask (recon endpoints only); flagged here rather
   than silently expanding scope, per K3 Surgical Changes.

## Findings (not the task, but worth more than the task)
1. **Own mistake, self-caught, logged per Honesty Protocol**: early in this session, a
   `select * from stripe._managed_webhooks` (checking the webhook registration) returned and
   printed the row's `secret` column — the raw `whsec_...` webhook signing secret — to this
   session's own terminal output, before the risk was recognized. No further `select *`
   against that table was run for the rest of the session. This is a real credential-handling
   miss on this session's part (should have selected specific columns from the start); it is
   not remediable by rotating the secret myself (Ariel-only per CREDENTIAL HANDLING). Flagging
   explicitly rather than omitting it — the webhook secret only signs inbound Stripe webhook
   payloads (not an account-wide credential), but it should be rotated by Ariel out of
   caution: Stripe Dashboard → Webhooks → the `we_1UBFnAKaSTwZgYdf1psux4LB` endpoint → "Roll
   secret", then update the `stripe_webhook_secret` vault entry.
2. **Sign-convention risk in #19737's real Plaid data — confirmed suggestive, not proven.**
   The 48 real Plaid-sandbox rows that landed mid-session show a mix of signs (42 positive /
   6 negative) that looks consistent with Plaid's raw convention (positive=money out) being
   stored unmodified, rather than negated to this build's documented convention
   (positive=inflow). Example: a `GUSTO PAY` (payroll, a real-world outflow) row shows
   `amount_cents=585000` (positive) — correct under Plaid's raw convention, backwards under
   this build's. This doesn't corrupt anything today (wrong-signed rows just produce
   exceptions instead of matches — fails safe), but will cause real future matches to be
   silently missed once genuinely-reconcilable transactions land, unless #19737's ingestion
   negates the sign on write. Flagged in `PORTING_NOTES.md` and the CP6 UPDATE checkpoint row
   for whoever owns #19737 next — not fixed here, since #19737 is a separate issue/lane (M5).
3. **#19737 landing real data mid-session is itself a good sign** — the parallel Plaid-engine
   track referenced in this issue's own body is progressing faster than expected. Once it
   exits sandbox and negates the sign convention (finding #2), CP6 will need zero code changes
   to pick up real production bank data — `recon_run()` and both dashboard views are already
   agnostic to fixture vs. real vs. sandbox at the SQL level (only `bank_connections.status`
   differs).
