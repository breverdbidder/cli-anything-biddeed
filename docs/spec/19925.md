# Spec — issue #19925 — C6: Model providers for Deed (Smart Router default, BYOK, Ollama, free tier)

Parent #19829. No `docs/intent/19925.md` exists — issue body is the only brief (per artifact chain, intent > body > comments; comments were empty).

## Scope built this session

All four architecture points from the issue body:
1. Default = BidDeed Smart Router (`claude-router`) — unchanged for anyone who sets nothing.
2. Bring-your-own-key: Settings → Models, `anthropic|openai|deepseek|gemini|openrouter`, encrypted key storage, Worker calls the provider directly, bypassing the Smart Router for that user only.
3. Ollama: base URL + model, `POST {base}/api/chat`, "Ping" test button, no localhost proxying (Worker only ever fetches whatever `base_url` the user typed — no special-casing that would let it reach a Cloudflare-internal address; it's just a public HTTPS fetch).
4. Free tier: new `force_tier: "free"` cascade in `claude-router`, OpenRouter free routes only, hard per-IP daily cap, visible rate-limit note, default for anonymous visitors.

Composer mode selector (Quick/Deep/Voice, C5) was **not** built — it doesn't exist yet in this repo (grepped `src/worker.js` before starting; C5 is a separate, not-yet-built issue) and the C6 issue body only cites it as *decided architecture context*, not something C6 itself must ship. `X-Chat-Provider` is honored as `router|byok|ollama|free`; the Quick/Deep/Voice → tier mapping is C5's job to wire once it exists.

## Deviations from the issue body (material ones only)

**1. Encryption primitive: pgsodium → pgcrypto (live-discovered platform boundary).** The issue names "pgsodium secretbox with a per-row nonce" explicitly. `20260904b` implemented exactly that (`pgsodium.crypto_secretbox`/`crypto_secretbox_noncegen`, keyed via `pgsodium.create_key`). Applying it and immediately live-testing (`biddeed_provider_upsert` via the service_role REST RPC path) hit `42501 permission denied for function crypto_secretbox_noncegen` — confirmed by querying `pg_proc.proacl` directly that those pgsodium functions are executable only by `supabase_admin`/`pgsodium_keyholder`/`pgsodium_keyiduser`/`pgsodium_keymaker`, and this session's `postgres` role (the only role the Management API connection can act as) is not a member of any of them. Confirmed un-fixable from this session: `GRANT pgsodium_keyholder TO postgres` → `42501 permission denied to grant role... Only roles with the ADMIN option may grant this role`. This is the same category of platform boundary CLAUDE.md's CREDENTIAL HANDLING section already documents for `REVOKE SELECT ON vault.decrypted_secrets FROM service_role` (needs dashboard-level `supabase_admin`, not available here) — not something to keep retrying with variations.
   Fix, shipped in `20260904c`: pgcrypto's `pgp_sym_encrypt`/`pgp_sym_decrypt` (confirmed directly callable by `postgres`, no special role) + a single master passphrase generated with `gen_random_bytes(32)` and stored via `vault.create_secret()`, read inside the SECURITY DEFINER functions through the **already-sanctioned** accessor `public.vault_secret(name)` (plain passthrough, EXECUTE already restricted to `postgres`+`service_role` per CLAUDE.md — no new grant needed). `pgp_sym_encrypt` embeds its own per-call random salt/IV in the returned OpenPGP packet, so the app-managed `key_nonce` column was dropped as dead weight rather than left as an unused landmine. A second bug in the same fix (pgcrypto functions live in the `extensions` schema, and these functions pin `SET search_path = ''`) was caught immediately by the same live round-trip test and fixed by schema-qualifying every call (`extensions.pgp_sym_encrypt`/`extensions.pgp_sym_decrypt`).
   Residual risk, disclosed rather than silently accepted: this design uses **one static Vault secret** to encrypt every user's key (vs. pgsodium's per-key envelope model). If that secret were ever exposed via the pre-existing, already-flagged `get_vault_secret_mcp` PUBLIC-grant gap (CLAUDE.md CREDENTIAL HANDLING, "⚠ OPEN FINDING, not yet fixed"), every user's BYOK key would decrypt at once. This rides on a pre-existing, already-tracked gap — not a new one introduced here — and fixing that gap is out of this issue's scope per M5 (it isn't named in the issue body). Flagging it here so it isn't silently absorbed as "solved."

**2. Free-tier model: no live DeepSeek `:free` route on OpenRouter today.** The issue suggests "e.g. DeepSeek free variants." Live-queried `GET https://openrouter.ai/api/v1/models` this session — 18 `:free`-suffixed models exist right now, none DeepSeek. Used an ordered candidate list (`z-ai/glm-5.2:free`, `minimax/minimax-m2.7:free`, `google/gemma-4-31b-it:free`) with the same `openRouterModelAvailable()` liveness check the existing vision cascade already uses — first live one wins — rather than hardcoding a slug that could vanish (documented precedent: the vision cascade's `:free` GLM slug already vanished once without notice).

**3. Single "active" provider per user, not simultaneous BYOK+Ollama.** The issue doesn't explicitly resolve whether a user can have multiple configured providers live at once. Implemented as: multiple providers can be *saved* (convenient re-switching without re-entering keys), but only one `is_active` at a time — saving a new one deactivates the rest. This matches the composer's stated intent ("My key" / "Ollama" as two of five mutually-exclusive modes) and keeps `X-Chat-Provider: byok`/`ollama` unambiguous without needing a provider name in the request (which the canon-tension rule forbids surfacing in the composer anyway).

## Secrets / provisioning notes for whoever reviews the PR

- No new Cloudflare Worker secret is required to ship this. BYOK calls use the *user's own* key (decrypted server-side per request); Ollama needs no key at all; the free tier reuses the *existing* `openrouter_api_key` vault secret the vision cascade already depends on, and `ROUTER_PROXY_KEY` (already required).
- `SUPABASE_SERVICE_ROLE_KEY` (existing optional Worker secret from #19829 P1 — gates `hasServiceRole(env)`) also gates the two new `/chat/api/providers*` routes, same fail-open/fail-closed pattern as the rest of chat persistence: unset = clean `503`, not a crash.
- `biddeed_user_providers_master_key` (new Vault secret, created idempotently by `20260904c`) is required for BYOK to function at all; Ollama-only usage doesn't touch it.
