## Item 1 — Census ACS keyless — DONE (VERIFIED)

**Code**: `packages/biddeed-mcp/src/report/context-layers.js` —
`fetchAcsLive()` no longer throws before attempting a call when
`CENSUS_API_KEY` is unset. It always builds the URL, omitting `&key=` when
no key is configured, and always attempts the fetch. Failure detection
switched from "no key configured" (a code gate) to a runtime check of the
actual response: Census's keyless/rate-limited response is an HTTP 200 that
redirects to `missing_key.html` with header `X-DataWebAPI-KeyError: 1` —
fetch() follows the redirect silently, so status/`res.ok` alone can't see
it; the header and `res.url` are checked instead. Any failure mode (missing
key, 5xx, JSON parse failure) renders the single message the issue asks
for: `"Pending — Census API unavailable at generation time"`. A failure is
never written to `context_layer_cache` (only successes are), so the next
report generation retries automatically — satisfies "retry on next
generation" without new code.

**Live re-verification, 2026-09-06 (this session, direct curl, not
inferred)**: the keyless call still 302-redirects to `missing_key.html`
with `X-DataWebAPI-KeyError: 1` from this environment — the issue body's
claim ("works without a key at low volume... ran keyless for months") does
not hold here, same finding #20043 made. **This is a runtime outcome now,
not a code gate** — the fix is real and correct regardless of whether
Census's policy is actually keyless-friendly from this network or not.

**Tests**: `packages/biddeed-mcp/test/context-layers.test.js` — replaced the
"no key → gated Pending" test with two tests that mock `globalThis.fetch`:
(a) keyless call → missing-key redirect → generic Pending message, and (b)
key configured → `key=` param present → a successful call is delivered.
5/5 pass (`node --test test/context-layers.test.js`, VERIFIED).

## Item 2 — Real 3-learner ensemble probability — DONE (VERIFIED)

### 2a — `scripts/ml_score_nightly.py`
Loads `ensemble.pkl` (`model_artifacts`, `model_version=v4.0-20260802-015242`)
— a dict of real sklearn/xgboost/lightgbm/catboost objects
(`xgb`,`lgbm`,`catb`,`rf_meta`) — same artifact and scoring formula as the
live Modal endpoint (`modal/ensemble_scorer.py`). Builds the 13-feature V4
vector per row, ported from `feature-vector.js`'s `V4_FEATURE_NAMES` +
`buildFeatureVector`. **Verified, not assumed**: `ensemble.pkl` itself
carries a `features` list — live-checked this session, it matches
`V4_FEATURE_NAMES` name-for-name and in the same order. The script now
asserts this at load time (fails loudly if a future retrain changes the
feature contract, instead of silently mis-scoring). `county_target_enc` is
computed once per distinct county in the batch (not per row), matching
`computeCountyTargetEncoding`'s formula and fallback (0.42) exactly.
Upserts in batches of 500 via `Prefer: resolution=merge-duplicates` +
`on_conflict=mca_id,model_version` — idempotent, matches the migration's
unique constraint.

**Reboot resilience**: every Supabase call goes through a retry wrapper (3x,
5/15/30s backoff). Only 5xx / connection errors / an HTML response body
(Cloudflare's actual error-page signature) count as "looks like a DB
restart" → exit 0 after retries exhausted. A genuine 4xx is raised
immediately (real bug, not swallowed as reboot-tolerance) — this
distinction was added after a real bug: the first live run's *first* draft
mis-classified a normal 201-with-empty-body upsert response (no
`Prefer: return=representation`, so no JSON body — completely normal) as
"looks like an outage" and gave up after only 1 of 7 batches, exiting 0
without completing. Fixed by checking for an HTML content-type / 5xx
specifically rather than "any non-JSON body."

**Dependency-pin findings (live, not assumed)**: loading the real
`ensemble.pkl` with the Modal image's pinned `scikit-learn==1.5.2` raised
three `InconsistentVersionWarning`s stating the true training version is
1.8.0 — confirmed by re-loading with `scikit-learn==1.8.0`, which produced
zero such warnings. That bump then broke `lightgbm==4.5.0`'s sklearn-compat
shim (`check_array() got an unexpected keyword argument
'force_all_finite'` — the parameter sklearn 1.8 removed); `lightgbm==4.6.0`
resolved it, verified live against the real artifact. Both findings and the
verification commands are documented in `scripts/requirements-ml.txt`. This
means the Modal image itself (`modal/ensemble_scorer.py`) is running a
stale/incorrect scikit-learn pin — flagged, not fixed (a different file,
out of scope for this issue; Modal apparently tolerates the version skew
in practice or hasn't hit the code path that would surface it).
