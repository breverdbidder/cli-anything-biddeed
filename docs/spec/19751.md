## Routing rule (required behavior #2)

`workers/winnerdata-ff` is single-tenant: `ORG_ID` is hardcoded to
Protection Partners (`032f4717-545f-4a18-b48b-28ea4257699d`), and every RPC
it calls (`ff_get_lead`, `ff_portal_leads`, etc.) validates that constant
server-side before returning any row — a mismatched org_id returns null/zero
rows. There is therefore no code path through this Worker that can ever
serve a different org. Root cause of the dual-template bug: the old code
reused `own_addr1 === phy_addr1` (owner-occupancy) — a legitimate signal for
`policy_type` (HO3 vs DP3) — as the template selector, so every
non-owner-occupied (DP3, e.g. a rental/investment property still insured by
Protection Partners) lead fell through to `TEMPLATE_A`. Live query against
`winnerdata.leads`/`signal_events`/`routing_decisions` for the 16 leads
routed on `2026-09-01` confirmed: 5 rows have `own_addr1 = phy_addr1`
(the 5 that rendered correctly) and 11 have it null or non-matching (the 11
that mis-rendered) — an exact match to the issue's reported 5/11 split.
**Rule going forward:** this Worker always renders `TEMPLATE_B` for every
lead it serves, full stop — no org/tenant conditional needed because there
is only ever one tenant. `ownerOccupied` is retained only to compute
`policy_type`.

   called with the anon key, not a literal service-role key embedded in the
   Worker.** This Worker's own architecture doc (index.js header comment)
   and `wrangler.toml` ("No [vars] — this Worker holds no secrets")
   already establish that every write goes through a narrow

   avoid holding a bypass-RLS secret in a bundled, deployed Worker's
   source. `ff_log_render_failure` follows that same, already-reviewed

2. **Removed the Template-A-only helper functions** (`propertyTableRows`,
   `propertySectionHeading`, `propertyTotalsLine`, `buyerOfRecordRows`,
   `contactRows`, `contactStatusLabel`, `contactComplianceNote`,

## Findings (not fixed — out of scope)

1. **Architectural gotcha that let 1101 through despite an existing
   try/catch**: the top-level `fetch()` handler's `try { return
   handleX(...); } catch (err) {...}` pattern does NOT actually catch async
   rejections from `handleX` — `return somePromise` inside a `try` block
   returns synchronously; a later rejection propagates as an unhandled
   promise rejection, bypassing the catch. This is the actual mechanism
   behind the 1101 (Postgres restart → `rpc()` throws asynchronously inside
   `handleFF`, which was never awaited by the outer catch). Fixed here by
   making `handleFF` itself never reject (its own internal try/catch now
   always resolves to a `Response`). The same latent pattern exists in
   every other `handleX` in this file (`handlePortal`,
   `handleFFSubmit`, `handleOwnerDashboard`, etc.) — none of them can
   currently produce a 1101 from a routine DB blip in the way `/ff/<id>`
   could (no evidence any of them have), but the same class of bug is
   there. Not fixed — out of scope (issue named only the `/ff/<lead_id>`
   failure).
2. **`templates/FF_TEMPLATE_A_AUCTION_SALES.html` and
   `FACT_FINDER_MASTER_TEMPLATE.html` were not checked for the same
   internal-reference leak class** in this session (`FACT_FINDER_MASTER_TEMPLATE.html`
   is already known to leak "issue #19392 comment 5390376020" / "issue
   #19434" per a grep run this session) — both ship through
   `scripts/portfolio_fact_finder_render.py` / `render_ff_9buyer_20260827.py`
   / `render_factfinder_master.py`, none of which are `workers/winnerdata-ff`.
   Worth a follow-up issue against whichever of those scripts is still live.
3. **`Property Profile — Owner-Occupied (HO3)` heading in `FF_TEMPLATE_B_HOMEOWNER.html`
   is a static string** that doesn't branch on the computed `policy_type`
   (HO3 vs DP3) — a DP3 (non-owner-occupied) lead still shows the
   "Owner-Occupied (HO3)" heading text even though `{{policy_type}}` further
   down correctly says DP3. Pre-existing, not touched (not named in this
   issue), flagged for whoever owns the next FF-template pass.
