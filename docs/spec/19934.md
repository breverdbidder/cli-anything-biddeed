## What "the same Worker endpoints" turned out to mean

The issue names `/chat/api/upload`, `/chat/api` with `upload_id`, and `/chat/api/identity` as the contract
to reuse. Those routes are **not** in `biddeed-web` — they are in *this* repo, `src/worker.js` (the legacy
Cloudflare Worker biddeed-web is strangler-replacing), built across #19829 P1 ([docs/spec/19829-P1.md](19829-P1.md))
and #19847 C3 ([docs/spec/19847.md](19847.md)) and live in production at `https://biddeed.ai/chat/api/*`
today (confirmed live this session — see "Live verification" below). `src/worker.js` was **not modified**
by this session — it was read-only reference for the exact request/response shapes, consistent with the
issue's own instruction to deliver only in `biddeed-web` and with standing mandate M5 (repo scope discipline).

`biddeed-web` already has one client of this same Worker: `app/api/deed/route.ts`, a same-origin POST proxy
to `/chat/api` that exists because the app's CSP (`connect-src 'self'`) refuses a direct browser fetch to
`biddeed.ai`. Everything this session added follows that exact, pre-existing pattern.

## What was built (in `biddeed-web`)

### New files
- `app/api/deed/identity/route.ts` — same-origin proxy to `POST /chat/api/identity`.
- `app/api/deed/upload/route.ts` — same-origin proxy to `POST /chat/api/upload`, forwards `X-Chat-Token`,
  enforces the same 8MB (×1.4 base64 overhead) cap the Worker does.
- `app/api/deed/projects/route.ts` — same-origin proxy to `GET`/`POST /chat/api/projects` (list + create
  only — per-project files/reports management stays on the Worker's own `/chat` surface, per the issue's
  "until the Next pages exist" scope note).
- `lib/deed/chatIdentity.ts` — localStorage-backed chat-identity token helper (`getChatIdentity`,
  `ensureChatIdentity`), reusing the Worker's own `bd_chat_token`/`bd_chat_email` key names.

### Modified files
- `components/deed-home/Composer.tsx` — added the "+" dropdown menu (Upload documents, Paste screenshot,
  Public-records search toggle, Deep Research → SIGNAL$), a Project selector submenu, an inline
  identity-gate row (email capture, mirrors the Worker's `requireIdentityThen` + sign-in drawer), a pending-
  upload chip, and a paste handler that attaches a pasted image as a screenshot. Mic button and Enter/Shift+Enter
  behavior unchanged.
- `components/deed-home/useDeedThread.ts` — `send()` now takes `DeedSendOptions` (`uploadId`, `uploadLabel`,
  `publicRecords`, `projectId`); forwards `X-Chat-Token` (read from `lib/deed/chatIdentity`) and the new body
  fields to `/api/deed`; captures the Worker's `event: meta` `conversation_id` and persists it on the thread.
- `app/api/deed/route.ts` — now forwards `X-Chat-Token` and accepts/forwards `conversation_id`, `upload_id`,
  `public_records`, `project_id`.
- `lib/deed/protocol.ts` — `readDeedStream()` gained an optional `onMeta` callback that parses the Worker's
  `event: meta` frame (previously only `properties` events and text deltas were handled; `meta` frames were

- `lib/deed/threads.ts` — `Thread` gained `workerConversationId?` and `projectId?`; `ThreadTurn` gained

- `components/deed-home/DeedHome.tsx` — plumbs `DeedSendOptions` through `onSend`, passes the thread's

- `components/shell/AppSidebar.tsx` — added `Projects` and `Skills` entries above `Recent`, both external

## Why conversation continuity needed touching at all
`biddeed-web`'s home surface never previously sent `X-Chat-Token`, so the Worker never saw an identified
user from `/` and never persisted anything server-side for it — this PR is the first thing to change that.
Left alone, that would have introduced a real bug: the Worker creates a new `biddeed_chat_conversations` row
on any identified turn that doesn't carry a `conversation_id` it recognizes (see `src/worker.js` around the
`POST /chat/api` handler), so every message in a home thread would silently spawn its own orphan conversation
server-side. Capturing `event: meta`'s `conversation_id` and replaying it on the next turn (this session's
`lib/deed/protocol.ts` + `useDeedThread.ts` changes) closes that gap — a necessary consequence of this PR's
own change, not scope creep (Karpathy K3).

## Deviations from intent (material ones, with reasons)

1. **Skills sidebar entry links to `/chat`, a placeholder, not a Skills surface** — because no Skills surface
   exists anywhere in this codebase yet (P3, "Not started" per [docs/spec/19829.md](19829.md)'s phase table).
   The issue's own text anticipates this ("links into the Worker /chat surfaces until the Next pages exist"),
   but flagging explicitly rather than letting the link look purposeful: it is a deliberate stand-in for
   "no destination exists yet," not "Skills lives at /chat."
2. **Project selector is a submenu with a `window.prompt` creation flow, not a richer inline form** — mirrors
   the Worker's own `createProjectThen()` UX exactly (same prompt text). A nicer inline creation form is real,
   deferred scope (Karpathy K2: minimum code that solves "scope the message to a project," not a redesign of
   project creation UX the Worker itself doesn't have either).
3. **"Harness 0 red" could not be run** — the tool named by that instruction does not exist in `biddeed-web`
   (confirmed via repo-wide search); it is a `cli-anything-biddeed` tool. Screenshots were checked visually
   against the canon light palette instead of via the automated gate.
4. **DOCX/XLSX/image uploads accepted client-side but not extraction-tested** — the file input's `accept`
   list matches the issue's literal ask (PDF/CSV/DOCX/XLSX/images), but only PDF (and, transitively, the
   Worker's existing CSV/TXT paths from #19829 P1) were exercised live this session; DOCX/XLSX/image
   extraction on the Worker is already documented as `extraction_status: 'unsupported'` by design (#19829-P1
   Deviation 9) and this session did not re-verify that per-type, only image (via the screenshot-paste test).
5. **Voice/mic unchanged** — still an honest external link to `/chat`, per the pre-existing comment in
   `Composer.tsx`; porting the ElevenLabs pipeline is tracked separately (issue #19828) and was correctly out
   of scope for "the '+' menu, mic, and project scope" (the issue names mic for parity-of-presence, not a
   request to build voice).
