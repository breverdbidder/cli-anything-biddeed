### 2.2 `scripts/biddeed_reels_pipeline_v2.py` — pre-existing `match_zw_parcel_geom` null-geom crash

Hit live, blocking 2 of the 10 targets (`broward/COWE-12-011377`, `palm_beach/502025CA009901XXXAMB`):
`the JSON object must be str, bytes or bytearray, not NoneType` from `json.loads(geom_row["geojson"])`.
Root-caused **CONFIRMED live**, not hypothesis: both parcels' `public.zw_parcels` rows match by
`pin_clean` and carry a real `centroid_lat`/`centroid_lon`, but `z.geom` itself is `NULL` (no
polygon on file) —

```sql
select county, pin_clean, centroid_lat, centroid_lon, (geom is null) geom_null
from public.zw_parcels
where (lower(county)='broward' and pin_clean='514018111070')
   or (lower(county)='palm beach' and pin_clean='56424225230001290');
-- broward/514018111070:    centroid_lat=26.003070 centroid_lon=-80.389454 geom_null=true
-- palm beach/56424225230001290: centroid_lat=26.788117 centroid_lon=-80.112620 geom_null=true
```

`match_zw_parcel_geom()`'s caller only checked `centroid_lat is not None` before assuming
`geojson` was populated — a latent bug in the existing v2 pipeline, same class as the numeric-cast
bugs already fixed in #20030/#20032, now hit for the first time by these 2 specific parcels. Fixed
by also requiring `geojson is not None` before taking the outline branch; added a new middle branch
(reuses the real zw_parcels centroid for a plain pin-marker aerial instead of falling all the way
back to street-address geocoding) so precision isn't lost, but **never fabricates an outline**
(`parcel_outline` stays `false` for these 2, honestly). In-scope to fix because it directly blocked
2 of this issue's own 10 named case numbers — not a drive-by cleanup elsewhere in the file.

### 2.3 `agents/reel_studio/hook_writer.py` + `agents/reel_studio/director_qa.py` — title-case i18n fix

Root cause **CONFIRMED live** (matches #20032's own HYPOTHESIS-flagged residual finding, now
verified): `hook_writer.check_title_case()` took no `lang` argument and always checked against the
English-only stopword list (`a, an, the, of, in, on, for, to, is, at, by, and, or, its, it's, this,
that, than, off`); `director_qa.review_reel()`'s own variants query never even selected the `lang`
column from `winnerdata.reel_variants`, so there was no way to pass it through even if the checker
had accepted it. Every Spanish/Portuguese connective word (`de`, `em`, `del`, `los`...) was
therefore flagged as a lowercase-drift violation on every non-EN title.

Fixed surgically:
- `hook_writer.py`: split the single stopword set into `_TITLE_CASE_STOPWORDS_EN` (unchanged) and
  a new `_TITLE_CASE_STOPWORDS_ES_PTBR` (`de, la, el, en, del, los, las, y, a, do, da, em, um, uma,
  o, os, as, e, com, para, por, no, na` — exactly the issue body's list). `_title_case_stopwords(lang)`
  picks by `lang.startswith(("es","pt"))`. `check_title_case(title, lang="en")` and
  `validate_title(title, lang="en")` both gained the optional `lang` param (default `"en"` keeps
  every existing call site — including both eval suites and the two `_cp3c_*` one-off scripts —
  byte-for-byte unaffected).
- `director_qa.py`: `review_reel()`'s variants `SELECT` now includes `lang`; `check_title_case()`
  and `check_title_compliance()` (the latter also runs `validate_title()`, which internally reruns
  the same title-case rule — both call sites needed the fix or `qa_pass` would still flip false on
  the `title_compliance` check even after `title_case` itself passed) both pass
  `variant.get("lang", "en")` through.
