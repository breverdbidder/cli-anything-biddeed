## Environment finding (not in scope to fix, blocks DoD #1's own prerequisite)
The GitHub Actions runner this session executed in has Node 20.20.2 as the default `node` on
`PATH`. `wrangler@4.x`'s transitive dependency `nanoid@6.0.1` requires Node `^22 || ^24 || >=26`
and `npm install` hard-fails (`EBADENGINE`) under Node 20. Node 22.23.2 and 24.19.0 are already
present in the runner's tool cache (`/opt/hostedtoolcache/node/`), so this session worked around
it by prepending the Node 22 bin dir to `PATH` for every command in this repo. **This is
session-local** — it does not change what Node version future `cc-runner-ghonly.yml` jobs use by
default. If the eventual GHA build/deploy workflow for `biddeed-web` doesn't already pin
Node ≥22, it will hit the same `EBADENGINE` failure. Flagging, not fixing (workflow-file edits
are out of scope for this issue per M5).

### Clerk 500 finding (CONFIRMED via code read, root cause INFERRED not to be migration-caused)
`lib/clerk-host.ts`'s `isClerkHostAuthorized(host)` returns `true` for `localhost`/`127.0.0.1`
in addition to `biddeed.ai`/`*.biddeed.ai`, and is the **only** gate `app/sign-in/[[...sign-in]]/page.tsx`
checks before rendering `<SignIn />`. `components/ConditionalClerkProvider.tsx` (wrapping the
whole app in `layout.tsx`) additionally requires `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` to be set —
if it isn't, it renders `children` with **no** `<ClerkProvider>` at all. With no Clerk keys
configured (true in this session, and per `middleware.ts`'s own comment, true in the *current
live Vercel production* as of 2026-08-20), hitting `/sign-in` on an authorized host renders
`<SignIn />` without a surrounding `<ClerkProvider>`, which Clerk's SDK throws on
(`useSession can only be used within the <ClerkProvider />`). **This is a pre-existing mismatch
in the sign-in/sign-up pages' own gating logic, independent of Vercel vs. Workers** — the same
env vars, same code, same host-matching logic would produce the same 500 on Vercel today. Not
fixed here: out of migration scope, not something the issue asked for, and fixing app auth logic
wasn't named in the issue's scope. Flagging for a separate issue.

### Minor finding: duplicated security headers under OpenNext
`curl -I http://localhost:8787/` showed every header from `next.config.mjs`'s `headers()`
(`Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`)
present **twice**, comma-joined in a single header line. HYPOTHESIS: OpenNext's asset-serving
layer and the Next.js middleware/handler layer both apply the config's `headers()` independently
under the Workers runtime. Not a correctness bug (values aren't contradictory, browsers accept
repeated equal directives), but worth a look before production cutover — flagging, not
investigating further, since it doesn't block preview verification.

## Process-management incident (relevant to why the intent file's HARD RULES exist)
This session hit the exact orphan pattern the intent file warned about, twice, despite following
the documented PID-capture pattern:
1. First `kill "$(cat /tmp/server.pid)")"` (recommended pattern from the intent file) killed only
   the top-level `npx wrangler dev` process — 7 child processes (`npm exec`, `sh -c`, the actual
   `wrangler` node process, two `esbuild --service` processes, and two `workerd` runtime
   processes) survived and kept the port bound.
2. Second attempt used the intent file's documented fallback, `kill $(lsof -ti:8787)` — this only
   killed the single process holding the listening socket (`workerd`), leaving 6 more orphans
   (`npm exec`, `sh -c`, `node cli.js`, `esbuild`, and a second `workerd` instance) still running.
3. Both times, resolved by `pgrep -fa "wrangler|workerd"` to enumerate the **exact** surviving
   PIDs, then `kill <pid1> <pid2> ...` against that specific, just-enumerated list — never a
   pattern match against a process name. Verified clean (`pgrep` empty, port free) after each.

**Recommendation for the next session that touches this repo's `wrangler dev`**: neither
documented pattern in the intent file (`kill $PID` from a captured single PID, nor `kill
$(lsof -ti:PORT)`) fully tears down a `wrangler dev` process tree — it forks through
`npm exec` → `sh -c` → `node` → `esbuild` + `workerd`, and none of those inherit as a single
killable group in this sandbox. The reliable pattern is: capture the wrapper PID for reference,
but before ending the session, always run `pgrep -fa "wrangler|workerd"` and kill every PID it
returns individually (never `pkill -f`, per the original hard rule — this is exact-PID kills of
processes just enumerated by content match, not a name-pattern broad kill).
