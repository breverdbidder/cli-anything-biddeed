## Result summary
**BLOCKED before deploy.** This runner session had no `CF_ACCOUNT_ID` /
`CF_API_TOKEN` / `VERCEL_TOKEN` in its environment (confirmed empty — see
"Credential gate" below), so the actual `wrangler deploy`, secret binding,
and DNS cutover (plan steps 0, 1, 5, 6, 7) could not be executed. Everything
buildable and locally-verifiable without those tokens was built and proven
against workerd (Cloudflare's real runtime, run locally via `wrangler dev`)
and against real production Supabase data. The Worker is deploy-ready; it
has never touched Cloudflare's edge or DNS.

## What was built
- `cloudflare/mcp-worker.mjs` — Worker entry. **Option 1** per the intent's
  preference: `cloudflare:node`'s `httpServerHandler` wrapping the existing,
  unmodified `startHttp(port)` factory from `packages/biddeed-mcp/src/http.js`.
  No duplicate routing logic between the Vercel-era code and the Worker.
- `cloudflare/wrangler.mcp.jsonc` — `name: biddeed-mcp-production`,
  `compatibility_date: 2025-09-23`, `compatibility_flags: [nodejs_compat,
  enable_nodejs_http_server_modules]` (the flag Cloudflare's Sept-2025 blog
  post requires for `http.createServer`/`httpServerHandler`), `limits.cpu_ms:
  30000` (the plan-check probe from guardrail #7 — untested, no CF token to
  submit it against; see Open items). No `routes`/`custom_domain` key yet —
  added at actual cutover time, not before.
- `packages/biddeed-mcp/src/report/pdf.js` — one-line import-compat shim:
  `import PDFDocument from 'pdfkit'` → `from 'pdfkit/js/pdfkit.standalone.js'`.
  The default entry reads AFM font files via `fs` at render time, which
  doesn't exist in workerd; the standalone build embeds font metrics inline.
  Zero logic change — same class, same API.
- `packages/biddeed-mcp/src/http.js` — two additions inside the existing
  `handleRequest()` (the single dispatcher both Vercel's `handleMcpRequest`
  and the new Worker now share): (1) the three CORS headers + OPTIONS→204
  shortcut, previously set only by the Vercel wrapper `api/mcp.js`, now set
  once here so the Worker (which has no per-route wrapper) matches Vercel on
  every route; (2) a `POST /api/stripe/webhook` route delegating to the
  already-existing `handleStripeWebhook` from `./webhook.js` (previously only
  reachable via the separate Vercel function `api/stripe/webhook.js`, which
  the Worker's single Node http server has no equivalent of). `api/mcp.js`
  and `api/stripe/webhook.js` themselves are untouched — Vercel's request
  path is unaffected by either change.
- `.github/workflows/cloudflare-mcp-production.yml` — new CI deploy workflow.
  Triggers on push to `packages/biddeed-mcp/**`, `api/**`, `cloudflare/**`,
  plus `workflow_dispatch`. Credential-gates on CF_API_TOKEN/CF_ACCOUNT_ID,
  binds secrets via `wrangler secret bulk` from a temp file deleted in the
  same step, deploys, then runs the no-auth/negative rows of the gate table
  against the workers.dev URL (the only rows that carry zero billing risk to
  run unattended in CI on every push). **Untested** — has never run for real;
  written from the same pattern as `mcp-vercel-deploy.yml` and validated only
  for YAML syntax (`yaml.safe_load` in this session).
- `.github/workflows/mcp-vercel-deploy.yml` — deprecated: push trigger
  removed, `workflow_dispatch` kept, header marks it DEPRECATED and points at
  the new workflow. File otherwise untouched.
- `docs/spec/20025-rollback.md` — written before any DNS change (none was
  made) per guardrail #3, so cutover has a documented path when a DNS-scoped
  token is available.
- `.gitignore` — added `.dev.vars` / `cloudflare/.dev.vars` (wrangler's local
  secret file for `wrangler dev`; must never be committed).

### PDFKit-standalone under workerd — isolated proof
Billing-gated `/report/pdf` couldn't be driven to a real 200 without funding
a synthetic customer's credit wallet and finding/certifying a Gold Standard
county for it (more production billing-table writes than this migration
warrants). Instead, `renderReportPdf()` (the exact function `/report/pdf`
calls) was invoked directly, with network mocked out, inside a throwaway
`wrangler dev` instance (`/tmp/pdf-smoke`, deleted after, never committed):
```
HTTP/1.1 200 OK
Content-Length: 7783
header bytes: 25 50 44 46 2d 31 2e 33  ("%PDF-1.3")
/Type /Page occurrences: 4
```
Confirms the one Workers-specific risk in this migration (pdfkit's `fs`
dependency) is resolved. The synthetic report only populates `cover` +
`auction_listing`, so its byte count (7.7KB) is smaller than a real full
17-section report (>20KB expected in the gate table) — this is a fixture-size
artifact, not evidence against the >20KB gate.
