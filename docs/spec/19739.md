## Finding-by-finding (VERIFIED / INFERRED / BLOCKED tags)

### washington — E — FIXED, VERIFIED
31 of 143 washington rows (all `sale_type='tax_deed'`, TDM-sourced, `tdm_case_id` populated) had
`parcel_id IS NULL` but a populated `account_number` column in the same dashed format
(`00000000-SS-BBBB-LLLL`) already used as `parcel_id` on 78 other washington tax_deed rows in the
same table (VERIFIED: byte-identical to `account_number` on those rows). Independently corroborated
against qPublic's and TaxNetUSA's published Washington County FL parcel-ID format documentation
(VERIFIED via WebSearch). A live single-parcel qPublic lookup to resolve one account number to a
named owner/address was attempted and BLOCKED by a Cloudflare bot-challenge — judged non-blocking
given the strength of the internal 78-row precedent plus external format corroboration.

Applied: 31 individual per-`id` PATCH calls (no bulk WHERE) setting `parcel_id = account_number`,
`geo_source = 'tdm_account_number_backfill'`. Post-write VERIFIED: 0 remaining nulls, all 31 rows
spot-checked for format sanity, row count unchanged at 143 (no phantom insert/delete), full 10-letter
regression scan for washington showed no other letter moved. Adversarial verify: **SURVIVED**.

Caveat (does not roll up into I/C/D): these 31 rows still have `property_address IS NULL` — letter I
(card completeness) and C/D (parity) need address/geo, not just `parcel_id`, so this fix does not
cascade into those letters despite the documented `I <= E` structural dependency (that dependency is
about the zoning-linked card view requiring a non-null `parcel_id` as a *necessary* condition, not
sufficient — these particular rows still fail the other I preconditions).

### sumter — E — BLOCKED, VERIFIED (of the blocker, not a fix)
2 rows (`2026-CA-000074`, `2026-CA-000129`) have zero identifying data beyond a case number — no
address, no account number, no owner name. The only path to a real parcel_id is Sumter Clerk's
Online Court Records Search, which is a stateful Civitek/PrimeFaces (JSF) app requiring session
cookies and per-request ViewState/component-ID tokens regenerated on every round trip — architecturally
unreachable by static curl/WebFetch, and no JS-executing browser tool (Playwright/browser-use) was
available in this session. No write was made. Adversarial verify: **SURVIVED** (claim of BLOCKED,
and of zero side effects, both reproduced independently).

### washington — C/D — ROOT-CAUSED, VERIFIED
The ~70 failing rows are exactly the address-less TDM tax-deed stub rows (confirmed via
`property_address IS NULL` grouping). Parity matching against PropertyOnion needs an address/legal
description to compare against, not a parcel_id — so the E fix above does **not** cascade into C/D
for washington. Fixing this for real would require an address-enrichment pass (e.g., a Washington
County Property Appraiser lookup keyed by the now-populated `parcel_id`/`account_number`), which is
new scraper work out of scope for a same-session mechanical fix; documented here rather than forced.
Adversarially verify: **SURVIVED**.

### sumter — C — SMALL-COUNTY COVERAGE GAP, VERIFIED (as a finding, not fixed)

### madison — B/F — PARTIAL FINDING, ONE CLAIM REFUTED
7 of 8 madison rows are genuinely future/upcoming (denominator=0 is structurally correct — not a
bug). Case `24-62-CA` (204 SW Church Ave) is `sale_result=SOLD_PLAINTIFF`, past `auction_date`
(2026-07-28), yet `sold_amount`/`tier1_sold_amount` are both null — a real gap. Madison Clerk's
public page only lists upcoming sales; Madison's Civitek OCRS requires the same interactive JSF form
submission as Sumter's (see above) and was equally unreachable this session; an Auction.com hit for
the same address is a **later, distinct** REO relisting (bank's post-title resale, opening bid $1),
not the original sale's outcome — correctly declined as a fabrication risk. No write was made.

**Refuted claim, corrected here per Honesty Protocol**: the original finding's evidence line stated
this null was "an outlier/gap not a structural ceiling" based on a 3-county sample (brevard/palm_beach/
broward) that happened to all be brevard rows and happened to look clean. The adversarial verifier
re-ran the same query fleet-wide: **~32–35% of all `SOLD_PLAINTIFF` rows with this exact status combo
are null on `tier1_sold_amount`**, including charlotte (22 rows), walton (6), and martin (2) — i.e.
this is very likely a **systemic** Certificate-of-Sale-population gap for plaintiff-reverted sales,
not a madison-specific scraper defect. No unsafe write resulted (action was NONE either way), but the
mischaracterization is logged as a corrected finding, not silently dropped. Two other madison rows
(`21-36-CA`, `26-20-CA`) have past `auction_date` with `sale_result` stuck at `PENDING` — flagged as
the same class of gap, not investigated further this session.

## Why this session did not use the full 6-hour budget
Real, verifiable progress on the remaining failing letters in this shard is blocked by two genuine
external constraints, not by giving up early: (1) two counties' OCRS case-lookup portals
(Sumter, Madison) are stateful JS applications that this sandbox has no browser-automation tool to
drive, and (2) the remaining C/D parity gaps require new address-enrichment/scraping infrastructure
rather than a data-plane fix. Continuing to poll the same blocked levers without a new tool or a new
angle would not have produced additional verified progress — it would have produced more diagnosis of
the same already-diagnosed blockers. The one genuinely fixable, safe, verifiable lever found this
session (washington E) was shipped and verified.
