# Spec — Issue #20057 (GTM-8 / M9): clickable deal-page link must ship IN THE POST — gate the publish queue on it

Status: **SHIPPED** (schema + code changes live, 20/20 EN kokoro finals backfilled and DB-verified; YouTube upload/pinned-comment path itself remains untestable — the lane is still dormant, no OAuth secrets exist, per #19788)

## Why (Ariel, 2026-09-06)
The end-card "See this deal →" + QR + `biddeed.ai/r/<code>` burned into the video frame is not clickable on any platform. The redirect chain itself was already verified working (#20052). What was missing is the one-tap path: a real, clickable short link living in the post **text** (YouTube description/pinned comment, IG/TikTok/Facebook caption) — not just the video pixels.

## Binding decisions / INFERRED reconciliations (documented per M6)

1. **`post_text` keyed by platform only, not platform+lang.** The issue's fix section says "per variant, per platform, per lang." Each `reel_variants` row is already single-language (a translation gets its own row with its own `variant_key`+`lang`+`short_code`+`hashtags`, per #20032/#19793) — nesting `post_text` by lang inside the jsonb would duplicate a dimension the row already carries. INFERRED simplification; K2.

2. **Queue gate implemented as "first line contains the short_url," not a strict string-prefix match.** Work item 3 says the description must "start with the variant's own short_url." Work item 1's own format for that line is `See this deal → https://biddeed.ai/r/<code>` — a label precedes the URL. Requiring the raw string to literally *start* with the bare URL would contradict the format the same issue specifies two paragraphs earlier. Implemented as: `split_part(description, E'\n', 1) like ('%' || short_url || '%')`. Verified live (below) — 20/20 rows pass.

3. **Disclosure line kept as a 4th line in the YouTube description.** The issue's 3-line format (link, title, hashtags) doesn't mention the legal disclaimer that `agents/youtube/metadata_builder.DISCLOSURE_LINE` already ships (#19788, M3 compliance). Kept as an additive trailing line (blank line + disclosure) rather than dropped — removing an already-shipped legal disclaimer wasn't asked for and would be a regression, not a fix.

4. **YouTube comment pinning: KNOWN PLATFORM LIMITATION, not implemented.** YouTube Data API v3 has no public endpoint to pin a comment — pinning is a YouTube Studio UI-only action. `agents/youtube/youtube_lib.py::post_top_level_comment()` posts the deal-page link as a real top-level comment (this is real, documented API surface: `commentThreads.insert`), but nothing pins it programmatically. Per the Honesty Protocol this is surfaced explicitly rather than faked. Per M9's own framing ("a Short with no clickable link is not published"), a comment-insert **failure** still fails the whole variant (`status='publish_error'`) — that part is fully implemented — but a successful, unpinned comment is the ceiling of what this repo can do against YouTube's real API today. This is a platform boundary, documented in `youtube_lib.py`, `uploader.py`, and `docs/gtm/YOUTUBE_LANE.md`, not a partial implementation of something that's actually possible.

5. **IG/TikTok/Facebook `link_in_bio_targets` rows are `status='pending'`, never `'live'`, in this session.** No IG/TikTok/Facebook publish lane exists anywhere in this repo (only the dormant YouTube lane, #19788, does). Writing `status='live'` today would claim a bio link was actually updated on a real Instagram/TikTok/Facebook account, which did not happen — nothing in this repo has ever called any of those platforms' APIs. The table and backfill rows exist so a future publish lane has somewhere to write `status='live'` when it actually posts; fabricating that state now would be a Honesty Protocol violation, not a shortcut.
