## What was built

1. **`finance.normalize_descriptor(text)`** — strips the WF `PURCHASE`/`RECURRING
   PAYMENT[ REVERSAL]` wrapper + date, trailing card/ref numbers, city/state, and the
   6 payment-processor prefixes named in the issue (`SQ *`, `IC* `, `GOOGLE *`, `TST* `,
   `PY *`, `SP `, `AMZN Mktp`). Tested against all 161 distinct raw descriptors behind
   the 186 exceptions before being wired into anything live.
2. **`finance.categorize_bank_txn`** updated to match `category_rules.pattern` against
   raw text **OR** `normalize_descriptor(text)` (additive: normalize_descriptor only
   ever removes characters, so this is a strict superset of the old raw-only matching).
   Verified **zero-diff** against all 616 live `simplefin` `bank_transactions`
   (old engine vs. new engine, via a temporary staging function) before promoting —
   in practice, the ~55 new `category_rules` rows below resolve 184/186 via plain
   raw-text substring matching (WF's column padding doesn't break single-token
   merchant names), so the normalization mainly fixes the *display* layer.

## Risk controls actually exercised (not just claimed)

- **Collision check before adding rules**: a systematic query checked all ~55 planned
  patterns against every *already-correctly-categorized* transaction. Found one real
  collision — `COSTCO` vs. the existing `INSTACART` rule, both would match the ~44
  "IC* COSTCO BY INST...INSTACART.COM..." rows. Fixed by giving `COSTCO` priority 40
  (below INSTACART's 30) so INSTACART keeps winning those rows unchanged; `COSTCO`
  only fires for the 2 truncated variants lacking the literal "INSTACART" substring.
  `AIRBNB`/`VERCEL`/`Workspace_zone` collision-check hits were verified as false
  alarms (different `entity_scope`+`direction`, so no actual overlap).
- **Dry-run projection before the write**: simulated `categorize_bank_txn()` output
  across the 186 open exceptions, got `matched=true: 184, matched=false: 2`, executed
  the batch, and the real result matched the projection exactly.
- **Idempotency proven, not asserted**: ran `recategorize_open_exceptions()` and
  `process_bank_transactions()` twice. Second run: `changed=0, resolved=0` on the
  batch driver (true no-op); `process_bank_transactions()` reprocesses a single
  pre-existing, unrelated `biddeed`-entity test fixture row (`"UNKNOWN VENDOR
  FIXTURE"`, no `journal_entry`/`recon_match`, present before this session) every
  run — flagged below as a finding, not fixed (out of scope, different entity).
- **One genuine correction found mid-run**: a `-$4.29` PUBLIX refund (inflow) didn't
  match the `out`-only PUBLIX rule; broadened that one rule to `direction='any'`
  rather than guessing broadly across all 40+ new rules.

## Deviations from spec

1. `normalize_descriptor` alone was **not** the primary fix for the 186 — the new
   `category_rules` rows resolve 184/186 via plain raw-text substring matching (WF's
   padding doesn't break single-token merchant names inside the wrapper). The
   normalization function is real, tested, and wired into matching as instructed, and
   is the actual fix for `v_commingled_business_costs`'s vendor-name display — but the
   issue's framing ("this alone should resolve most of the 186") slightly overstates
   its role in the *matching* fix versus the *display* fix. Both are delivered.
2. 6160 (scope #3) was already done in the prior session (`20260902q`) — not
   re-created, verified and reported instead of silently claimed.
3. Left 2 of 186 genuinely uncategorized (`SQ *FAST`, `THE LAW OFFICES OF`) rather than
   guessing, per the issue's own instruction. Both are well under the "<25" target.
