## Deviations (required per Session Summary Loop Closure)

**Edit 7 (`/answers/*` descriptions) was NOT a DB trim — it was a renderer bug fix.**

- **What the issue claimed:** `/answers/redemption` meta description is 158
  chars (>155), fix by trimming `site.site_content` at the source.
- **What I found:** `public.get_published_content('redemption')` returns
  `body_jsonb.meta_description` = 142 chars, well under the limit (VERIFIED via
  direct RPC call, JSON decoded, literal apostrophes, no HTML entities).
  `buildAnswerPage()` in `src/worker.js` called `escHtml()` on `metaDesc`
  **twice** — once when computing `metaDesc` (line 5069, correct), again when
  inlining it into the `<meta>` tag (line 5161, redundant). Each of the two
  apostrophes in the redemption copy went `'` → `&#39;` (correct, +4 chars) →
  `&#39;` → `&amp;#39;` (bug, +4 more chars). `142 + 2×4 + 2×4 = 158` — exactly
  the number in the issue. Confirmed live via `curl` before the fix: raw HTML
  showed literal `&amp;#39;`.
- **Why I fixed the renderer instead of the DB:** the DB content was already
  correct and under-limit; double-escaping was a defect that would have
  rendered `&#39;` as literal text in a Google search snippet even after any
  DB trim, and would recur on any future `/answers/*` row containing an
  apostrophe, ampersand, or quote (audited: `foreclosure-vs-tax-deed`,
  `how-the-max-bid-is-calculated`, `surplus-funds`, and
  `what-happens-after-you-win-a-foreclosure-auction` all also contain
  apostrophes and were silently affected). Removed the redundant `escHtml()`
  call at line 5161. This is a one-line, surgical fix, touches no DB row.
- **Verification all 8 published rows post-fix** (via
  `list_published_content_slugs` + `get_published_content`, raw JSON length =
  what the DOM sees once escaping is single-pass):
  `deposits-and-payment`=133, `foreclosure-vs-tax-deed`=126,
  `how-the-max-bid-is-calculated`=143, `redemption`=142, `surplus-funds`=136,
  `what-happens-after-you-win-a-foreclosure-auction`=155 (exactly at the
  `<=155` boundary — passes), `what-survives-a-foreclosure-sale`=146,
  `what-survives-a-tax-deed-sale`=134. **All 8 within limit — no
  `site.site_content` UPDATE was needed once the renderer bug was gone.**

**h1→h2 choice was a judgment call, not specified by the issue.** For both
`/county/:slug` and `/buy-report`, the issue says "keep the page title as the
only h1, demote the other two to h2" but doesn't say which of the 3 duplicate/
near-duplicate headings counts as "the page title." I kept whichever heading
is actually visible under normal operation (JS + assets load successfully) as
the sole `<h1>`, and demoted the two that are only rendered on the noscript /
asset-failure fallback paths (`/county/:slug`) or on wizard steps hidden by
`display:none` on initial load (`/buy-report`). Added a matching
`h1,h2.step-title{...}` CSS rule to `BUY_REPORT_HTML` so the demoted step
headings keep their original visual size once a user advances the wizard —
zero visual change for any real user in either fix.
