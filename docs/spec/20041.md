# Spec — issue #20041 — LAUNCH-A2: rate limiting must be provably effective

## Intent reference
docs/intent/20041.md — supersedes the rate-limit part of #20035 only (its
edge cache + security headers are VERIFIED live and were left untouched).

## Why this issue existed
#20035 shipped a `caches.default` "counter" as a fallback after Cloudflare's
Workers Rate Limiting binding was found to always return `success:true` on
this Free-plan account. The `caches.default` fallback is not a real counter:
Cache API writes are per-colo and non-atomic. Verified live on 2026-09-05
16:13-16:15 UTC (this issue's own evidence, gathered by a prior session
before any fix): 25 sequential unauthenticated POSTs to
`mcp.biddeed.ai/api/mcp` returned 25×401, zero 429; 8 sequential POSTs to
`biddeed.ai/chat/lead` returned 8×400, zero 429. The product was
unprotected in production.

## What was built

**cloudflare/rate-limit-do.mjs** (new) — `RateLimiterCounter`, a
SQLite-backed Durable Object: one table (`window_start`, `count`), reset
when the fixed window expires, `fetch()` returns `{allowed, count,
windowStart}`. Plus `checkRateLimitDO(env, bindingName, bucket, key, limit,
windowMs)`, a thin caller that `idFromName`s a DO instance per
`${bucket}:${key}` and fails OPEN (`allowed:true`) on any error, matching
the fail-open posture the rest of this codebase already uses for rate
limiting. This file is used by `cloudflare/mcp-worker.mjs` only (see
deviation #1 below for why `src/worker.js` has its own inlined copy instead
of importing it).

**cloudflare/mcp-worker.mjs** (biddeed-mcp-production) — replaced
`checkRateLimitCache()` (the `caches.default` counter) with
`checkRateLimitDO()` calls against the new `RATE_LIMIT_DO` binding.
Re-exports `RateLimiterCounter` so wrangler can bind it to this Worker's own
script. Added `isRateLimitExempt()`: `/health`, `/`, `/.well-known/*`, and
`/api/stripe/webhook` are never rate-limited (previously the limiter ran
unconditionally on every path).

**cloudflare/wrangler.mcp.jsonc** — added `durable_objects.bindings`
(`RATE_LIMIT_DO` → `RateLimiterCounter`) and `migrations` (`new_sqlite_classes`).

**src/worker.js** (worker-damp-snowflake-cead) — `RateLimiterCounter` class
and the `checkRateLimit()` helper are now defined inline in this file
(exported alongside the existing `export default { fetch }`), not imported
from a sibling module. See deviation #1. Call site updated to pass `env`
through. `caches.default` is still used, unchanged, for the `/auctions` and
`/county/:slug` **response** cache (that mechanism was already proven
correct via a `cf-cache-status: HIT` test in #20035 and was never the part
that was broken — only its reuse as a *counter* was).

**wrangler.toml** — added the same `durable_objects.bindings` +
`migrations` block as the MCP worker's config.

## Deviations from intent

1. **`worker-damp-snowflake-cead` cannot import a sibling `.mjs` module.**
   This Worker deploys via `wrangler deploy --no-bundle`
   (`.github/workflows/deploy-worker.yml`), and `--no-bundle` uploads do not
   auto-discover additional local modules referenced by `import` — both
   attempts failed live against the real Workers API, even though both
   resolved fine in a local `wrangler --dry-run`:
   - Attempt 1: `import ... from '../cloudflare/rate-limit-do.mjs'` →
     `Uncaught TypeError: Invalid module specifier "../cloudflare/rate-limit-do.mjs"` (error 10021) — parent-directory (`..`) specifiers are rejected outright.
   - Attempt 2: duplicated the file to `src/rate-limit-do.mjs` and imported
     `'./rate-limit-do.mjs'` (same directory) → `Uncaught Error: No such
     module "rate-limit-do.mjs"` (error 10021) — `--no-bundle` simply never
     uploaded the second file.
   - Attempt 3 (landed): inlined `RateLimiterCounter` and the
     `checkRateLimit()` helper directly into `src/worker.js`, matching that
     file's pre-existing zero-import, single-file convention. This is why
     `cloudflare/rate-limit-do.mjs` and `src/worker.js`'s rate-limit section
     are near-duplicates rather than a shared module — a real constraint of
     this Worker's build mode, not an oversight. `biddeed-mcp-production`
     was unaffected throughout (it deploys via the default bundled path and
     resolved `./rate-limit-do.mjs` correctly on its first and only
     deploy).
2. **`biddeed-web-production` (`breverdbidder/biddeed-web`,
   `lib/rate-limit.ts`) was NOT converted to a Durable Object counter —
   deferred, not shipped.** It has the identical `caches.default`-as-counter
   defect (same non-atomic per-colo problem, see the file's own header
   comment). Fixing it correctly requires Cloudflare's Durable-Object-only
   binding to be reachable from Next.js middleware, which OpenNext's
   Cloudflare adapter only supports via its documented "custom worker"
   wrapper (opennext.js.org/cloudflare/howtos/custom-worker) — a
   structural change to that repo's build pipeline, not a config or
   in-file edit. That app handles Stripe checkout and Clerk auth for real
   customers; landing an unverified build-pipeline change there — with no
   local way to fully exercise the OpenNext build/deploy cycle before
   pushing to its production workflow, and a repo I can only reach via a
   throwaway `/tmp` clone — was judged higher-risk than the evidence this
   issue actually requires. **None of the 5 DoD table rows above test
   biddeed-web-production directly** (they cover the two Workers in *this*
   repo only); this deferral does not block any DoD item. Flagged here as
   the clear residual for a follow-up issue scoped to that repo alone.
3. **`/` was added to the MCP worker's rate-limit exemption list**
   alongside `/health`, `/.well-known/*`, and `/api/stripe/webhook`. The
   intent only names `/api/health`, `/.well-known/*`, and Stripe webhooks
   explicitly, but `packages/biddeed-mcp/src/http.js` serves identical
   health-check content on both `/health` and `/` — exempting one without
   the other would leave a live health-check path rate-limited, which the
   intent's own principle ("never rate-limit health checks") argues
   against. This worker has no `/api/health` path; `/health` is its
   closest equivalent, treated the same way.
