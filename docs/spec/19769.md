## What was built (repo: `breverdbidder/everest-cfo-agent`, commit `8d06071`)

### Bug 1 — charts render blank + table toggle empty
Root cause (confirmed by reading `useECharts.ts`): the callback/effect that calls
`echarts.init()` only ran once, tied to the *component's* mount (empty deps array) — but
`ChartCard` doesn't render the chart `<div>` into the DOM until `loading=false` and
`isEmpty=false`, which happens on a *later* render after the initial mount. `ref.current`
was `null` when the init effect fired, so `echarts.init()` was silently skipped forever, with
no console error (headless Chromium confirmed: `canvas count: 0`, `svg count: 0`, no console
errors, matching the issue's own diagnosis). A concurrent session found and fixed this
identically for #19764 (`47ff35d`: moved `echarts.init()` into the same effect that reacts to
`option`/`deps` changes, so it retries every time data changes, succeeding once the div is
finally mounted) — kept their fix, no changes needed to `useECharts.ts`.

While proving that fix end-to-end (see Evidence below), found a **second bug**: the
Chart/Table toggle in `ChartCard.tsx` rendered an empty table. Both the `chart` and `table`
branches are bare `<div>` elements in the exact same JSX tree slot with no `key`, so React
reused the same host DOM node across the swap instead of unmounting/remounting. The chart
div's `ref` gets detached when the table branch renders (that div has no `ref` prop), which
fires `useECharts`' cleanup — disposing the ECharts instance, which clears the node's DOM
content — *after* React had already inserted the table's `<tr>` rows into that same node,
wiping it back to empty. **Fix:** keyed the `loading`/`empty`/`chart`/`table` branches in
`ChartCard.tsx` so every transition between them is a clean unmount + fresh mount, instead of
an in-place DOM node reuse.

### Bug 2 — status banner inverted
Root cause: `CloseBadge.tsx` compared `latest.status !== "success"` against
`finance.cfo_daily_close.status`, whose real values are `'VERIFIED'` / `'FAILED'`
(`20260903b_cfo_daily_close_pipeline_19765.sql`) — this comparison was `true` for every
successful close, always rendering "DAILY CLOSE FAILED". The same concurrent session fixed
the core comparison for #19764 (`ed0bc72`: `failed = latest.status === "FAILED"`), but kept
the 26h stale threshold and let `unbalanced_count` only drive the amber "warning" tone via
the pre-existing `hasIssues` check — not a full implementation of this issue's explicit
3-state spec. Extended on top of their fix to match #19769's literal text: **red only** when
`status <> 'VERIFIED'` OR `unbalanced_count > 0` (previously unbalanced closes showed amber,
and `exceptions_open` also affected tone, which the issue's spec doesn't call for), **amber
only** when stale by **>36h** (was 26h), **green** otherwise. Added a distinct "Books out of
balance" label for the unbalanced-but-VERIFIED case so it doesn't misleadingly read as a
close *failure*.

### Bug 3 — FIXTURE accounts in "All business"
Root cause: `listVizBankAccounts()` (`worker/src/lib/viz.ts`) tags every row
`data_source: "FIXTURE"` when `current_balance_cents IS NULL`, but never filtered those rows
out — every `/api/viz/*` endpoint sources accounts from this one function
(`agent.ts getVizData()`), so FIXTURE rows (e.g. `Business Checking (FIXTURE)`,
`entity_code='biddeed'`/`'everest_capital'`, confirmed live) flowed into cash, cashflow, and
burn's cash-on-hand for every entity including the aggregate "all business" view. **Fix:**
added `.filter(r => r.data_source !== "FIXTURE")` at that single source. Added
`worker/src/lib/viz.test.ts` (2 new tests, mocked Supabase client) as a regression guard,
since this can't be curled live (see Evidence / Finding 1).

### Bug 4 — `finance.bank_accounts.mask` NULL on the 4 real WF accounts
**Found already fixed live** when this session queried current state (see Evidence) — a
concurrent session on the sibling issue #19768 got there first, exactly as #19769's own text
anticipated ("whoever gets there first fixes it, note it in both"). Root cause (read from the
live `pg_get_functiondef`, matches this session's own independent analysis before checking
live state): `workers/everest-bank-engine/src/simplefin.ts` always upserts `mask: null`
(SimpleFIN's API has no mask field), and `public.bank_engine_upsert_accounts`'s original
`on conflict ... do update set mask = excluded.mask` unconditionally overwrote any
previously-good mask with that null on every ~6h SimpleFIN cron tick once the cron
self-healed during #19755/#19762/#19765 (2026-09-02 21:05–2026-09-03 00:01 UTC). The live fix
(already deployed, found via `pg_get_functiondef`) changes the upsert to
`mask = coalesce(excluded.mask, finance.bank_accounts.mask, finance._extract_account_mask4(excluded.name))`
— never let an incoming null blank out an existing mask, with a name-parsing fallback
(`finance._extract_account_mask4`, several account names already embed the mask, e.g.
`"BUSINESS CHECKING ...3519 (3519)"`) for the fresh-insert case. Initially found no
corresponding migration file in this repo for the live fix and drafted one
(`20260903c_cfo_bank_accounts_mask_regression_19769.sql`, matching the live
`pg_get_functiondef` output byte-for-byte) — before committing it, a second `git fetch`
turned up `#19768`'s own commits landing in the interim: `05c6db16` (TS-side —
`workers/everest-bank-engine/src/simplefin.ts` now extracts the real mask from the account
name via `extractMask()` instead of hardcoding `mask: null`) and `38b4266e`, whose
`supabase/migrations/20260903c_cfo_tax_year_2026_readiness_19768.sql` already contains the
**identical** SQL-side `bank_engine_upsert_accounts` coalesce fix plus a one-time backfill
UPDATE, bundled inside their larger tax-readiness migration. Deleted my draft migration file
rather than commit a byte-for-byte duplicate under a colliding `20260903c_` prefix — the fix
is already correctly captured in the repo's history via their commit, this session's job here
was verification only.

--     session's migration commit, 2026-09-03T01:01Z
select ba.mask, ba.plaid_account_id, a.entity_code
from finance.bank_accounts ba left join finance.accounts a on a.id = ba.ledger_account_id
where ba.plaid_account_id like 'simplefin:%' order by ba.mask;
-- 1130 | simplefin:ACT-5f913afc-... | ariel_personal
-- 2308 | simplefin:ACT-79c38056-... | ariel_personal
-- 3519 | simplefin:ACT-03ed8ef3-... | everest_capital_brevard
-- 9264 | simplefin:ACT-1867a707-... | everest_capital_brevard
-- (all 4 real masks present, matches issue's "Evidence to close" query exactly)

-- (2) April 2026 Brevard burn, live re-derivation
select to_char(date_trunc('month', je.entry_date), 'YYYY-MM') as month,
       sum(p.debit_cents - p.credit_cents) as expense_cents
from finance.postings p join finance.journal_entries je on je.id = p.entry_id
join finance.accounts a on a.id = p.account_id
where a.type = 'EXPENSE' and je.entity_code = 'everest_capital_brevard'
  and je.entry_date >= '2026-04-01' and je.entry_date < '2026-05-01'
group by 1;

## Findings (not the task, but worth Ariel's attention)

1. **`CFO_AGENT_SHARED_SECRET` remains unretrievable by any sanctioned path** — same finding
   as #19764. Every session touching this dashboard will keep substituting Playwright-against-
   local-build + live-SQL verification for genuine authenticated-endpoint curl proof until
   this is resolved (recommend adding it to this session type's runner scope, or accepting
   the substitution pattern as permanent).
2. **`api.supabase.com` Management API blocks Python's default `urllib` User-Agent** (Cloudflare
   error 1010) but works fine with a normal UA string via `curl`/any browser-like UA. This
   looked identical to a genuine network block on first attempt and cost real time to
   diagnose — worth documenting in the credential-handling constraints list alongside the
   known `psql`/pooler failure, so future sessions don't waste a turn assuming it's the same
   dead end.
3. **Two sessions worked #19764/#19768/#19769-adjacent bugs concurrently** and independently
   arrived at the same fix for bugs 1 and 2 within minutes of each other (`47ff35d`/`ed0bc72`
   vs. this session's initial, since-discarded commit). No data was lost — caught via
   `git fetch` before push and rebased — but it's a real coordination gap worth flagging: nothing
   in the issue text indicated another session was actively working the identical bugs at the
   same time (unlike bug 4, which explicitly said "whoever gets there first").
4. **`finance._extract_account_mask4` is `GRANT EXECUTE TO PUBLIC`** (default Postgres grant
   for a new SQL function, not explicitly revoked) — low risk since it's a pure, `IMMUTABLE`
   text-regex function with no table access, but noting it since every other function this
   session touched follows the repo's own `revoke all from public / grant to service_role`
   pattern explicitly.
