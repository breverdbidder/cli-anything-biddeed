## Pre-flight findings (re-derived live, not trusted from the brief)

### 1. The SimpleFIN cron was NOT SKIPPED — it had already self-healed
The issue asked to "verify against `public.agent_ops_log` (task=`bank_engine_simplefin_cron_sync`)
before changing anything, and report what it actually says." Live query, before any change this
session:

```
task='bank_engine_simplefin_cron_sync', status='VERIFIED',
evidence={"status":"VERIFIED","accounts":4,"upserted":2,"skipped_no_account":0},
created_at='2026-09-03 00:01:30.287622+00'
```

Root cause: a manual `/simplefin/sync` call during the #19755 session (2026-09-02 21:05–21:24Z)
created `finance.bank_connections` rows with `status='simplefin'` for both linked entities
(`everest_capital_brevard`, `ariel_personal`). `public.bank_engine_simplefin_default_entity()`
needs at least one such row to resolve an entity_code; once it existed, the existing 6h cron
started working on its own. The underlying fragility the issue was actually worried about — a
fresh/rotated access URL with **zero** `status='simplefin'` connections has no bootstrap path
and would SKIP forever — is real, but that specific failure mode has never manifested, and
`finance.daily_close`'s sync step (below) sidesteps it entirely by not depending on any
connection lookup at all.

### 2. `finance.simplefin_sync(p_days)` was NOT "already proven" — it was the bug #19762 just fixed
The issue's own text: *"SQL helper `finance.simplefin_sync(p_days int)` exists ... It works —
chat used it to load 338 real transactions ... Simplest correct option: have the cron call
`finance.simplefin_sync(7)` via RPC ... one code path, already proven."*

Live `pg_get_functiondef` inspection (this session) showed the deployed function:
- inserted `plaid_transaction_id` **without** the `simplefin:` prefix the TS sync path always
  uses, and
- used the **opposite** amount sign from `finance.bank_transactions`'s documented/verified
  convention (positive=outflow, negative=inflow — confirmed in `docs/spec/19755.md` against raw
  payloads).

Per `docs/spec/19755.md`'s own pre-flight finding, the "338" transactions this function produced
were exactly the wrong-sign, unprefixed-id duplicate stub rows deleted in
`supabase/migrations/20260902p_cfo_bank_dedup_simplefin_stub_rows.sql`. Routing the daily-close
cron through this function unmodified — as the issue's literal text asked — would have
re-duplicated every already-synced transaction the moment it ran, undoing #19762's cleanup on
the very first tick. Per CC_META_PROMPT §2.3 ("the DoD query itself may be wrong"), fixed the
function to match the TS path's proven convention (prefix + sign + full raw payload) instead of
calling it as-is. Logged here rather than silently substituted and reported green.

## What was built

### DB (this repo, `supabase/migrations/20260903b_cfo_daily_close_pipeline_19765.sql`)
- **`finance.simplefin_sync(p_days)`** — fixed: `simplefin:` id prefix (with a deterministic
  md5 fallback for transactions missing an `id`), negated sign to match the table convention,
  full raw payload (`{"source":"simplefin"} || t` instead of a stub), `last_synced_at`
  bookkeeping, and distinguishable exceptions for a missing vault secret / 401/403 (credential
  errors) vs. any other non-200.
- **`finance.cfo_daily_close`** — new table, one row per `daily_close()` run. RLS enabled,
  `cfo_agent_ro_select` policy (`using (true)`), `grant select ... to cfo_agent_ro` — same
  pattern as every other CFO-dashboard-readable table in this schema.
- **`finance._send_close_alert(status, summary, reasons)`** — Resend email to
  `everestcapital8@gmail.com`, mirrors the existing `sweep_security_alerts()` pattern
  (vault-only `resend_api_key`/`alerts_from_email`, key never printed or returned). Logs to
  `public.finance_ops_log`.
- **`finance.daily_close(p_from date default null)`** — orchestrator: (a) `simplefin_sync(7)`,
  (b)+(c) `process_bank_transactions(null)` (categorize + post; litigation-gated
  `everest_capital_brevard` stays drafts, per existing `_litigation_gated()` rule), (d)
  `recon_run(null, coalesce(p_from,'2026-01-01'))`, (e) verify `v_recurring_costs` /
  `v_commingled_business_costs` compute without error, (f) `assert_balanced()`. Steps (b)+(c)+(f)
  are wrapped in a nested `BEGIN...EXCEPTION` block — plpgsql gives that block an implicit
  subtransaction, so a detected imbalance `RAISE EXCEPTION`s and Postgres rolls back every
  posting made in that block while the outer function keeps running to log a `FAILED` row and
  fire the alert. Returns a JSON summary; writes one row to `finance.cfo_daily_close`; calls
  `_send_close_alert` only when `status='FAILED'` or any alert reason fired
  (unbalanced / `uncategorized_open > 25` / SimpleFIN credential or sync error / recon or
  cost-view error). On a clean run, no email — matches the issue's "no noise on success."
- **`public.bank_engine_run_daily_close(p_from date default null)`** — thin `SECURITY DEFINER`
  SQL wrapper in `public` (`select finance.daily_close(p_from)`), because PostgREST only exposes
  the `public` schema for RPC (same reason every other `bank_engine_*` wrapper exists —
  `service_role` has no `USAGE` on `finance`). This is the actual invocation path the Worker's
  cron uses.

### Proof the abort path works
Ran a `DO $$ ... BEGIN ... EXCEPTION WHEN OTHERS ... END $$` block using the identical nested
subtransaction construct `daily_close` relies on: inserted a `journal_entries` row plus a single
unbalanced `postings` debit leg (no offsetting credit), detected the imbalance via
`assert_balanced()`, and `RAISE EXCEPTION`'d exactly as `daily_close` does.

```sql
select count(*) from finance.journal_entries where memo ilike '%ROLLBACK TEST%';  -- 0 (rolled back)
select * from finance.assert_balanced();                                          -- 0 rows (books clean)
```

A genuinely unbalanced condition cannot arise from `daily_close`'s normal code path — every
`post_bank_txn`/`post_bank_transfer` insert is constructed as a balanced pair by design — so this
DO-block test proves the rollback *mechanism* the function depends on, rather than forcing an
artificial failure through the real pipeline against live data.

## Negative tests
- Sent a bad/expired-credential path is exercised structurally (the fixed `simplefin_sync` now
  `RAISE EXCEPTION`s distinctly on HTTP 401/403 vs. other failures) but **not exercised live**
  this session — the real `simplefin_access_url` in vault is currently valid, so a genuine
  401/403 response was not available to trigger without breaking a working credential. Tagged
  **UNTESTED** — the code path exists and is reachable (verified by reading it), but end-to-end
  firing of the `simplefin_credential_error` alert reason was not observed live.
- The forced-unbalanced abort path (above) is a mechanism proof, not a `daily_close()`-native
  failure, for the reason stated above (the real pipeline cannot construct an unbalanced pair by
  design). Tagged **VERIFIED** for the rollback mechanism itself, **INFERRED** that
  `daily_close`'s own wrapping of the identical construct behaves the same way (same Postgres
  subtransaction semantics, same exception type).

## Deviations from spec (all disclosed inline above)
1. `finance.simplefin_sync` was rewritten rather than called as-is — the issue's premise that it
   was "already proven" was wrong; using it unmodified would have reintroduced #19762's bug.
2. The SimpleFIN cron was found already `VERIFIED` (not `SKIPPED`) before this session touched
   anything — the issue's stated suspicion did not hold live. Fixed the underlying fragility
   anyway (daily_close's sync step no longer depends on any `bank_connections` bootstrap row).
3. `finance.cfo_daily_close.error` is a single concatenated text field (`"step: message; "` per
   failed step) rather than structured per-step columns — the issue didn't specify a shape here
   and a single field was simplest for what's a rare, human-read diagnostic field.
