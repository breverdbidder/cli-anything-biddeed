## Restore — what was done

Fastest safe path per the issue's own priority order: **did not attempt to unpause via API**
(no evidence the project was in a "paused" state reachable by that verb — `vercel deploy`
resolved and redeployed the existing project directly, which is functionally equivalent and
faster). Went straight to re-running the **existing, already-built** workflow
`.github/workflows/mcp-vercel-deploy.yml` — this workflow already:
- resolves the Vercel project named `biddeed-mcp` by API search (personal scope, then team
  scope) rather than assuming an ID, so it cannot accidentally create a new project or target
  the wrong one,
- has its own `VERCEL_TOKEN` properly wired in its own `env:` block (this workflow was
  already correctly configured — the credential gap found in #19812 was specific to
  `cc-runner-ghonly.yml`, a different workflow),
- builds `api/mcp.js` (which imports `packages/biddeed-mcp/src/http.js`) locally, smoke-tests
  the bundle before shipping, deploys `--prebuilt --prod`, and verifies `/report/pdf` and
  `/api/mcp` on the production alias.

Dispatched via `gh workflow run mcp-vercel-deploy.yml -f environment=production` (run
[`33793975960`](https://github.com/breverdbidder/cli-anything-biddeed/actions/runs/33793975960),
**conclusion: success**, 19:01:29–19:02:35 UTC). This is a **workflow_dispatch of an
existing, unmodified workflow file** — no workflow file was edited, per mandate M5. No Vercel
project was deleted, paused, or had its settings changed; only a fresh `vercel deploy --prod`
was run and the existing `mcp.biddeed.ai` alias was re-pointed to the new deployment (log
line: `▲ Aliased  https://mcp.biddeed.ai`, 19:02:23 UTC).

**Service was restored via the Vercel path, not Cloudflare.** The issue's step 2 (Cloudflare
migration) was not needed once step 1's spirit (fix it on Vercel first, minimum action) was
confirmed correct. `packages/biddeed-mcp` is only imported as a library by the Vercel
serverless function `api/mcp.js` — it is not itself a deployable Cloudflare Worker (no
`wrangler.toml` targets it), so a same-session Cloudflare port would have been a genuinely

### MCP protocol check
```
$ curl -s -X POST https://mcp.biddeed.ai/api/mcp \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}'
{"error":"Authorization required","hint":"Set header: Authorization: Bearer bd_live_xxx (API key) or a WorkOS OAuth access token","get_key":"https://biddeed.ai/dashboard"}
```
This server requires a valid API key/OAuth token on **every** MCP call including
`initialize` — there is no unauthenticated handshake to demonstrate. `mcp_api_keys` stores
only `key_hash` (bcrypt-style, one-way) — **no plaintext customer key exists anywhere this
session can read**, by design, and no test/internal/sentinel key is provisioned as a repo
secret (checked: `gh secret list` has no `*_MCP_TEST_KEY`/`*_MCP_KEY` entry). Minting a fresh
customer key to self-test was not done — that would create a real `mcp_api_keys` /
`mcp_customers` row and is outside this issue's scope (M5).
