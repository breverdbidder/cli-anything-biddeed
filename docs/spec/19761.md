## What this session built (T1-T6)

### T1 — Schema (migration `20260903a_biddeed_reels_presale_schema.sql`, applied live)
Added to `winnerdata.biddeed_reels`: `phase text check in ('presale','postsale') default 'postsale'`, `opening_bid numeric`, `judgment_amount numeric`, `days_to_auction int`, `presale_rank numeric`. Dropped the old `unique(case_number, county)` constraint (`biddeed_reels_case_number_county_key`, confirmed live via `pg_constraint` before touching it) and replaced with `unique(case_number, county, phase)` so the same case can carry both a presale and (later) a postsale row. All 15 pre-existing rows defaulted to `phase='postsale'` — verified unchanged (`select phase, count(*) group by phase` → `postsale=15` immediately after migration, before this session wrote any presale rows).

### T2 — Deal page UPCOMING variant + paid gate (migration `20260903b_...rpc.sql` + `src/worker.js`)
- `get_reel_landing()` gained `phase`/`opening_bid`/`judgment_amount`/`days_to_auction`/`presale_rank` in its returned jsonb (purely additive; postsale callers already ignore unknown keys — regression-checked live, see below).
- **Auth deviation, logged explicitly per K1**: this site has no cookie/session login anywhere in `src/worker.js` — its only auth is the MCP API key issued after a real Stripe checkout (`mcp_api_keys`, Bearer header or `?key=` query param, the exact shape `/report/:mca_id` already uses). "Reuse the existing biddeed.ai auth" is implemented as `public.check_paid_tier(p_key_hash)`, a new SECURITY DEFINER RPC that mirrors `check_s5_report_access`'s exact key-hash lookup — any row in `mcp_api_keys` is by construction a paid subscriber (rows are only ever inserted by `stripe-webhook`'s `issueKey()` post-payment), so "does an active row exist for this hash" *is* the paid-tier check. No new auth system was built.
- **Security design note**: the gated block's real numbers are only ever interpolated into the HTML when the tier check passes server-side. An unauthorized viewer's HTML never contains the real figures at all (masked placeholders like `$•••,•••` are sent instead, then CSS-blurred) — not a client-side blur of real data, so there is nothing to recover via view-source.
- `insert_reel_lead()` gained a 7th param `p_source default 'reel'` (old 6-arg signature dropped first to avoid an ambiguous-overload PostgREST error) so presale's "Set alert" form can write `source='presale_deal'` — server-side allow-listed (`'reel'|'presale_deal'`, else falls back to `'reel'`), never trusts the client's hidden field directly.
- OG tags, `<link rel="canonical">`, and `X-Robots-Tag: noindex` (any URL carrying a `key`/Bearer credential is a personalized variant — never indexed) added to the new presale template only; the existing postsale template (`buildDealLandingHtml`) was not touched (K3 surgical scope).
- **Deviation, fixed same session**: first Playwright screenshot showed the new `.psale-card` was unreadable (white text on the shared shell's light-theme cream background, since `.psale-card` had no background of its own and relied on `<body>`'s background, which the shell `!important`-overrides). Fixed by giving `.psale-card` its own `#020617` background — the pre-existing postsale `.deal-card` has the identical latent gap but was left alone (out of this issue's lane, not newly introduced).

### T3 — Deal pages for all calendar rows, no video (`scripts/biddeed_reels_pipeline_presale.py`)
For every `auction_date = today+2` (or `--auction-date`) row: upsert `biddeed_reels(phase='presale')`, outlined aerial(s) + street shot (reusing v2's `match_zw_parcel_geom`/`build_parcel_aerial_urls`/geocode-fallback path verbatim, same 2-Maps-call cap), vision score via `score_condition()` (OpenRouter GLM primary — never a direct Anthropic/Gemini call), `landing_url`/`short_url`/`qr_url`. No TTS, no video for this step.
- **Column-scope deviation, logged**: T1's explicit column list did not include `flip_rate_pct`/`avg_roi`/`zip_score`/`anchors_in_zip`/`pa_link`/senior-liens/an ML estimate as new columns. Per "reuse all existing columns," these travel inside the already-existing `condition_json` jsonb under a new `presale_intel` key, written at T3 time — no new columns beyond T1's own list were added.
- **"ML max bid / ML score" deviation, logged per K1**: the paid S5 report's real calibrated Shapira model lives behind the MCP server / Modal.com inference and needs a purchase record to query — not reachable or safe to re-implement here. `ml_max_bid` is `round(assessed_value * 0.70)`, a simple honestly-labeled ("Est. Max Bid") heuristic, not a re-implementation of the calibrated model. `ml_recommendation` ("Deal Signal") is a 3-band gap-percentage message. Both are null-safe when `opening_bid`/`judgment_amount` are missing (the common case, per the live numbers above) — rendered as "Pending" rather than a fabricated number.
- **Real bug found and fixed live, mid-session**: `ensure_short_link()`'s no-existing-code branch checked `short_code` uniqueness but never executed the `INSERT` into `winnerdata.reel_links` — all 8 rows' `GET /r/{code}` 404'd on first verification pass. Root cause: `reel_links.reel_id` is a hard FK to `biddeed_reels.id`, and this pipeline (unlike v2, which only re-renders rows v1 already inserted days earlier) creates the `biddeed_reels` row in the same pass as the short link, so the ordering had to change — deal-page upsert now happens first (to get a real `id`), then the short link, then a final small update writes `short_code`/`short_url`/`qr_url`. Backfilled the 8 already-created rows' missing `reel_links` rows directly via SQL (matched by their already-stored `short_code`, no re-spend of vision/imagery calls) rather than re-running the full pipeline. All 8 `GET /r/{code}` re-verified 302 after the fix (see evidence below).

### T4 — Reels for the top 20, ranked (same script, `lib.rank_presale_score()` / `lib.build_presale_script_and_caption()` / `lib.assemble_video_presale()`)
`presale_rank = 0.4×gap_component + 0.25×zip_component + 0.2×condition_component + 0.15×price_tier_component`, each null input defaulting to the 50 neutral midpoint rather than crashing or zeroing a row out of ranking — **weights are INFERRED, not specified by the issue** beyond "f(gap%, zip_score, price_tier, condition_score)"; documented in `rank_presale_score()`'s own docstring. Top 20 (all 8, here) get a rendered reel; top 5 shortlisted. Beat sheet: hook (`AUCTION {Mon DD}` + opening-bid sub) → reveal (county/sale-type lower third) → street (static "Assessed $Y", not an animated count-up — deviation logged: presale has no sale-outcome delta to animate against) → condition badge + 2 pills → payoff ("Bid with data, not guesses.") → CTA card (QR + short URL + a countdown chip, the presale-only addition vs v2's card). `eleven_v3` / brand `voice_id` (same `TX3LPaxmHKxFdv7VOQHJ` as v2), `[excited]`/`[warm]` tags, 3 hook variants by gap band (>=50/25-50/<25, plus an honest 4th "gap unknown" case the issue didn't name but is the common live state).

### T5 — Workflow (`.github/workflows/biddeed-reels-presale.yml`)
Daily cron `10:00 UTC` (independent of the postsale pipeline's `auction_buyer_sightings` dependency, which only exists after a sale closes), `workflow_dispatch` inputs `auction_date`/`force`, per-row error isolation (never raised out of the loop), skip-if-already-rendered unless `--force`. Requires `Pillow` in addition to `qrcode` — an undeclared transitive dependency discovered live this session (see T3 fix below), added to `requirements.txt` and the workflow's install step.

### T6 — Smoke test for 2026-09-04
Ran `python scripts/biddeed_reels_pipeline_presale.py --auction-date 2026-09-04` end to end against production. **8/8 deal pages, 8/8 reels, 5/8 shortlisted.**

## Deviations from spec (all logged inline above, summarized here)
1. Gated presale intel fields (flip_rate_pct/avg_roi/zip_score/anchors_in_zip/pa_link/senior_liens/ML estimate) live inside `condition_json.presale_intel`, not as new `biddeed_reels` columns — T1's own column list didn't include them, and "reuse all existing columns" pointed at the JSONB column that already exists for exactly this kind of structured extra data.
2. "ML max bid / ML score" is a simple, honestly-labeled heuristic (`assessed_value × 0.70`, gap-band recommendation), not the paid S5 report's calibrated model — that model isn't reachable without a real purchase record and living behind Modal.com inference.
3. Presale auth reuses the MCP-API-key mechanism (Bearer/`?key=`), because that is genuinely the *only* auth this site has — there is no session/cookie login to "reuse" instead.
4. Video count-up on the street beat is a static "Assessed $Y" figure, not an animated percentage (v2 animated a sale-outcome delta; presale has no such delta pre-auction).
5. `rank_presale_score()`'s exact weights (0.4/0.25/0.2/0.15) are INFERRED — the issue specifies the four inputs but not their weighting.
