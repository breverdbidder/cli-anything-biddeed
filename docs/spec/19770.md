`docs/spec/19768.md` claims `finance.simplefin_probe_range()` was "written to the repo." It was
not — `grep -rl simplefin_probe_range` across the whole repo returns only the spec doc itself, no

## Pre-flight finding: stale test fixtures would have been posted to the real ledger
While re-deriving `finance.v_bank_coverage` live (rule 1.2), found 4 leftover, never-cleaned-up,
unposted bank_transactions from a prior file-import test session: mask `9998`/`9999`, names
literally `"AMAZON.COM PURCHASE FIXTURE"`, `"PAYROLL DEPOSIT FIXTURE"`, `"NETFLIX.COM FIXTURE"`,
`"UBER TRIP FIXTURE"`, each with an open `recon_exceptions` row and zero `journal_entries` links.
This issue's scope item 3 wires an automatic categorize→post→recon pipeline into every `/import`
call — had these been left in place, the very next import (or the next 6h/daily cron tick) would
have posted four fabricated transactions into the real books. Dry-run counted (4 txns / 2 accounts
/ 2 connections / 4 recon_exceptions, 0 journal_entries), then deleted in FK order
(recon_exceptions → bank_transactions → bank_accounts → bank_connections), verified 0 remaining.
Not part of the issue's named scope, but directly threatened the integrity of the pipeline this
issue builds — same class of pre-existing-bug-that-blocks-the-real-work as #19768's finding 1.

### 3. `/import` tested with a real-format WF CSV and a QFX — idempotency proof
Both formats tested via the same temp proof workflow (run `33704542696`, all 8 steps green),
against two throwaway masks (`0091` CSV, `0092` QFX) never used by a real account, entity_code

DELETE ME ... 19770` so they could never be mistaken for real data.

- **Negative test**: `POST /import` with `X-CFO-Secret: definitely-wrong` → `401` (confirmed).
- **CSV** (no header, `Date,Amount,*,*,Description`, sha256-fallback dedup path — no FITID):
  upload 1 → `parsed:2, upserted:2, skipped_no_account:0, status:VERIFIED`. Upload 2 (byte-identical
  file) → same response shape (`parsed:2, upserted:2` — the RPC's `upserted` counts rows
  **processed**, insert-or-update, by design; it does not by itself prove zero duplicates).
- **QFX** (OFX 1.02 SGML, `<STMTTRN>` blocks with explicit `FITID` — the native-id dedup path):
  same result both uploads, `parsed:2, upserted:2, status:VERIFIED`.
- **Real proof (row count, not the RPC's self-reported count)**, queried live immediately after
  both re-uploads completed:
  ```sql
  select ba.mask, count(bt.id) as txn_count, count(je.id) as journal_entry_count
  from finance.bank_accounts ba join finance.bank_transactions bt on bt.bank_account_id=ba.id
  left join finance.journal_entries je on je.ref_table='finance.bank_transactions' and je.ref_id=bt.id
  where ba.mask in ('0091','0092') group by ba.mask;
  -- 0091 | 2 | 0
  -- 0092 | 2 | 0
  ```
  **2 rows after 2 uploads of the same file, for both formats — zero duplicates inserted on
  re-upload.** `journal_entry_count=0` for both also confirms the auto-triggered
  `daily_close` pipeline did not post this test data to the ledger (its categorization step did
  not match these synthetic descriptions — `categorized_count:0`/`posted_count:0` in both
  `daily_close_summary` payloads), so no ledger cleanup was needed beyond the source rows.
- **Cleanup**: test bank_transactions/accounts/connections for masks `0091`/`0092` deleted
