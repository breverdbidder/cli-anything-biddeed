## Migration verification (disposable local Postgres — production untouched)

Per the issue body's instruction, this migration was **not applied to the live Supabase project**. Instead it was
verified against a throwaway `docker run postgres:15` container (port 15432, destroyed at the end of the session),
seeded with the same `pgcrypto` extension, `anon`/`authenticated`/`service_role` roles (with `BYPASSRLS` granted to
`service_role`, matching how Supabase actually configures that role — a vanilla `CREATE ROLE` does not get this),
a stub `storage.buckets` table, and C2's own migration file (`20260904a_chat_persistence_19829_p1.sql`) applied
first to satisfy the `biddeed_reports.conversation_id` foreign key.

Results:
- Both migrations (`20260904a` then `20260904b`) applied cleanly with `psql -v ON_ERROR_STOP=1`, in order.
- `\d` on all four new tables confirms the exact columns/types/defaults/FKs/CHECKs specified in the issue body.
- `anon` role: `SELECT` on `biddeed_deal_rooms` → `insufficient_privilege` (RLS enabled, zero policies, no grants —
  same default-deny pattern as C2).
- `service_role` (with `BYPASSRLS`): full CRUD works.
- Cross-user isolation, the exact query shapes the Worker runs:
  - `getRoomOwned()` shape: `SELECT id FROM biddeed_deal_rooms WHERE id = '<bob's room>' AND owner_email =
    'alice@example.com'` → **0 rows**.
  - `getReportOwned()` shape: `SELECT id FROM biddeed_reports WHERE id = '<alice's report>' AND owner_email =
    'bob@example.com'` → **0 rows**; the same query with `owner_email = 'alice@example.com'` → 1 row.
- Share link lifecycle: insert → `getShareLink()` shape returns `revoked_at: null` → `revokeShareLinksForReport()`
  shape (`UPDATE ... WHERE report_id = $1 AND revoked_at IS NULL`) → re-query shows `revoked_at` now non-null.
- FK cascade behavior: deleting a room cascade-deletes its `biddeed_deal_room_items` rows and sets
  `biddeed_reports.room_id` to `NULL` (report itself survives, per `ON DELETE SET NULL`); deleting a report
  cascade-deletes its `biddeed_share_links` rows.

## Deviations from intent (material ones, with reasons)

1. **Migration not applied to production.** The issue body says this explicitly for C3 ("NEVER apply DDL to
   production from the runner"), which is stricter than C2's own session (which did apply its migration live via
   the Management API, per the general standing pattern that predates this specific instruction). This session
   followed the more restrictive, issue-specific instruction literally: the migration ships as a file in this PR,
   applied at merge time by whatever process Ariel uses for that (not `supabase db push` from this runner). This
   means every "live" DoD item above is VERIFIED at the schema/logic level (isolated Postgres + a local Worker) but
   UNTESTED against real production rows until the migration lands — flagged explicitly per item above, not
   silently claimed done.
2. **"PDF" is a self-printing, print-styled HTML document, not real PDF bytes.** There is no server-side PDF
   generator anywhere in this Worker, and `wrangler deploy --no-bundle` (zero `import` statements — reconfirmed
   before writing this code) rules out adding an npm PDF library without also editing the deploy workflow (out of
   scope per M5). This reuses the *exact* mechanism the existing S5 report's own "Download PDF" button already
   relies on (`renderS5ReportHtml`/`s5Page`'s `#dl-pdf` → `window.print()`): the stored `format='pdf'` object is a
   print-styled HTML page that auto-triggers the browser print dialog on open, and "Save as PDF" there produces a
   real PDF. This is the same class of constraint C2 hit for DOCX/OCR uploads (documented in
   [docs/spec/19829-P1.md](19829-P1.md) Deviation 9) — flagged here rather than silently claiming a real PDF
   byte-stream exists.
3. **CSV generation is conditional on a literal signal, not inferred property data.** The schema for a chat message
   is free text; there is no structured "property table" attached to a conversation anywhere in this codebase. The
   only honest, non-fabricating heuristic available is detecting an actual markdown pipe table in an assistant
   message (Deed frequently renders one when discussing multiple properties) — if none exists, no CSV row is
   created, matching the issue's own "when the conversation has a property table" wording. This is a real,
   testable signal (unit-tested above), not an invented one.
4. **`GET /chat/api/reports/:id/download?format=` — `:id` is the specific report row, `?format=` is a validation
   guard.** Each `biddeed_reports` row already has exactly one `format`; a POST to `/chat/api/reports` can create up
   to three sibling rows (json/pdf/csv) sharing the same `conversation_id`+`version`. The route resolves `:id` to
   its own row and, if `?format=` is also passed, 400s on a mismatch rather than silently ignoring it or trying to
   guess which sibling row was meant.
5. **Share-link revoke is scoped to the whole report, not one specific token.** The issue names `POST
   …/revoke` as a continuation of the `/share` sub-resource path (`/chat/api/reports/:id/share/revoke`) without a
   token parameter in the route shape. `revokeShareLinksForReport()` revokes every currently-active link for that
   report id (there is normally exactly one), which satisfies the literal acceptance test ("share link 200 then 404
   after revoke") without inventing a second, unspecified route parameter.
6. **No dedicated Room-detail view.** The issue's explicit UI ask is "left sidebar 'Deal Rooms' list... above
   Recent chats" and "right side panel 'Report'... Add to Room on any message" — a full room-detail screen (listing
   every item inside a room: conversations, reports, uploads, parcels together) is not named in the acceptance
   criteria and was not built. Clicking a room in the sidebar (outside of the "Add to Room" picker flow) currently
   loads that room's **reports** into the right panel — a real, working action, not a dead click — but does not yet
   show the room's other item kinds (conversations/uploads/parcels). Flagged as a scope cut, not silently shipped
   as complete room management.
7. **Report generation is per-conversation only.** `POST /chat/api/reports` requires `conversation_id`; there is no
   route to generate a report from a whole Deal Room's aggregate content (multiple conversations). The issue body's
   route list only specifies "generate from a conversation," so this matches the literal spec — flagged in case
   room-level report rollups are wanted in a follow-up.
