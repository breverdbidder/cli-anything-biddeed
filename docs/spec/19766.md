## Negative test result

No generic validator exists in this repo for arbitrary vendored skills —
`scripts/validate_platform_skills.py` is intentionally narrow: it hardcodes a 5-item
`CANDIDATES` list (`zonewise-scraper`, `cost-discipline`, `honesty-protocol`, `brand-colors`,
`ship-gate`) and requires `## Role`/`## Working Mode`/etc. sections + a 25-assertion
`eval.json` — that is the **Platform Skills** harness format (a different, stricter concept
from a plain vendored community skill; the existing `wizard`/`writing-for-agents` precedent
also has no `eval.json` and is not in that list). Adding these 14 to that list would
misclassify them.

Instead, reimplemented the accepted repo's own MIT-licensed `validate-skills.sh` rule set
(name present & matches directory, description present & ≥20 chars, frontmatter properly
delimited, SKILL.md ≤500 lines as a non-blocking WARN — matching upstream's own severity,
since it's a `skill_warnings` not `skill_errors` check there) as a standalone Python script.

- **Negative test:** wrote `/tmp/negtest/broken-skill/SKILL.md` with no frontmatter
  delimiters, a `name` that doesn't match its directory, and a description under 20 chars.
  Ran the validator against it → `FAIL broken-skill: Missing YAML frontmatter (---)`,
  exit code 1. Confirmed failing as required.
- **Positive test:** ran the same validator against the 14 newly-installed skill
  directories → all 14 `PASS`, exit code 0 (`seo-audit` lands at exactly 500 lines,
  the upstream's own non-blocking threshold, after the one-line Everest-context
  insert pushed it from 499).
- **Full-repo sweep (informational only, not part of DoD):** ran the same script against
  all of `.claude/skills/`. 16 pre-existing directories fail this ruleset (`dream` has no
  frontmatter at all — it's a different skill format entirely; several skills exceed 500
  lines, e.g. `nodejs-backend-patterns` at 1042; `react-best-practices` and `search` have a
  frontmatter `name:` that doesn't match their directory name). None of this blocks anything
  — it just confirms this repo has never enforced that convention repo-wide, so the 14 new
  skills are held to a stricter bar than their neighbors, not a looser one.

## Deviations from intent

Two surgical, mechanical edits applied to every vendored `SKILL.md`, per the issue's explicit
instruction ("stripping human approval gates (zero-HITL adaptation) and adding Everest context
pointers"):

1. **Zero-HITL strip** (6 of 14 files: `ai-seo`, `cold-email`, `churn-prevention`, `revops`,
   `lead-magnets`, `directory-submissions`) — each had one "gather context (ask if not
   provided)" / "ask the user these N questions" line. Rewritten to: infer from repo/session
   context, tag the assumption `INFERRED` per Honesty Protocol, don't block waiting for an
   answer nobody will give in a headless `claude -p` session. No other prose touched.
2. **Everest context pointer** (all 14 files) — one blockquote line inserted immediately
   after the `# Title`, pointing at the README attribution section and flagging MANDATE M3
   (no vendor/tool/internal-ID names in client-facing output) for the skills whose output can
   reach real people (cold email, PR pitches, launch copy).

No other content was rewritten, reformatted, or reorganized — `references/*.md` and
`evals/evals.json` under each skill copied byte-for-byte from upstream.
