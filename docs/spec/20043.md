## Item 1 — Section 18 Auction Outcome loop — FIXED (VERIFIED)

**Finding (contradicts the issue's assumed mechanism — logged as a
deviation):** the issue described the bug as "renders Pending even when
sold_amount/winning_bidder/sale_result_date are populated." That is not
what's live. `packages/biddeed-mcp/src/report/outcome.js` already read
`tier1_sold_amount`/`sold_amount`/`sale_result_date`/`winning_bidder`
directly off the auction row (no separate "post-sale loop" table) — I
regenerated the actual bug by pulling the cached report_json for case
250104 (`s5_pdf_cache` row `mca_id=19499973-5191-4e5b-bb96-c0f59fb14101`,
`generated_at=2026-08-05T12:42:34Z`): `sold_amount`/`tier1_sold_amount` are
genuinely NULL for that row — there is no unread sale price. The real bug:
`tier1_sale_status='CANCELED'` (`auction_status='cancelled'`) on a past
auction rendered `"Pending — outcome not captured — the post-sale result
loop has not written sold_amount/winning_bidder for this auction"`, which
is false — the outcome IS known (the sale was canceled), it just isn't a
sale. This is the "outcome not captured on an Oct-2025 sale" the issue's
own baseline note refers to.

**Fix:** `outcome.js` now recognizes 8 terminal no-sale
`tier1_sale_status` values (vocabulary sourced from existing harvest
scripts, not invented — see file comment) and renders `"Canceled — no sale
occurred (tier1_sale_status=X)"` instead of "Pending", with the scorecard
correspondingly withheld with a distinct reason. New field
`terminal_no_sale` added to the section-18 JSON.

**Tests:** `packages/biddeed-mcp/test/outcome-terminal-no-sale.test.js` (3
cases) — run against the real case-250104 field values. `node --test`:
3/3 pass (VERIFIED, command run this session).

**DoD ("count of cached reports whose underlying auction has sold_amount
but section 18 says Pending: before/after")**: reframed per the finding
above — no cached report in this instance's 6-row cache has a populated
sold_amount with section 18 still showing Pending (checked directly: none
of the 6 cached rows have non-null `sold_amount`/`tier1_sold_amount`).
The population this fix actually changes is the 6,324 (2024+) /
8,602 (all-time) terminal-no-sale rows above, which is larger and more
consequential than the issue's literal ask.
