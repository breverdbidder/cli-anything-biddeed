## A real infrastructure finding this session (not assumed, live-reproduced)

Issue #19782 requires "No Anthropic API calls in any agent (router t1/t1.5,
OpenRouter GLM/DeepSeek, or Ollama on the runner only)." `claude-router`'s
own T1/T1.5 tiers (the "router t1/t1.5" the issue names) were live-tested
and found non-functional this session:
- `T1_gemini_free`: the vault key (`gemini_api_key_biddeed`) resolves fine,
  but live calls consistently cascade past it.
- `T1.5_deepseek_cheap`: `get_vault_secret_mcp('deepseek_api_key')` returns
  `None` — the secret is absent from vault, matching a comment already in
  `supabase/functions/claude-router/index.ts` dated 2026-08-03 ("Fixed
  2026-08-03: deepseek_api_key is absent from vault.secrets so T1.5 never
  enters the cascade") — a known, pre-existing gap, not something this
  session broke.
- Two independent live calls (force_tier=gemini, then no force_tier) both
  landed on `T2_claude_oauth`/`provider=anthropic`. `agents/reel_studio/
  router_client.py` correctly refused both (`RouterBlockedAnthropicTier`) —
  it does NOT trust `force_tier` alone to guarantee non-Anthropic, since the
  router's own code doesn't gate T2 by `force_tier` (read directly from
  `index.ts`, not assumed).
- Worked around with the issue's other explicitly-allowed path: direct
  OpenRouter GLM (`z-ai/glm-5.3-flash`), vault key `openrouter_api_key`
  (same key `T10`'s vision cascade already uses — not a new credential).
  Required `reasoning: {"exclude": true}` and a 3500-token budget per call
  (live-observed: this model spends 800-1000+ tokens on a hidden reasoning
  trace even with `exclude:true`, before any visible content; 1200 tokens
  truncated with `finish_reason=length`). Requesting all 4 variants in one
  call reliably hit `finish_reason=error` around 100s; switched to one
  OpenRouter call per variant (~30-60s each, reliable).
- `router_client.py` also closed a real gap found by its own eval: a cache
  HIT (`tier=cache`, `provider=cache`) can carry a `model` field that
  started life as a Claude generation — the tier/provider fields alone
  don't reveal that. Fixed to also inspect the `model` string for `claude`.

## A second real infrastructure finding (mid-session, live-caught)

While verifying `resolve_reel_link` post-insert, `select
public.resolve_reel_link('F5oeMD')` (a real, freshly-minted variant short
code) returned `null` instead of the expected redirect target. Investigation
(`pg_get_functiondef('public.resolve_reel_link(text)'::regprocedure)`)
showed the live function body no longer contained any reference to
`reel_variants` at all — a **different, concurrent process** (not this
session) had run its own `CREATE OR REPLACE FUNCTION` on the same function
in the time between this session's original migration and this check,
which is a full overwrite in Postgres, not a merge. The other session's
version added its own columns (`winnerdata.biddeed_reels.archetype`,
`winnerdata.reel_links.utm_content`) for an apparently-related but distinct
feature. Fixed by re-applying the `reel_variants`-first branch as an
additive prefix on top of the CURRENT function body (preserving the other
session's archetype/utm_content additions rather than reverting them) —
`supabase/migrations/20260903f_reel_variant_studio_resolve_link_fix.sql`,
applied live, re-verified: `resolve_reel_link('F5oeMD')` now returns the
correct variant target, an unknown code still correctly returns `null`.
Flagged here because it's a real example of the multi-session concurrency
risk this repo's CLAUDE.md documents elsewhere (FLEET lanes, parallel
SUMMIT worktrees) — a function is not a safe "additive-only" surface the
way a new column or new table is, since a later `CREATE OR REPLACE` from
anywhere can silently drop an earlier session's logic.
