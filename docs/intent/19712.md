# Intent — issue #19712 — FF billable-loop (enrichment state machine + attempt ledger)

## Originator
Ariel Shapira (founder), 2026-09-02, in his words: "the data scraping and the additional information like the skip tracing and other tools and platforms ... have no commitment to create the information including the Sunbiz chain of information to create full loops until FFs each of them become billable."

## Problem, in the originator's words
The Daily Winner FF pipeline runs enrichment once. When a provider returns nothing, the lead is labeled NOT AVAILABLE and never touched again. Nothing keeps working the lead through the remaining sources (Sunbiz chain, skip trace, web) until it is billable. This is the first product Claude AI + Claude Code + Ariel have monetized, and 22 of 37 leads are sitting non-billable with zero provider attempts on record.

## Outcome that counts as done (DoD)
1. winnerdata.ff_enrichment_attempts exists (RLS on) and has >=1 row for each of the 22 currently non-billable leads.
2. Leads meeting the 2-of-3 rule > 15 (baseline 15). Report exact before/after.
3. ff_batch_leads.row_enrichment_status constrained to the state set below; contact_confidence constrained to the 5 canonical strings; 0 NULL contact_confidence; 0 rows spelled 'VERIFIED_CROSS_CHECKED'.
4. No lead is EXHAUSTED without a ledger row for every applicable stage.
5. billable_ff_events count == count of leads with row_enrichment_status='BILLABLE' that have been delivered (currently none newly delivered — so no new billable rows this session unless a prior delivered lead flips).
6. ff-billable-loop.yml committed, pg_cron 'ff-billable-loop-tick' scheduled every 30 min.
7. docs/spec/19712.md written with a stage × outcome table.

## Non-goals
No sends (M1). No LMS changes. No cc-runner-ghonly.yml edits. No new paid subscriptions. No touching winnerdata.ff_digest_log or billable_ff_events except the reconciliation in DoD 5.

## State machine (row_enrichment_status)
not_started → stage1_identity → stage2_sunbiz_chain → stage3_skiptrace → stage4_web → stage5_dnc → BILLABLE | EXHAUSTED ; retry_due re-enters at the stage recorded in the ledger.
Re-evaluate 2-of-3 after EVERY stage; the moment it is met, set BILLABLE and stop spending credits.

## Stage plan by identity_type
- person / person_joint: stage1 fl_parcels own_name self-match → mailing address; stage3 Tracerfy enhanced at that address; stage4 Exa/Crawl4AI for email; stage5 DNC + phone validity. Sunbiz stage applies only if the person appears as an officer of an entity holding the parcel.
- business: stage1 fl_parcels match on entity name; stage2 Sunbiz chain — entity → officers/principals (names + addresses) → registered agent → sibling entities sharing the same RA or mailing address → principal home address via fl_parcels own_name match on each principal; stage3 Tracerfy find_owner on principals; stage4 Apify/Exa/Crawl4AI for business website, business phone, business email, LinkedIn; stage5 DNC.
- land_trust_unpierceable: stage2 trustee → if attorney-trustee, pull sibling trusts with the same trustee and the deed grantor from Brevard clerk/property appraiser records (public); stage3 Tracerfy on any named beneficiary/grantor; if still nothing after all stages, EXHAUSTED with reason 'attorney_trustee_shield' — this is a legitimate exhaustion, not a miss.
- Any row with contact_match_status='MATCHED_PRINCIPAL_DNC_BLOCKED': address + email path only; never re-attempt phone.

## Task-specific mandates
- One ledger row per provider call, no exceptions. A stage with no ledger row did not happen.
- EXHAUSTED requires every applicable stage to have outcome in ('miss','error'). A credit-gate skip is 'skipped_gate' and forces retry_due, never EXHAUSTED.
- Claim protocol on every lead pickup (shard rule): update ... set row_enrichment_status=<next stage>, ... where (batch_date,case_number)=($1,$2) and row_enrichment_status in ('not_started','retry_due') returning case_number; no row → skip.
- The 22 leads must actually be run this session, not just scheduled.
